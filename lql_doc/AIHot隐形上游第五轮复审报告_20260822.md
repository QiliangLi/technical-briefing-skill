## 三、阻断问题

### P1-1：ledger-status 仍可遮蔽真实失败，且不验证 DB 完整性

位置：

- `briefing_skill/adapters/aihot.py:556-591`
- `briefing_skill/publication_stage.py:121-147`
- `briefing_skill/utils.py:241-249`

本提交已修复第四轮指出的两个状态翻转问题：resume 成功会清除旧错误，resume 失败会重新记录错误。但发布门把“sidecar 中没有 `last_error`”直接等同于“ledger 完整”，仍然 fail-open。

已复现三种情况：

1. freeze 中存在真实 `ledger_error`，在同目录放置空对象 `{}` 的 `ledger-status.json`，发布门返回 `[]`；
2. run B 使用 run A 的健康 sidecar，发布门仍返回 `[]`，因为没有验证 `status.run_id == active run_id`；
3. 模拟 `upsert_radar_upstream_records()` 静默 no-op：采集有 1 条记录、数据库实际为 0 行，但 sidecar 写出 `records_attempted=1, last_error=null`，发布门仍放行。

另外，sidecar 使用普通 `write_text`，不是临时文件 + 原子替换。若进程在写入时中断产生截断 JSON，当前读取会抛解析异常，而不是形成明确、可恢复的 validation failure。

影响：内部 upstream ledger 实际缺失、属于其他 run，或状态文件损坏时，仍可能发布；这违反 run 隔离、审计完整性和 resume 幂等要求。

建议：

- sidecar schema、`run_id`、`records_attempted`、状态枚举全部必填并严格验证；
- 从 active run 的 freeze/采集结果推导预期 `record_id`/内容 hash，与 DB 中该 run 的实际集合精确比较；
- 只有 DB 集合完整时，健康 sidecar 才能覆盖历史 freeze 中的旧错误；
- sidecar 缺失、损坏或属于其他 run 时 fail closed，并提供旧 run 的显式迁移/重建路径；
- 用同目录临时文件 + `os.replace` 原子写 sidecar。

### P1-2：active-run 与报告时间锚点仍是部分修复

位置：`briefing_skill/publication_manifest.py:463-486`

已经生效的部分：

- direct、manifest、freeze 中存在且错误的非空 run ID 会被发现；
- direct 的 `reference_date` 与 `issue.json.date_to` 非空但不一致时会失败；
- direct 时区与可读取配置中的时区不一致时会失败。

仍可放行的最小复现：

- 删除 active `issue.json` 的 `date_to`，完整发布链仍返回 `errors=[]`；
- 删除 manifest 的 `run_id`，仍返回 `errors=[]`；
- 配置不可读时，`configured_timezone()` 返回 `None`，时区校验被直接跳过；
- 校验只读取同一 run 目录中的 `issue.json`，没有和 SQLite `issues` 表中 active issue 的 `run_id/date_to` 交叉核对。

影响：缺失或来自陈旧文件系统状态的报告日期仍可能被接受，不符合 AGENTS 对“最终日期必须来自 active run；缺失/非法上游数据必须显式失败”的要求。

建议：

- active issue 日期、manifest run ID、配置时区均设为必填，不能使用 truthy 条件跳过；
- service-aware validation 从 DB 查询 active issue 的 `run_id/date_to/issue_json_path`，再与 issue JSON、direct、manifest、freeze 逐层比较；
- 配置缺失或无法解析时输出明确 validation failure，而不是取消时区校验。

## 四、应修复问题

### P2-1：`source_name` 和规则版本仍未完整进入发布契约

位置：

- `briefing_skill/radar_direct.py:698-730`
- `briefing_skill/publication_manifest.py:539-576,632-641`

已复现：

- 删除 manifest 的 `source_name`，校验返回 `[]`；
- 同步把 direct、manifest、DOM 的来源名改成“伪造站点”，原 selection hash 无需变化，校验返回 `[]`；
- 把规则版本改为 `0`，重算 selection hash 并更新 manifest 回链后仍可通过；
- 把 direct 顶层 `version` 改为 `999` 也不会产生错误。

原因：

- `_selection_binding()` 没有包含 `source_name`；
- manifest 来源名为 `None` 时明确跳过比较；
- 版本校验只拒绝 `> current`，没有明确的最小值或支持版本集合；
- 顶层 `version` 与新增的 `direct_copy_version` 并存，但没有明确校验语义。

建议：从 canonical URL 确定性重算公开来源名，把它和 `radar_id` 一起纳入 selection hash；manifest 字段必填。规则版本使用显式支持集合，例如 `{1}`，并明确顶层 `version` 是 schema version 还是废弃别名。

### P2-2：全量测试在上海/UTC 换日窗口不稳定

位置：`tests/test_radar_direct.py:23-30,458-479`

测试用：

```python
NOW = datetime.now(timezone.utc)
REFERENCE_DATE = NOW.date().isoformat()
```

生产代码则把 `REFERENCE_DATE` 按 `Asia/Shanghai` 当天 23:59:59 解释。2026-08-22 00:18 上海时间仍是 2026-08-21 16:18 UTC，所谓“8 天前”的 fixture 到上海报告日末实际只有约 7.99 天，因此被正确纳入 7 天窗口，断言却期待排除。

当前实测：

```text
FAILED tests/test_radar_direct.py::test_freshness_uses_report_date_not_wall_clock
1 failed, 479 passed
```

这不证明生产逻辑错误，但意味着“480 全绿”不能跨时区边界稳定复现。建议使用固定 aware datetime，或先在配置时区构造 reference day，再从该 reference 精确减 6/8 天生成 fixture，不要混用 import-time UTC `NOW`。

### P2-3：设计要求的 shadow run 仍未闭环

仓库中仍只有设计、运维建议和历次复审文字，没有“同一冻结输入下，旧 Radar 与 direct-copy Radar 的差异产物、阈值和签收结果”。`config/scoring.yaml` 仍默认启用 `direct_copy: true`。

这不是本提交新增的代码错误，但仍是设计文档明确要求的上线验收项。建议至少保存一期可复现的对比结果：条数、重复率、分类覆盖、具体原始页比例、文案差异、公开痕迹扫描和签收结论。

## 五、低优先级观察

### P3：“具体原始页”仍主要依赖 URL 形状

位置：`briefing_skill/radar_direct.py:303-319`

本提交已经让 `https://example.com/?p=123` 这类 query 路由通过，修复了第四轮的一半问题。但当前逻辑接受任意非空 query，也仍接受 `/news` 等频道路径，无法真正区分文章详情页和列表页。

建议至少识别稳定内容 ID query 和常见频道/列表路径；更可靠的做法是保存 upstream original-page 类型或解析后的 canonical/页面元数据，而不是仅凭 URL 形状判断。
