## 三、仍然阻断发布的问题



### P1-1 ledger 的新 record_id 与旧唯一约束冲突，会清空整个 AI Hot 批次



相关代码：



- `briefing_skill/db.py:219-249`

- `briefing_skill/db.py:393-441`

- `briefing_skill/adapters/aihot.py:496-547`

- `briefing_skill/collection.py:68-84`



修复提交已经把 `record_id` 绑定到完整 `lane_key`，使同一 item 在不同 query lane 中可以拥有不同审计记录；但表结构仍保留：



```sql

UNIQUE(run_id, provider, upstream_lane, upstream_item_id)

```



两个 `all:<query>` lane 的 `lane_key` 不同，`upstream_lane` 却都等于 `all`。当它们命中同一个 `upstream_item_id` 时，第二条记录违反旧约束。当前 upsert 只声明 `ON CONFLICT(record_id)`，无法处理这个冲突。



最小复现得到：



```text

sqlite3.IntegrityError: UNIQUE constraint failed:

radar_upstream_records.run_id,

radar_upstream_records.provider,

radar_upstream_records.upstream_lane,

radar_upstream_records.upstream_item_id

```



更严重的是，`_write_ledger()` 在 collector 返回之前执行。异常会冒泡到 collection 外层，外层把该 provider 的 `items` 替换为空数组。因此只是一个内部审计表冲突，就会静默丢掉所有已经成功采集的 AI Hot 内容，违反 briefing integrity 和“单 lane 失败不清空成功结果”的目标。



现有测试只覆盖同一 item 同时出现在 `all` 和 `paper`，两者的 `upstream_lane` 不同，所以没有触发该约束。



建议：



1. 对现有 SQLite 数据库执行显式表重建迁移，删除旧四列唯一约束；

2. 以 `record_id` 为唯一审计身份，或建立包含完整 `lane_key` 的新唯一键；

3. 增加两个不同 `all:<query>` 命中同一 item 的回归；

4. ledger 写入失败不能把已成功采集的公开候选静默降为零，应显式失败或把 collector 结果与审计失败分开处理。



### P1-2 跨期 story/item 去重修复没有进入生产发送路径



相关代码：



- `briefing_skill/emailer.py:742-761`

- `briefing_skill/bootstrap.py:136-142`

- `briefing_skill/publication_history.py:12-19`

- `briefing_skill/publication_history.py:213-235`

`EmailService._record_sent` 中新增了从 `issue_radar_items` 投影 `upstream_item_id` 和 `story_id` 的 SQL，这段代码单独看是正确的。但 bootstrap 最后调用 `install_publication_history()`，把该方法替换为 `publication_history.record_delivery`。



真正的生产 owner 使用 `PublishedSource`；这个数据结构没有 story/item 字段，`_project_compatibility()` 写 `radar_history` 时也只写 URL、规范化标题、发送时间和 issue ID。



复现方式是先在 `issue_radar_items` 写入 `item-42/story-42`，再调用生产使用的 `record_delivery()`。发送完成后查询 `radar_history`，两个字段仍为 `NULL`。下一期候选虽然会读取 `history_item_ids/history_story_ids`，但历史中根本没有这些值，同一故事换 URL 和标题后仍会再次发布。



新增测试 `test_cross_period_story_identity_blocks_republish` 直接手工构造了包含 story/item 的 `radar_history`，只证明“如果历史里已有身份，读取侧能去重”，没有覆盖“真实发送是否写进去”。



建议：



1. 只保留一个 canonical SENT owner；

2. 在 `record_delivery` 中按最终 Radar URL 回查 `issue_radar_items`，或把 story/item 加入 canonical `PublishedSource` 和 publication history schema；

3. 用 bootstrap 后的 `EmailService._record_sent` 做连续两期端到端回归：第一期真实记录发送，第二期同 story 换 URL/标题必须被挡住。



### P1-3 直出完整性仍是自证闭环，没有锚定真实 freeze



相关代码：



- `briefing_skill/radar_direct.py:628-690`

- `briefing_skill/publication_manifest.py:300-317`

- `briefing_skill/publication_manifest.py:407-498`



新代码已经能做到：



- 对 `radar-direct.json` 内的 title/summary span 和 hash 做内部自洽检查；

- 把最终 DOM 的 title/summary hash 与 `radar-direct.json` 比较；

- 检查 direct-copy 模式缺文件、缺条目或多条目；

- 写入更完整的 `selection_hash` 和 `frozen_input_sha256`。



这些修复有价值，但最终发布门仍没有：



1. 重新计算并验证 `selection_hash`；

2. 验证记录的 `frozen_input_sha256` 等于当前 freeze 文件 hash；

3. 根据 lane key、item ID、source field 回到 freeze 中定位真正的原始字段；

4. 对比 manifest 的 `summary_sha256`；

5. 验证 selection 声称的 category 和报告日期确实被绑定。



因此，当前链条实际是“radar-direct 自己声称一个 source_text，然后 HTML 与它一致”，而不是“最终公开字符可证明来自那份冻结输入”。主审和交叉审查都复现了联合篡改：把 `radar-direct.json` 的 source text/span/hash 与 HTML 同时改成另一段自洽文字，保留陈旧的 selection hash、freeze hash 和 manifest summary hash，发布校验仍返回空错误。



另外，`record_direct_publication()` 把 group items 展平后没有注入 group 名称，而 `_selection_hash()` 读取 `item.get("category")`；常规 item 通常只有 `category_key`，所以 selection hash 中的 category 可能为 `None`。



建议建立单向可验证链：



```text

freeze 响应

  -> 精确 lane_key / item_id / source_field / span

  -> radar-direct.json

  -> selection_hash + publication-manifest.json

  -> 最终 DOM

```



发布时应从最左侧重新计算到最右侧，任一文件缺失、hash 不一致、条目无法在 freeze 定位都 fail closed。还应把 active report date、真实 group category、规则版本和公开字段全部纳入重算对象。



### P1-4 同一 run 改 lane plan 会产生新 freeze 与旧 raw_items 的 split-brain



相关代码：



- `briefing_skill/adapters/aihot.py:195-250`

- `briefing_skill/collection.py:173-223`



lane plan hash 不一致时，现在会把旧 freeze 整体判为失效并在同一 run 重新联网，这解决了“部分回放、部分补抓”的旧问题；但它又引入了更直接的 run 幂等问题：



1. 新响应覆盖同一 run 的 `freeze.json`；

2. `raw_items.id` 对稳定 item 保持不变；

3. `CollectionService.persist()` 使用 `INSERT OR IGNORE`；

4. 数据库中的旧 title/summary/payload 不会更新，被新 plan 删除的旧 item 也不会删除。



复现后，freeze 保存的是新摘要，`raw_items` 仍是旧摘要。后续 Radar 从数据库读取旧内容，provenance 文件却记录新 freeze hash。该状态同时破坏 run isolation、resume 幂等和直出溯源。



建议在以下方案中明确选择一个：



- active run 一旦产生 freeze，lane plan/config hash 变化就报 stale-run 错误，要求创建新 run；这是风险最低的方案；

- 或者在一个事务中完整重物化该 run 的 AI Hot raw/candidate/ledger/下游状态，并原子替换 freeze，保证不存在新旧混合状态。



只覆盖 freeze、保留旧数据库状态不可接受。回归测试必须经过真实 `CollectionService.persist()`，不能只测 collector 返回值。



### P1-5 报告日期已绑定 active run，但没有按配置时区解释



相关代码：



- `briefing_skill/radar_direct.py:272-299`

- `briefing_skill/radar_direct.py:389-402`

- `briefing_skill/freshness.py:19-34`

- `config/settings.yaml:2`



这次修复已经消除了墙上时钟：缺少 `issue.date_to` 会明确报错，同一裸日期不会随 resume 当天变化。这解决了上一轮问题的一半。



剩余问题是 `date_to` 以 `YYYY-MM-DD` 传给 freshness，`reference_datetime()` 把裸日期解释为 UTC 的 23:59:59；仓库配置却是 `timezone: Asia/Shanghai`。报告日末应当先构造上海时间 `23:59:59`，再转换为 UTC。



边界例子：原始发布时间为 `2026-08-14T00:30:00+08:00`，报告日期为 `2026-08-21`。当前实现计算为 8 天并淘汰，按上海日末计算应为 7 天，仍符合 Radar 的 7 天窗口。该问题会静默丢掉时区边界内容，也不满足 AGENTS 规则“final date must come from active run and configured timezone”。



建议从配置读取 `ZoneInfo`，用 active report date 构造配置时区日末的 aware datetime，再传给 `published_age_days`；非法时区必须明确报错，不能回退 UTC。
