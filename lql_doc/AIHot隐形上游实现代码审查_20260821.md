## 一、结论

结论：**需要修改后再合并或默认启用（Request changes）**。

四个提交已经搭出了正确的主体结构：多 lane 采集、run 内冻结、304 响应体回放、确定性 Radar 选择、公开痕迹扫描、归档阻断、Idea 证据隔离等都已落地；全量测试也确实通过。但是目前仍有 7 个高优先级正确性问题和若干中优先级契约缺口：

1. 发布门没有真正验证公开摘要的 hash/span，摘要被改写或篡改仍可通过；
2. Radar 新鲜度使用执行当天而不是 active run 的报告日期，同一冻结 run 隔几天 resume 会得到不同结果；
3. AI 日报日期被伪装成原始发布日期并公开展示；
4. 未核验 Radar 在晋升 cluster 后仍可直接成为 Roadmap stage 的支持证据；
5. 跨期历史没有保存 story/item 身份，同一事件换 URL 和标题后会重复发布；
6. 历史归档 `apply-rewrite` 可以绕过上游痕迹扫描并流入 Pages；
7. `reason` 会在没有 summary/description 时被当作公开摘要；
8. 多 lane 合并会提前丢弃其他摘要版本，可能把本来可用的中文摘要静默淘汰；
9. 冻结文件、选择 hash 和标题溯源还没有达到设计文档声明的可复现强度。

因此，`447 passed` 说明现有测试没有回归，但不能证明设计验收已完成。

## 三、必须修复的问题

### P1-1 发布门没有校验 Radar 公开摘要，直出完整性契约可以被绕过

相关代码：

- `briefing_skill/publication_manifest.py:353-425`
- `briefing_skill/publication_stage.py:102-118`
- `briefing_skill/radar_direct.py:438-456`

`radar-direct.json` 保存了 `source_text_hash`、span 和 `public_text_hash`，manifest 也保存了 `summary_sha256`；但最终 `Renderer.validate` 调用的 `publication_provenance_errors` 只比较 Radar 的分类、标题和 URL，没有读取 DOM 摘要，也没有调用 `verify_copy_integrity`。

实际复现中，把 HTML 摘要替换成任意新文案，只要标题和 URL 不变，校验仍返回空错误。也就是说，当前实现只能“记录溯源”，不能“强制溯源”。这直接破坏了“Radar 不经 Agent 改写、每个公开字符可证明来自冻结字段”的核心验收标准。

建议：

1. 发布校验读取 `issue/radar-direct.json`，逐条执行 hash/span 验证；
2. 从最终 DOM 提取每条 Radar 摘要，计算 hash，与 manifest 和 `radar-direct.json` 同时比对；
3. direct-copy 模式下，缺失 provenance 文件、缺失条目或条目数量不一致必须 fail closed；
4. 标题也加入 source field/hash 或明确的连续 span 校验，不能只校验摘要。

### P1-2 新鲜度基准取系统当前时间，同一冻结 run 不幂等

相关代码：`briefing_skill/radar_direct.py:225-240`、`293-359`

`_candidate_from_row` 直接调用 `published_age_days(row.published_at)`，没有传入 active run 的 `date_to`；`normalized_radar_candidates` 虽然收到 `issue_data`，却没有使用报告日期。

结果是：同一个 run、同一份 freeze、同一规则版本，今天 render 可能保留一条 6 天前的内容，几天后 resume/render 就会把它作为超过 7 天的内容删除。该行为违反：

- active run 作用域与幂等要求；
- “同一冻结输入和同一规则版本产生相同结果”；
- 报告日期必须来自 active run 和配置时区的仓库规则。

建议：从 active issue 的 `date_to`（按配置时区解释）构造唯一 freshness reference，并把它显式传入候选规范化和 `published_age_days`。缺失或非法报告日期应明确报错，不能回退到墙上时钟。

### P1-3 AI 日报日期被当成原始发布日期公开

相关代码：

- `briefing_skill/adapters/aihot.py:158-190`
- `briefing_skill/adapters/aihot.py:299-347`
- `tests/test_aihot_adapter_lanes.py:175-178`

日报条目没有 `publishedAt` 时，代码执行：

```python
entry.setdefault("publishedAt", daily_date)
```

之后该值进入 `raw_items.published_at`，参与 7 天新鲜度筛选，并在邮件 Radar 卡片中作为日期显示。测试还把这个错误行为固定成了断言。

日报日期只证明“在哪一期日报被发现/编排”，不证明外部原始网页何时发布。仓库规则明确禁止用发现时间或抓取时间冒充原始发布日期。

建议：

- 保留 `aihot_daily_date`、日报窗口和真实 `discovered_at`；
- 只有上游单条 item 明确给出原始发布日期时才填 `published_at`；
- 对缺失原始发布日期的日报条目，选择一种显式策略：先解析原始页补齐；或内部用日报窗口做召回边界但公开日期显示“未知”；或直接不进入要求发布日期的公开 Radar。不能静默伪造日期。

### P1-4 未核验 Radar 可直接支撑 Roadmap stage

相关代码：`briefing_skill/knowledge_materialization.py:340-395`

新代码把已发布 Radar 标记成 `evidence_kind=discovery_signal`、`claim_strength=unverified`，Idea 校验也正确拒绝这类证据。但 Roadmap 校验在 promoted cluster 命中目标 branch 后，会把 Frontier Radar 加入该 branch 的通用 `allowed` 集合；同一个集合同时用于 `evidence_timeline` 和 stage 的 `evidence_for/evidence_against`。

主审复现证明：把未核验 Radar 直接放入 stage 的 `evidence_for`，校验返回 `[]`。这与设计“可进入临时方向聚类/时间线，但不能用于 Roadmap 阶段结论”不一致。

建议把证据权限拆开：

- promoted Radar 可以进入精确目标 branch 的 `evidence_timeline`，并继续标记 unverified；
- stage 的 `evidence_for/evidence_against` 只允许通过原始来源事实流程晋升后的已核验证据；
- 增加正反测试，证明 timeline 可用、stage 必须拒绝。

### P1-5 story/item 身份没有进入跨期历史，同一事件可以换报道后重复发布

相关代码：

- `briefing_skill/radar_direct.py:293-320`
- `briefing_skill/publication_history.py:213-235`
- `briefing_skill/db.py:194-213`

本期内去重会使用 `story_id` 和 `upstream_item_id`，但跨期只读取 `radar_history(canonical_url, normalized_title)`；run-scoped ledger 的 story/item 身份没有投影到发布历史。因此，上一期已发的 story 换一篇原始报道、URL 和标题后，会在下一 run 再次成为合法候选。

标题历史还存在规范化不一致：发送历史使用 `normalize_text()`，候选侧先用 `_normalise_title()` 删除空格，再调用 `normalize_text()`。英文标题只改变空格或换 URL 时，也可能绕过历史标题去重。

建议在发布历史中持久化 story ID、upstream item ID 和可用的稳定事件身份；跨期依次检查这些身份、URL、统一规范化后的标题。增加连续两个 run、同 story 不同报道的回归测试。

### P1-6 历史归档 `apply-rewrite` 绕过公开上游痕迹扫描

相关代码：

- `briefing_skill/archive_reader.py:616-639`
- `scripts/archive_sent_issue.py:237-252`

新归档入口 `archive_issue()` 在写完后执行了负向扫描，但历史重写入口直接调用 `apply_historical_rewrite()` 并重建 index，没有扫描。Reader 重写可以修改 Radar 文案；现有 Reader 校验主要限制事实、数字和身份，并不禁止写入“AI HOT”或上游域名。因此 `reader.json`、两份 HTML 和 Pages 数据可以通过官方重写命令重新暴露上游。

建议所有公开归档写入口共享同一个负向扫描和 fail-closed 契约。更稳妥的实现是在临时目录渲染、校验、扫描全部通过后，再原子替换正式归档目录。

### P1-7 `reason` 会被当作公开摘要，违反“推荐理由仅内部使用”

相关代码：

- `briefing_skill/adapters/aihot.py:299-347`
- `briefing_skill/radar_direct.py:178-187`

连接器使用 `summary or description or reason` 生成 `CollectedItem.summary`，而 `_summary_source_field` 还明确允许返回 `reason`。selected/all 条目如果只有推荐理由、没有单条摘要，就会把 AI Hot 的编辑判断包装成原始网页摘要公开。

设计文档明确规定 `reason` 默认不公开，只能作为内部排序特征。建议公开候选只接受批准的单条 `summary`/`description` 字段，保留 `reason` 在 ledger 内部；最终发布门还应显式拒绝 `source_field=reason`。

## 四、应修复的问题

### P2-1 多 lane 合并先丢文案，无法执行“尝试同 item 其他栏目摘要”

相关代码：`briefing_skill/adapters/aihot.py:426-451`

同一 URL/item 在 selected、daily、all、paper 中出现时，`_deduplicate` 只保留 priority 更高的一个 `CollectedItem`，其他版本只留下 lane 名，不保留 title/summary 备选。all/paper 又会因为 topic boost 获得更高 priority。

因此，若 selected 有完整中文摘要，而 all 返回英文摘要或不完整摘要，合并后会只保留 all 版本；后续 `select_public_summary` 发现不可用并淘汰整条内容，无法按设计回退到 selected 的中文摘要。

建议在合并时保留按 lane/source_field/hash 标识的 `copy_variants`，在直出规范化阶段先验证中文、完整句和 URL 绑定，再按明确顺序选择可用版本。测试至少覆盖“高优先级英文 + 低优先级中文”和“高优先级残句 + 低优先级完整句”。

### P2-2 freeze 不是完整的 lane 计划，配置变化后同一 run 会重新联网且不落盘

相关代码：

- `briefing_skill/adapters/aihot.py:239-245`
- `briefing_skill/adapters/aihot.py:352-376`

加载合法 freeze 后，只有 freeze 中存在的 lane 会回放；如果同一 connector version 下配置新增/改变 query lane，缺失 lane 会实时请求上游。由于 `_frozen_lanes is not None`，`_write_freeze` 又直接返回，新请求结果不会写回 freeze。之后每次 resume 都会再次联网，结果可以持续漂移。

建议让 freeze 同时绑定 connector version、影响 lane 计划的配置 hash 和完整 lane key 列表。有效 freeze 一旦加载，就不能补抓缺失 lane；需要变更输入时，应明确使旧 freeze 整体失效并原子生成新版本，而不是部分回放、部分联网。

### P2-3 selection hash 没有绑定冻结输入、规则版本和公开字段

相关代码：`briefing_skill/radar_direct.py:485-525`

当前 `selection_hash` 只包含 `run_id + URL 列表`。虽然同一 JSON 中另外保存了 freeze hash 和版本号，但它们没有进入 selection hash；标题、摘要、分类、日期等公开字段也没有进入。上游摘要变化但 URL 不变时，selection hash 完全不变。

这不满足设计 7.4 “至少绑定冻结输入 hash、taxonomy 版本、选择规则版本和公开字段 hash”。建议对规范化、稳定序列化后的以下对象统一 hash：freeze hash、connector/direct-copy/taxonomy/selection 版本、报告日期、最终条目的 radar_id/category/title hash/summary hash/original URL/published_at。

### P2-4 标题会按字符硬截断，且没有标题 provenance

相关代码：`briefing_skill/radar_direct.py:89-91`、`241-285`

标题超过 160 字时直接 `text[:160]`。这可能截断括号、版本号或语义结构；同时当前 `copy_provenance` 只记录摘要，无法证明公开标题来自哪个冻结字段。manifest 也只保存标题明文，没有标题 hash。

建议不要对标题做无标记的字符硬截断：超长标题应使用完整冻结标题、按明确完整结构规则选择可验证子串，或淘汰。无论采用哪种策略，都要记录标题 source field/hash/span，并在发布门校验。

### P2-5 一个可选 lane 失败会清空此前成功的全部 AI Hot 结果

相关代码：

- `briefing_skill/adapters/aihot.py:84-154`
- `briefing_skill/collection.py:68-84`

`AIHotCollector.collect()` 顺序请求多个 lane，但只在全部结束后返回、写 ledger 和 freeze。selected/all 已成功后，如果 daily 或 hot 抛错，整个 collector 抛出；外层把该 collector 的结果替换为 `items=[]`。一个只用于补充或加权的接口失败，就会让本期所有已成功的 AI Hot Radar 静默归零。

建议采用 lane 级错误隔离，并把成功响应和错误状态一并冻结。hot/daily 失败不应丢弃 selected/all；只有所有必要 lane 均失败时才报告 provider 级失败。测试应覆盖每个新增 lane 单独 429/503 的情况。

### P2-6 `direct_copy=false` 回退开关与当前 Prompt 契约矛盾

相关代码：

- `prompts/issue-synthesis.md:1-60`
- `briefing_skill/radar_signal_synthesis.py:306-332`

关闭 direct-copy 时，代码会重新向 `issue_synthesis` 注入 `radar_candidates`，并设置 `radar_signals_required=True`；但当前 Prompt 无条件声明任务不得读取或写入 `radar_signals`。因此文档所说的 rollback 开关并不能可靠回退，旧 pending task 也可能进入 INVALID。

建议为 legacy fallback 使用独立版本化 Prompt，或让任务输入显式携带模式并生成一致的条件化契约；补一个真实 `TaskService` 集成测试，而不是只测试 `direct_copy_groups()` 返回 `None`。

### P2-7 公开 original URL 缺少绝对、可解析、非上游域名校验

相关代码：

- `briefing_skill/adapters/aihot.py:299-313`
- `briefing_skill/radar_direct.py:234-241`

连接器允许没有 original、只有 AI Hot URL 的观察项；direct selector 又可回退到 `canonical_url`，但没有统一要求公开 URL 是 `http/https` 绝对地址且 host 不是上游域名。结果可能是上游链接拖到最终痕迹扫描才失败，也可能把相对 URL 作为邮件 href。

建议内部 ledger 可以保存不完整观察，但进入公开候选前必须使用统一的 resolved-source 校验：绝对 `http/https`、具体页面、非 AI Hot 域名；不合格条目只能留在内部。

### P2-8 ledger 丢失具体命中方式和稳定抓取身份

相关代码：

- `briefing_skill/adapters/aihot.py:109-145`
- `briefing_skill/adapters/aihot.py:378-416`

多个 query lane 在 ledger 中都被压成粗粒度 `all`/`paper`，相同 item 会覆盖，实际 query、topic、direction 和完整 lane key 丢失；`etag` 固定为 `None`；冻结回放时 `retrieved_at` 又会更新成 resume 当天。这不足以回答“哪次请求、哪个方向、哪份冻结响应产生了这条公开 copy”。

建议 ledger 保存完整 lane key、query/topic/direction、freeze 文件 hash/响应引用、原始 retrieved_at 和 ETag；resume 只更新本次 replay 记录，不覆盖原始抓取身份。

## 六、非阻塞观察

1. 公开痕迹扫描中的 `discovery_source` 正则实际只匹配字段名，不检查值是否为 AI Hot，可能误杀其他合法 discovery source：`briefing_skill/public_trace_scan.py:19-26`。
2. 公开痕迹扫描覆盖 run 和新 archive 数据；Pages 当前直接读取 archive，因此主要数据路径能受益。但设计中的“Pages DOM/数据文件负向检查”没有独立构建期验证，建议在 Pages CI 增加一次对最终发布树的扫描。
3. 新归档扫描发生在目标目录写入之后。扫描失败会退出，但已写入的公开目录会留在工作区；更稳妥的做法是在临时目录组装和扫描通过后再原子替换目标。

## 七、建议修复顺序

1. 先修 P1-1、P1-2、P1-3，保证发布内容和日期可信、同一 run 可复现；
2. 修 P1-4、P1-5，封住长期知识污染和跨期重复路径；
3. 修 P1-6、P1-7，确保所有公开写入口和公开字段遵守隐形上游契约；
4. 修跨 lane copy variants、lane 级降级和完整 freeze 绑定；
5. 完成 selection/title provenance、历史事件身份和 resolved original URL 校验；
6. 修复或移除名义上的 `direct_copy=false` 回退开关；
7. 补 shadow run：至少对同一期冻结输入记录旧/新 Radar 的数量、重复率、分类覆盖、正文来源完整性和公开痕迹扫描结果；
8. 修复后重跑全量测试，并把主审和交叉审查的失败复现加入永久回归测试。

## 八、最终判断

这版实现的方向是对的，而且比原流程更接近“AI Hot 做不可见的编辑上游，本系统做范围、选择、分类、去重和长期边界”。但当前代码对外宣称的几个强保证——“完全直出可验证”“同一冻结 run 幂等”“原始发布日期可信”“跨期不重复”“所有归档写入口零上游痕迹”“Radar 不能支撑 Roadmap 阶段结论”——尚未由代码真正强制。

建议暂不合并到默认发布路径；完成上述 P1 项并补齐对应回归后，再做一次 shadow run 和最终复审。
