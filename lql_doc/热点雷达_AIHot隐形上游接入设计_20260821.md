# 热点雷达 AI Hot 隐形上游接入设计

文档日期：2026-08-21  
状态：需求口径已确认，等待实现  
适用仓库：`technical-briefing-skill`  
关联设计：`lql_doc/技术情报系统_Roadmap_IdeaBank_Pages重构设计_20260820.md`

## 一、背景

当前热点雷达从本期全部采集来源中构造候选。AI Hot 已经是其中一个重要发现源，但现有流程只使用了 AI Hot 的“精选”和按专题关键词查询的“全部 AI 动态”，没有使用热点榜、AI 日报和事件聚合能力。候选进入本期综合任务后，还会由 Agent 再次压缩成 Radar signal 和 summary。

这条路径存在三个问题。

1. AI Hot 已经提供质量较好的中文标题和摘要，再次让模型总结会增加调用成本，也可能损失信息或重新产生明显的模型文风。
2. AI Hot 的热点榜、日报和多源事件聚合没有被充分利用，导致 Radar 的信息密度和热点覆盖不足。
3. 如果最终页面直接出现“AI Hot 精选”“AI Hot 摘要”或 AI Hot 链接，读者容易把本系统理解成一个简单的聚合转发展示，而忽略本系统在技术边界、跨源选择、去重、分类和跨期积累上的价值。

本设计把 AI Hot 定义为不可见的上游编辑和发现服务。系统可以采用它已经生成的单条标题与摘要，但最终邮件、公开归档和 GitHub Pages 只展示原始网页来源，不展示 AI Hot 品牌、链接、栏目或发现路径。

## 二、产品目标

目标流程如下。

```text
AI Hot 精选 / 全部动态 / 热点榜 / AI 日报
                    ↓
          本地冻结与内部溯源
                    ↓
     技术范围过滤、分类、排序、去重
                    ↓
       直接选择已有标题和单条摘要
                    ↓
          热点雷达公开阅读结果
                    ↓
    只显示原始网页名称与原始网页 URL
```

系统负责的价值是：

- 决定哪些信息符合本项目技术范围；
- 在多个上游栏目和其他采集来源之间统一去重；
- 按 AI Infra、Agent 生态、KVCache 生态、存储与介质和边界探索重新分类；
- 控制每期数量、类别多样性和跨期重复；
- 将 Radar 与深度条目、专题补充、Roadmap 和 Idea Bank 的证据边界分开；
- 保证运行隔离、可恢复、可审计和发布幂等。

系统不在读者页面声明 AI Hot 标题或摘要由本系统原创，也不使用“本简报独立采集”“本简报原创总结”“经本简报核验”等会造成错误归属的表达。

## 三、已确认的产品决定

### 3.1 AI Hot 不出现在最终阅读结果

以下公开产物不得显示 AI Hot 名称、域名、栏目、条目链接或 attribution：

- 当前运行的 `email.html`；
- 当前运行的 `email-illustrated.html`；
- 归档根目录公开阅读版；
- 归档中的 `reader.json`、`issue.json`、`papers.json` 和 `publication-manifest.json`；
- GitHub Pages 的日报、首页、图谱、Roadmap 和 Idea Bank 阅读界面；
- 邮件正文中的来源名称、链接标题和可见脚注。

上述约束只针对最终发布产物。源码配置、内部 SQLite、被忽略的运行目录和内部诊断输出仍需要保存真实上游身份。

### 3.2 内部必须保留真实溯源

展示层隐藏发现渠道，不等于内部删除发现渠道。系统必须在本地保存：

- `provider=aihot`；
- AI Hot item ID 或 story public ID；
- AI Hot 条目 URL；
- 原始网页 URL；
- 上游栏目和命中方式；
- 拉取时间、ETag 和响应版本；
- 被采用标题、摘要和推荐理由的 hash；
- 原始响应或可恢复的规范化快照；
- 本期最终是否采用、未采用原因和最终 Radar ID。

这些字段服务于跨栏目去重、跨期去重、内容更正、撤回同步、运行恢复和问题审计，不进入公开发布目录。

### 3.3 AI Hot 文案不再二次生成

AI Hot 候选进入 Radar 后，默认不再由 `issue_synthesis` 或其他 Agent 改写。

允许的确定性操作包括：

- 从多个现成字段中选择一个完整字段；
- 选择摘要中的一个或两个完整句子；
- 清理重复空白和明显的控制字符；
- 将来源名称替换为原始网页域名或原始站点名称；
- 按本系统 taxonomy 分类；
- 去重、排序和淘汰。

禁止的操作包括：

- 让模型重新概括同一摘要；
- 把多个不相关条目合成一个“趋势”；
- 添加上游摘要中没有的因果关系、数字或判断；
- 把 AI Hot 的推荐理由改写成“我们的判断”；
- 将多源事件 digest 伪装成某一个原始网页的摘要。

### 3.4 最终只展示原始网页来源

每条公开 Radar 卡片至少包含：

- 公开标题；
- 一段现成的中文摘要；
- 本系统 Radar 分类；
- 原始发布日期；
- 原始网页站点名称；
- `links.original` 指向的绝对 URL。

不显示 `links.aihot`，也不把 AI Hot 的 source name 当作公开来源名称。

### 3.5 Radar 仍然是未经深度核验的快速信号

隐藏上游不改变证据等级。通过这条路径生成的条目统一标记为内部 `discovery_signal`，公开页面继续保留 Radar 区域的总体免责声明。

这些条目不能直接支撑：

- 本期判断；
- 项目结论；
- Roadmap 阶段、转折或收敛判断；
- Idea 的支持、反对或淘汰结论；
- 已经完成验证的结论。

Radar 可以作为 `frontier_exploration` 的弱信号形成临时 cluster，但只能证明“该信号曾被发布并值得观察”，不能证明摘要中的技术事实已经核验。

## 四、当前实现与目标实现的差异

| 能力 | 当前实现 | 目标实现 |
|---|---|---|
| AI Hot 精选 | 拉取最近 24 小时最多 50 条 | 保留，成为主要直出候选池 |
| 全部 AI 动态 | 按每个 Direction 的关键词查询最近 7 天 | 保留，降为专题补漏和候补池 |
| 热点榜 | 未接入 | 接入，只用于热点权重、排序和事件身份 |
| AI 日报 | 未接入 | 接入，用结构化日报条目补充遗漏 |
| AI Hot 主题 | 未直接接入 | 当前通过公开 API 的 `q/category` 映射，不抓取网页 UI |
| 热点 story digest | 未接入 | 可作内部判断上下文，不在无 AI Hot 署名的页面直接发布 |
| Radar 写作 | Agent 将候选重新总结成 signal | 直接采用上游单条标题和摘要，不调用 Agent |
| 最终来源 | 只显示原始网页 | 保持不变 |
| 内部溯源 | raw payload 中部分保留 | 增加明确的上游 ledger 和内容 hash |
| 公开 AI Hot 痕迹 | 当前渲染器已经主动排除 | 扩大到全部公开 JSON、HTML 和 Pages 数据 |

## 五、AI Hot 接口与栏目接入策略

本设计基于 2026-08-21 可用的 AI Hot Public API v1。实现时只依赖官方公开、匿名、只读接口，不抓取网页 DOM 作为生产数据源。

### 5.1 精选

接口：

```text
GET /api/v1/items?mode=selected&window=24h&by=timeline&limit=50
```

用途：主要 Radar 候选池。

采用字段：

- `id`；
- `title`；
- `summary`；
- `reason`，只在内部排序时使用，默认不作为公开文案；
- `category`；
- `score`，只作为弱排序特征；
- `publishedAt`；
- `discoveredAt`；
- `links.original`；
- `links.aihot`，仅内部保存。

精选身份不能替代本系统技术范围判断。融资、股价、政治政策、消费应用等即使进入 AI Hot 精选，仍按本系统 Radar 排除规则处理。

### 5.2 全部 AI 动态

接口：

```text
GET /api/v1/items?mode=all&window=7d&by=timeline&q=<query>&limit=<limit>
```

用途：对指定技术方向补漏，不作为无差别全量输入。

查询继续来自版本化配置，不在 Prompt 或运行时临时发明。重点覆盖：

- Agent、agentic、harness、coding harness；
- LLM serving、inference runtime、compiler、kernel；
- KV cache、prefix cache、remote prefill、Agent memory；
- GPU/NPU/ASIC、HBM/HBF、Chiplet、互联；
- CXL、NVMe、NAND、QLC/TLC、ZNS 和计算存储；
- AI 集群、集合通信、可观测性和故障恢复。

全部动态噪声较大，排序优先级低于热点榜、精选和日报。

### 5.3 热点榜

接口：

```text
GET /api/v1/hot-topics
```

用途：提供当前热点事件的 rank、多源覆盖强度和 story 身份。

热点榜本身通常只提供标题、rank、原始链接和 story 链接，不提供适合直接展示的完整单条摘要。处理流程如下。

```text
hot topic
    ↓ 提取 AI Hot item ID / original URL
在本期 selected/all/daily 冻结结果中寻找同一 item
    ↓
找到带 links.original 的单条 summary
    ↓
只给该单条候选增加热点权重
```

如果无法找到与 `links.original` 明确绑定的单条摘要，该热点只参与内部覆盖统计，不直接生成公开 Radar 卡片。

### 5.4 热点事件 story

接口：

```text
GET /api/v1/stories/{publicId}
```

story 中的 `digest` 由多个报道聚合形成，可能包含更新、冲突和多来源数字。由于最终页面不显示 AI Hot，不能把这段多源 digest 绑定到某一个原始网页并作为该网页的摘要展示。

允许用途：

- 内部判断多个 item 是否属于同一事件；
- 构造稳定 story 去重身份；
- 判断事件是否仍在更新；
- 在多个原始报道之间选择一条更合适的单条 item；
- 记录热点强度和多源覆盖。

禁止用途：

- 将完整 digest 直接放进公开 Radar；
- 将 digest 中的数字归因到 `hot-topics.links.original`；
- 用 digest 支撑 Roadmap 或 Idea 结论。

### 5.5 AI 日报

接口：

```text
GET /api/v1/dailies/latest
GET /api/v1/dailies/{date}
```

用途：使用 AI Hot 已完成的日报编排发现精选和关键词查询遗漏的条目。

日报条目只有同时具备以下字段才可进入候选池：

- 非空 `title`；
- 非空 `summary`；
- 非空 `links.original`；
- 明确的日报日期和窗口；
- 满足本系统技术范围和时间窗。

日报 section label 可以作为内部分类辅助，不能直接替代本系统 Radar taxonomy。

### 5.6 主题

当前公开 OpenAPI 没有独立的主题列表或主题详情 endpoint。第一阶段不抓取 `/topics` 网页，不依赖可能变化的页面结构。

第一阶段使用两种替代方式：

1. 将本系统 Direction 关键词映射到 `/api/v1/items?q=...`；
2. 使用公开 `category` 参数做粗分类召回。

未来 AI Hot 如果提供稳定主题 API，再作为新的版本化 source lane 接入。

## 七、运行隔离、缓存与幂等

### 7.1 每个运行必须冻结自己的输入

AI Hot 的热点榜和 story digest 会持续变化。同一 run 一旦完成采集，后续 resume、advance、render 和 archive 必须只读取该 run 已冻结的响应，不得在渲染阶段重新请求 AI Hot。

否则同一个 run 可能在两次渲染之间改变标题、摘要、热点身份或数量，破坏任务绑定和发布幂等。

### 7.2 304 不能等同于本期没有内容

ETag 返回 `304 Not Modified` 只表示远端响应与缓存一致，不表示当前 run 没有候选。

正确流程是：

```text
请求返回 200
  → 更新跨运行 HTTP 响应缓存
  → 将规范化结果物化到当前 run

请求返回 304
  → 读取对应的已验证响应缓存
  → 仍将规范化结果物化到当前 run
```

禁止在新 run 中因为 304 直接返回空列表。否则会造成跨运行静默丢失 Radar 内容。

### 7.3 active run 作用域

- `raw_items`、规范化候选、选择结果和发布对象必须带当前 `run_id`；
- 跨期只能显式读取 `radar_history`、HTTP 响应缓存和内部 upstream ledger；
- 上一期候选不能因为本期 API 失败而自动复制进本期；
- resume 重复执行不得重复插入同一候选或重新应用不同文案；
- 同一冻结输入和同一规则版本必须产生相同 Radar 结果。

### 7.4 版本绑定

建议引入：

- `aihot_connector_version`；
- `radar_direct_copy_version`；
- `radar_taxonomy_version`；
- `radar_selection_policy_version`。

最终选择 hash 至少绑定冻结输入 hash、taxonomy 版本、选择规则版本和公开字段 hash。

## 八、候选合并与去重

### 8.1 同一期多栏目合并

同一条内容可能同时出现在热点榜、精选、日报和关键词查询中。合并身份按以下顺序使用：

1. AI Hot story public ID；
2. AI Hot item ID；
3. 规范化原始 URL；
4. DOI、arXiv ID、GitHub repository/release 等稳定身份；
5. 规范化标题。

合并后只产生一个候选，内部保留全部 `upstream_lanes`。栏目越多不增加公开条目数量，只提高内部优先级。

### 8.2 与其他采集源合并

如果 arXiv、GitHub、RSS 或 Builder lane 已经采集到同一个原始 URL：

- 只保留一个 Radar 候选；
- 原始来源身份优先；
- AI Hot 可以提供 reader copy，但内部必须记录该 copy 的真实来源；
- 如果该 URL 已进入深度条目或专题补充，Radar 必须删除；
- 同一 GitHub 项目的普通 release 不得在深度、补充和 Radar 中重复占位。

### 8.3 跨期去重

继续按规范化原始 URL 和规范化标题使用 `radar_history`。新增 story identity 后，同一事件的多个报道还应按 story ID 去重。

旧事件只有出现明确增量时才允许重新发布。增量判断不能只依据 AI Hot 改写了标题或摘要。

## 九、技术范围、分类和排序

### 9.1 允许范围

- AI Infra；
- Agent 生态；
- KVCache 生态；
- 存储与介质；
- AI 芯片、内存和互联；
- 编译器、Kernel、运行时和分布式系统；
- 可以扩大未来三个月技术假设空间的边界探索。

### 9.2 排除范围

- 融资、财报、股价和并购本身；
- 高管言论和缺少技术内容的战略表态；
- 政治政策、版权诉讼和社会争议；
- 游戏娱乐和普通消费应用；
- 只有模型榜单名次、没有机制或部署信息的模型新闻；
- 只有产品营销描述、没有技术变化的发布；
- 与当前 Radar 技术范围无关的教育、办公和内容创作信息。

### 9.3 分类

继续使用本系统 taxonomy，不直接使用 AI Hot 的产品栏目。分类优先级如下：

1. 存储与介质；
2. KVCache 生态；
3. Agent 生态；
4. AI Infra；
5. 边界探索；
6. 其他技术前沿。

`agent`、`agentic`、`harness`、`agent harness`、`coding harness`、`agentic coding`、`agentic workflow` 和 `agentic system` 必须继续纳入 Agent 语义召回；泛业务意义的 agentic 仍应被深度通道排除。

### 9.4 内部排序

建议采用确定性排序，不调用 Agent。

```text
hot topic 且能解析到单条摘要          +40
selected                              +30
daily                                 +20
命中配置中的高优先级技术 Direction     +0～20
拥有 A 级 original URL                +10
多个栏目同时出现                       +5
最近 24 小时                           +5
只有 all/query                         +0
命中排除范围                           直接淘汰
```

AI Hot score 只作为同条件候选的弱排序特征，不能替代本系统技术价值判断，也不能成为公开重要度。

### 9.5 数量与多样性

- 最终最多 8 条；
- 每个 Radar 分类最多 2 条；
- 同一项目或同一 story 最多 1 条；
- 候选充足时优先覆盖不同类别；
- 不为满足最低数量引入范围外信息；
- 合法候选不足时允许少于 5 条，并明确记录 underfill 原因。

现有“候选达到 8 条时至少保留 5 条、4～7 条时至少保留 3 条”的发布门可以保留，但 `raw_eligible` 必须只统计通过技术范围、中文完整性、来源 URL、跨期去重和深度去重后的合法候选。

## 十、直出文案规则

### 10.1 字段选择

公开标题优先使用 AI Hot 单条 item 或日报条目的 `title`。

公开摘要按以下顺序选择：

1. 长度合适、语义完整的单条 `summary`；
2. `summary` 中不超过公开上限的一到两个完整句子；
3. 其他栏目中同一 item 的完整 `summary`；
4. 没有合适摘要则放弃该候选。

默认不公开 `reason`。`reason` 是 AI Hot 的编辑判断，不是原始网页事实。如果未来确实需要使用，只能作为内部排序特征，或者在重新获得允许显示上游来源的产品模式中单独展示。

### 10.2 不做生成式改写

直出 Radar 不创建 `item_writing`、`reader_projection` 或专门的 Radar 写作任务。确定性处理必须能够证明最终文本是某个冻结上游字段的完整值或连续完整句子子串。

建议保存：

- `source_field`；
- `source_text_hash`；
- `selected_span_start/end`；
- `public_text_hash`。

测试可以据此验证发布文字没有新增字符级事实内容。

### 10.3 标点与长度

- 摘要必须包含完整中文句子；
- 不允许以省略号、逗号、冒号或分号悬空结束；
- 不允许按字符硬截断；
- 如果完整摘要过长，只能选择完整句子；
- 没有可用完整句子时淘汰，不调用模型补写。

## 十一、任务图和发布流程调整

### 11.1 从 issue synthesis 中移除 Radar 写作责任

`issue_synthesis` 继续负责：

- 本期判断；
- watch next；
- project insights；
- topic names。

它不再读取 `radar_candidates`，也不再生成最终 `radar_signals`。这样可以避免同一个模型调用把已完成的上游摘要重新写一遍。

### 11.2 新增确定性 Radar finalize 阶段

建议流程：

```text
collect
  ↓
freeze AI Hot responses in active run
  ↓
normalize and merge Radar candidates
  ↓
deep / appendix selection completes
  ↓
deterministic Radar selection and direct copy
  ↓
persist issue_radar_items + synthesis.radar_signals
  ↓
render / validate / send / archive
```

为了兼容现有 `issue.json`、归档和 Pages，最终确定性对象仍可写入 `synthesis.radar_signals`，但写入者不再是 Agent。写入操作必须 hash 绑定并保持幂等。

### 11.3 发布时最终去重

Radar finalize 必须发生在深度条目和专题补充已经确定之后，确保能够删除：

- 与深度条目相同的原始 URL；
- 与专题补充相同的原始 URL；
- 同一 GitHub 项目重复 release；
- 同一 story 的多个原始报道；
- 历史已发布且无增量的事件。

## 十二、邮件、归档和 GitHub Pages 展示

### 12.1 邮件

Radar 继续使用分栏卡片，每张卡片展示标题、摘要、日期和原始网页链接。区域级免责声明继续说明该区域为快速信号、未经本简报深度核验。

不得显示：

- AI Hot Logo；
- “AI Hot 精选”“AI Hot 热点榜”“AI Hot 日报”；
- AI Hot 域名；
- “推荐理由”标签；
- 发现源调试字段。

### 12.2 归档

公开归档只保存公开 Radar 对象。内部 upstream ledger 不复制进 `archive/issues/<date>/`。

`publication-manifest.json` 仍记录 Radar ID、分类、标题、原始 URL 和公开内容 hash，用于 HTML provenance 校验，但不记录 AI Hot URL 或 provider 名称。

### 12.3 GitHub Pages

Pages 只读取归档中的公开对象，不直接调用 AI Hot API，也不在浏览器端拼接 AI Hot 数据。

这样可以保证：

- Pages 构建可复现；
- 已发布一期不会随 AI Hot 后续改写而变化；
- 浏览器不会暴露上游 API 请求；
- Roadmap 和 Idea Bank 不会意外读取内部 provider 字段；
- GitHub Pages 与邮件内容一致。

### 12.4 公开痕迹校验

发布门增加负向扫描。对公开 HTML 和 JSON 检查：

```text
AI HOT
AIHOT
aihot.virxact.com
links.aihot
upstream_provider
discovery_source=AI HOT
```

源码、配置和测试 fixture 不属于扫描目标。扫描范围只覆盖本期发布目录、归档公开目录和 Pages 数据产物。

## 十三、Roadmap、Idea Bank 与边界探索

### 13.1 不作为已核验 Machine Evidence

AI Hot 直出摘要不能直接进入深度 Machine Item，也不能替代原始全文、Evidence Pack 或 facts。

### 13.2 已发布 Radar 的长期身份

已发布 Radar 可以继续进入 `frontier_exploration`，但需要增加或保留以下语义：

```json
{
  "role": "radar",
  "topic_id": "frontier_exploration",
  "evidence_kind": "discovery_signal",
  "claim_strength": "unverified",
  "source_urls": ["https://original.example/article"]
}
```

知识层只能使用它做：

- 临时方向聚类；
- 信号出现次数和跨期持续性；
- 后续需要回到原始来源验证的线索；
- Idea seed 的候选触发器。

知识层不能使用它做：

- Roadmap 阶段结论；
- 技术性能结论；
- Idea 支持或反对证据；
- 自动淘汰 Idea 的证据。

如果某条 Radar 后续需要晋升为强证据，必须从原始 URL 重新进入 A 级来源解析、Evidence Pack、事实抽取和必要的事实检查流程。

## 十四、失败与降级

### 14.1 AI Hot API 失败

- 保留 arXiv、GitHub、RSS、Builder 和其他当前 run 来源；
- Radar 可以减少，不能复制上一期内容填充；
- 保存明确错误、HTTP 状态和 Retry-After；
- 不影响深度正文生成；
- 不在渲染阶段再次联网补救。

### 14.2 热点榜成功但条目摘要无法解析

- 只记录内部热点命中；
- 不发布空摘要卡片；
- 不使用 story digest 冒充单一原始来源摘要；
- 允许由精选、日报或 all 查询中的同一 item 补齐。

### 14.3 上游摘要为英文或不完整

- 不调用模型翻译或补写；
- 尝试同一 item 在其他 AI Hot 栏目的中文摘要；
- 仍不可用则淘汰；
- 其他来源的中文候选可以正常补位。

### 14.4 上游更正或撤回

当前 run 尚未发布时，可以在重新 collect 后产生新的冻结版本；已经发布的 archive 不静默改写。需要更正时创建明确的新归档版本或更正记录，不能无痕替换历史内容。

## 十五、使用范围与风险边界

AI Hot 当前公开规则允许个人非商业、公益非商业和组织内部使用，并说明这些允许用途不强制界面署名，但机器响应中的来源和 canonical 信息应保留。对外商业产品、公开镜像、批量公开再分发等场景可能需要书面授权。

本设计采用以下处理：

- 内部机器层保留真实 provider、canonical、AI Hot URL 和原始响应；
- 公开阅读层不显示 AI Hot；
- 公开层只展示少量经本系统重新选择和分类的技术条目，不提供 AI Hot API、批量导出或镜像能力；
- 不声称 AI Hot 文案由本系统原创；
- 不使用 AI Hot Logo 或暗示官方合作；
- 如果 GitHub Pages 的用途转为商业、客户交付、广告、赞助或持续大规模公开再分发，上线前需要重新确认授权范围。

这是一项产品和工程边界，不构成法律意见。实现时应把上游规则 URL 和规则版本保存在内部配置或运维文档中，便于后续变化检查。

## 十七、测试设计

### 17.1 连接器测试

- selected、all、hot 和 daily 正确解析；
- story ID 只从官方返回链接提取；
- 不构造不存在的 story URL；
- ETag 304 能从缓存物化到新 run；
- 429/503 遵守 Retry-After；
- 同一 run resume 不重复插入。

### 17.2 隔离与幂等测试

- run A 的候选不会进入 run B，除非 B 从显式响应缓存重新物化；
- 同一冻结输入重复 finalize 结果完全一致；
- 渲染和归档阶段不会重新访问 AI Hot；
- 上游 story 后续更新不会改变已冻结 run；
- advance 重跑不会重复写 Radar 或 history。

### 17.3 去重测试

- 同一 item 同时出现在精选、日报和热点榜时只生成一条；
- 同一 story 的多个报道最多生成一条；
- 同一原始 URL 被其他采集器采集时只生成一条；
- 深度条目和专题补充优先，Radar 自动删除重复项；
- 历史已发 URL 和标题不能重复进入。

### 17.4 文案完整性测试

- 最终摘要等于冻结字段或其连续完整句子子串；
- 不出现上游不存在的新数字；
- 不按字符硬截断；
- 不以悬空标点结束；
- 不使用 story digest 绑定单一 original URL；
- 没有可用中文完整摘要时不发布。

### 17.5 公开产物测试

- `email.html` 不包含 AI Hot 名称和域名；
- `email-illustrated.html` 不包含 AI Hot 名称和域名；
- archive 公开 JSON 不包含 AI Hot provider 和 URL；
- publication manifest 只含原始 URL；
- Pages DOM 和数据文件不包含 AI Hot 可见记录；
- 所有图片 URL 仍为稳定绝对 URL，不受 Radar 改造影响。

### 17.6 知识层测试

- Radar 仍映射到 `frontier_exploration`；
- `claim_strength=unverified` 的 Radar 不能更新 Roadmap 阶段；
- 不能直接成为 Idea 支持、反对或淘汰证据；
- 只有重新进入原始来源事实流程后才能晋升。

## 十八、验收标准

### 18.1 产品验收

- 最终热点雷达不出现任何 AI Hot 可见标识；
- 读者只看到原始网页来源；
- Radar 信息量不低于旧流程，热点榜和日报能够补充新候选；
- 不再出现一块明显的外部聚合器搬运区域；
- 页面不宣称摘要由本系统原创或深度核验。

### 18.2 内容验收

- 每条公开文案都可追溯到一个冻结的单条上游字段；
- 不使用无法绑定单一原始网页的多源 digest；
- 不增加上游不存在的数字和因果关系；
- 排除融资、政治、消费应用等非技术 Radar 内容；
- 每期最多 8 条、每类最多 2 条。

### 18.3 工程验收

- 新 run 遇到 304 不会得到空 Radar；
- active run 数据不跨 run 泄漏；
- resume、advance、render 和 archive 保持幂等；
- 发布后不依赖浏览器或 Pages 实时访问 AI Hot；
- 内部 upstream ledger 完整，公开产物无上游痕迹；
- 现有深度、专题补充、图片和邮件发送链路无回归。

### 18.4 长期知识验收

- Radar 只作为未核验边界信号；
- Roadmap 和 Idea Bank 不把直出摘要误当事实证据；
- 同一边界信号跨期出现时可以聚类；
- 需要晋升时必须回到原始来源完成现有事实流程。

## 十九、暂不实施

- 抓取 AI Hot `/topics` 网页；
- 在 GitHub Pages 前端实时调用 AI Hot；
- 公开 AI Hot 热点排名或热度值；
- 直接发布多源 story digest；
- 让 Agent 对 AI Hot 直出摘要再次润色；
- 用 AI Hot 摘要直接更新 Roadmap 或 Idea 状态；
- 建立 AI Hot 数据公开镜像、批量导出或代理接口；
- 对旧归档重新补入当时没有发布的 AI Hot 内容。

## 二十、最终口径

本次改造不是把热点雷达变成 AI Hot 专区，也不是在最终页面展示外部聚合器。AI Hot 作为不可见上游提供候选、现成中文摘要、热点身份和日报编排；本系统负责技术范围、选择、分类、去重、跨期控制和长期知识边界。

最终读者只看到本系统编排后的热点雷达和对应原始网页来源。内部保留真实上游溯源，公开页面不暴露 AI Hot，也不把未经核验的 Radar 包装成深度事实或原创研究结论。
