# 一、信息选择机制要彻底换思路：从“统一打分”变成“分赛道选拔”

现在最大的设计错误是：

**所有信息先进入一个分数体系，然后全局竞争。**

当前 `project_relevance` 权重达到 30，是最大的单项权重。 Scorer 也直接把 relevance score 转换成这 30 分。

这非常适合回答：

> “这条和我现在做的东西相关不相关？”

但不适合领导的新目标：

> “三个月后有没有可能从外面学到一个我们现在没想到的 Idea？”

### 应该改成三个 lane

**Academic Evidence**

论文、OpenReview、标准等。

关注：

机制是否新、实验是否扎实、技术边界是什么。

---

**Industry / Builder Signal**

官方技术博客、GitHub Release、工程团队博客、Simon Willison、Latent Space、SemiAnalysis 等。

关注：

工业界开始解决什么问题、工程实现发生了什么变化、哪些技术正在被采用。

这里**不应该要求必须再找一个 A-level 论文才能出现**。

它可以明确标：

> 工业观察 / Builder Insight

而不是假装它和论文拥有同一种证据等级。

---

**Frontier Exploration**

完全取消：

`project_relevance`

这个维度。

改为评价：

**新颖性 + 可迁移性 + 技术反直觉程度 + 信息增益。**

这才能真正“跳出边界”。

---

最终不是：

> Top 20 score wins

而是：

> 每个 Topic 从 Academic / Industry 中分别拿最值得看的东西；再独立选少量 Frontier Exploration。

这样才能解决“我配了 20 个源，最后为什么还是 20 篇 arXiv”。

# 二、“不限主题”不要继续叫 AI Infra 横向动态

当前已有：

> `AI Infra横向动态`

但它定义的是“与 AI 语义 Fabric 直接相关、无法归入前六个专题的基础设施进展”。

这**还是一个受限主题**。

我建议明确新增：

### 边界探索 · EXPLORE

它不回答：

> 和 TPN / DPU / Agent / 跨域有什么关系？

而是回答：

> **这个技术有什么反直觉、可迁移或者可能打开新方向的地方？**

例如今天可能出现：

- 数据库的新并发控制思想；
- HPC 新通信机制；
- 操作系统调度；
- 新型存储介质；
- 编译器/runtime；
- 网络测量；
- 新的 memory hierarchy；
- 芯片封装；
- 甚至一些非 AI 系统工作。

关键不是“直接相关”，而是：

> **这里有没有一个 mechanism 可以移植回来？**

这才符合领导说的“扩展视野”。

> 有什么东西？

Roadmap回答：

> **这个方向是怎么一步一步走到今天的？**

而对三个月后的立项，后者明显重要得多。

### Roadmap 不应该只是时间轴

- 2026-07-xx 日报

- GitHub Release B
- Company Blog C

# 五、反馈模块应该砍掉 80%

当前 review 页本质上是一个**编辑器 + 审批系统**：每条有接受 checkbox，还有多个字段的 textarea。

这个可以保留，但应该叫：

> 高级审核

真正的 Feedback 就两个东西：

**♡ 有启发**

**× 没启发**

最多再加一个很轻的小入口：

> `为什么？`  
> 不相关 / 已知 / 太浅 / 看不懂

但默认不要显示。

而且反馈的学习不要简单做成：

> 喜欢 TPN → TPN +10 分

更应该学习：

> 用户喜欢哪种 mechanism、哪种来源、哪种信息粒度。

比如你可能不是喜欢“Agent”这个 Topic，而是喜欢：

> 有具体架构 + 有工程数据 + 能直接形成实验假设

这个比 topic preference 有价值。

# 六、中文表达我建议直接换 Reader Schema

机器内部继续保留：

`mechanism / result / boundary / relevance`

因为 Roadmap、Idea 和 fact check 都需要。

**但是不要直接拿这些字段拼邮件。**

Reader-facing 改成：

### 一句话看懂

> LMCache 新版本把 KVCache 的跨节点传输从应用层拷贝改成了 XXX，主要解决 XXX。

### 它具体做了什么

正常两三句话讲清楚机制。

### 为什么我觉得值得看

> 这个工作的价值不在 XXX，而在于它说明 XXX 已经成为独立调度对象。对我们的启发是……

没有 benchmark 就不要强行放“实验结果”。

没有明确 boundary 就不要强行写“边界”。

没有项目关系也不要强行写“项目相关性”。

**现在的 AI 味很大一部分，就是模型在被迫把每条消息填满固定槽位。**

另外我会增加一个非常简单的生成后检查：

> **“一个不了解这篇论文的系统同事，看完第一段能否用一句话回答：它到底做了什么？”**

回答不了，就自动重写。

这比再加 30 条“禁止使用某某词语”的 prompt 有效得多。

# 七、自动仿真不要一上来做“万能 Agent 仿真”

这很容易把项目做炸。

你的技术主题其实很适合先建立几个**确定性的实验模板**：

| Template | 典型 Idea |
|---|---|
| Cache | KVCache 命中、容量、淘汰、复用 |
| WAN Transfer | RTT、带宽、压缩、冗余、重传 |
| Queue/Scheduling | Prefill/Decode、调度、排队 |
| Offload | DPU 覆盖率、吞吐、CPU offload |
| Fabric | 拓扑、链路、流量分布 |

然后流程：

```text
日报 Insight
   ↓
Idea Seed
   ↓
Hypothesis
   ↓
自动判断可否映射 Simulation Template
   ↓
生成 experiment.json
   ↓
Python runner
   ↓
plots + metrics
   ↓
与 success criteria 比较
   ↓
Promising / Uncertain / Reject
```

例如：

> “跨域 KVCache 加 EC 冗余是否比丢包后重传更划算？”

Agent 不需要自己写一个大型 simulator。

只需要生成：

```text
WAN RTT = 20~100 ms
loss = 0~2%
bandwidth = 100 Gbps
redundancy = 0~30%
object size = ...
```

已有的 WAN Transfer simulator 自动扫参。

最后自动说：

> 当 RTT > X、loss > Y 时该方案开始有收益；低 RTT 场景不值得。

这就是非常像“技术立项前筛 Idea”的系统了。

# 还有一种更隐蔽的 AI 味：过度压缩

比如：

> “静态ECMP哈希在结构化LLM流量下最坏无界不均衡;ZCube不含Braess子图,可证对任意流量矩阵均衡,AllReduce与KV传输均衡是推论。” `53aef9b0-8316-4c4b-a07f-8eb06f33dd30.html`

这不是普通的“文风不好”。

这是**为了塞进固定字数，把三个完整逻辑压成一个 telegram**。

正常写法应该是：

> **论文认为问题出在 ECMP：LLM 训练和推理的流量高度结构化，哈希后可能长期集中到少数路径。ZCube 干脆减少路径，并证明其拓扑中不存在会导致这种反常拥塞的 Braess 子图。因此，即使路径数量变少，AllReduce 和 KV 传输反而更容易获得稳定的负载均衡。**

字多了一点。

但读者读一次就懂。

**日报的目标不是压缩比最大化，而是单位阅读时间获得的信息最大化。**

这两个目标差别很大。

# 我现在会把“AI 味”的来源拆成 6 层

| 层次 | 当前现象 | 严重性 |
|---|---|---|
| 标题 | 项目名 + 让/把/靠/用 + 技术名词 | 很高 |
| 句法 | 逗号、分号串联大量逻辑关系 | 很高 |
| 词汇 | 资产、原语、边界判断、验收项、结构性解释 | 很高 |
| Schema | 每条都必须机制/证据/边界/启发 | **根因** |
| 项目关联 | 强迫每篇文章找一个“对项目的价值” | **根因** |
| 综合判断 | 强迫几篇文章抽象成“大趋势” | 高 |

所以我会修正我刚才的一点判断：

**Reader Schema 不只是需要优化，而是应该直接推翻重做。**

# 我现在更倾向于这样的正文格式

对于详细条目，不再固定：

> 摘要  
> 机制  
> 证据  
> 边界  
> 启发

而是：

### `CommitKV：工具任务结束后，哪些 KV 可以真的删掉？`

**它解决什么问题**

多轮 Agent 会不断积累 KV Cache。现有方法通常根据“最近有没有用过”决定淘汰，但一个 KV 暂时没被访问，并不代表后面不会再用。

**它怎么判断**

CommitKV 利用工具调用的 commit 时刻做判断。如果某段 KV 在工具调用之前很重要、工具结果返回后明显不再重要，系统才认为这部分上下文已经完成使命，可以删除；只是暂时休眠的 KV 会继续保留。

**结果怎么样**

在 Qwen3-14B、4096 token 预算下，准确率为 46.54%，而最强压缩基线为 26.69%。 `53aef9b0-8316-4c4b-a07f-8eb06f33dd30.html`

**我为什么把它放进日报**

这里真正有意思的不是某一种 KV 压缩算法，而是它利用了 **Agent 执行状态** 来管理缓存。如果内部 Agent 系统也能识别“工具调用完成”“任务阶段结束”等状态，我们可以验证这些状态能不能帮助判断哪些上下文可以提前释放。

这一版明显更长。

但是我非常确定：

**一个人读这一版获得的信息，会远远多于读现在那五个高度压缩字段。**

## 1. human-writing 根本没有权力改变“怎么讲这件事”

它能做的是：

> 把一个难看的 `mechanism` 字段重写成好一点的 `mechanism`。

但它不能说：

> “这篇其实不需要单独写机制、证据、边界、启发，我用三段话把事情讲清楚就行。”

更不能说：

> “这篇没有真正的项目启发，`project_relevance` 不写。”

因为 schema 不允许。

所以你看到现在每篇都是：

> 摘要  
> 机制  
> 证据  
> 边界  
> 启发

这不是模型偶然形成的写作习惯，**是我们代码强制它这么写的**。

换模型、加 human-writing、再增加 50 条“像人一样说话”的规则，都改变不了这个事实。

## 2. 我们一边要求“自然”，一边要求“所有事实一个都不能丢”

PR #60 的 human-writing prompt 里有一句很关键：

> Preserve **every fact, number, comparison, baseline, condition, caveat, causal strength**...

也就是说，它必须保留草稿中的**每一个事实、数字、comparison、condition、caveat**。

与此同时，它又必须：

> 6 个字段全部填写  
> 总共控制在 230-330 字。

这两个目标其实是冲突的。

拿 AAFLOW+ 来说，它要在大约 300 字里保留：

- KV 可物化
- 可传输
- 可分叉
- 可组合
- 可逐出
- 零拷贝
- transfer vs recomputation cost model
- 10-400 Gbps
- Mistral 0.041s vs 2.057s
- 16 Agent 220s vs 1680s
- 内存 1.72-6.10×
- 64 output token
- 7-8B
- 微基准而非墙钟
- 项目启发

然后还要分成五六个槽。

模型还能怎么办？

只能写成：

> “状态流算子扩展数据流抽象,调度按传输字节除以带宽加时延对比重算预填的成本模型决策……” `53aef9b0-8316-4c4b-a07f-8eb06f33dd30.html`

**这不是 human-writing 没努力，而是我们给了一个几乎不可能自然完成的压缩任务。**

上次只是把 260 字增加到了 330 字，缓解了一点，没有解除矛盾。

## 4. 标题的 AI 味也是 Contract 制造的

当前 item-writing contract 要求：

> technology/project + single core change/value。

结果模型非常自然地学成了模板：

> `X + 用/把/让/靠/按 + mechanism + result`

于是整期变成：

- Genesis **以**……
- AutoDesign **让**……
- CommitKV **按**……
- ZhuLong **用**……
- AAFLOW+ **把**……
- PTStore **按**……

这不是 human-writing 没有“vary sentence rhythm”。

而是**任务给它定义了一个高度稳定的标题生成公式**。

所以 PR #60 虽然 prompt 里已经明确要求“vary sentence rhythm”， 但模型优化的第一目标仍然是满足结构和 schema，而不是创造自然标题。

## 5. 上次 human-writing 只处理了 Deep Item，根本没覆盖整封邮件

## 6. 单次 issue-level 润色其实还有一个副作用：风格收敛

我们当初选择：

> `$human-writing ×1 / issue`

主要有两个原因：

1. 降 token 成本；
2. 一次看到整期，可以消除跨条目重复。

这个决定不是完全错误。

但是把二三十条 item 一次放进去，再要求输出同样六个 JSON 字段，模型很容易进入一种**批处理模式**：

> 每条都用相同信息结构、相似句法、相似压缩率完成。

于是越润色，整期可能越“整齐”。

而人的技术日报反而不会这么整齐：

有的条目重点讲机制；
有的只需要一个结果；
有的应该解释为什么反直觉；
有的只有一句话就够。

**过度统一本身就是 AI 味。**

# 7. 我们的 Validator 检查的是“有没有违规”，不是“人能不能看懂”

这是上一次最大的方法论错误。

我们加了很多 fail-closed contract：

- 标题不能和结论重复；
- 字数不能超；
- 不能超过多少句；
- 不能出现某些 generic filler；
- 数字数量受限；
- 不能用某些 consultancy phrase。

这些很适合检测：

> **明显坏格式。**

但它检测不了：

> “给TPN卡网络侧价值问题生产级量化”

到底是不是人话。

因为：

- 字数合法；
- 是完整句；
- 没有黑名单词；
- 没有事实错误；
- 没有重复标题；
- 有项目相关性。

从 Validator 眼里，这是一个**完美答案**。

甚至这期里的：

> “跨Agent上下文复用的系统原语与传输重算决策公式，可直接进跨节点缓存设计。” `53aef9b0-8316-4c4b-a07f-8eb06f33dd30.html`

也完全可以通过我们现有的所有 deterministic tests。

因此出现了一个很讽刺的状态：

> **CI 全绿，语言仍然很烂。**

不是 CI 坏了。

是我们测错东西了。
