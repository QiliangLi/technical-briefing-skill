4 Balanced session-centric scheduling
4.1 Analysis of existing schedulers
A preliminary on the LLM scheduling in a cluster.To
the best of our knowledge, LLM schedulers [ 54, 38, 17, 2,
34, 3, 42, 59, 53, 11] follow the same methodology as tradi-
tional request routing: upon receiving a request, the scheduler
computes a score for each instance i and routes the request to
the instance with the lowest (or highest) score, depending on
the score definition. Figure 10 illustrates the methodology.
Specifically, for each instance to route, its score is defined as
f(c i, li) over two per-instance indicators: ci estimates how
much of the request’s prefill can be skipped by reusing in-
stance i’s locally cached KV$ (e.g., the prefix hit length),
and li estimates the instance’s load (e.g., its batch size or the
number of inflight tokens).
Our analysis uses the following representative methods:
• BAILIANis the production method currently deployed
at BAILIAN. It uses a linear-combined scoring function
of KV$-awareness (the hit ratio) and the current load
(batch size). Other popular open-source schedulers adopt
a similar design [34, 3]. Specifically, the f is defined as
f= (1−λ)· ˆli +λ·(1−ˆci) (the lower the better), where ˆci
is the KV$ hit ratio and ˆli is the batch size of the instance,
and λ is a tuned weight that trades KV$ reuse for load
balance. Note that each indicator carries aˆ· that normalizes
it to a common range; otherwise the two indicators
cannot be added together. For serving agentic workloads,
the operator explicitly sets a largeλ to favor more KV$ hits.
• LMetric[ 54] is the state-of-the-art scheduler published
recently, whose effectiveness has been verified on
non-agentic workloads. It uses a multiplication-based
combinator to combine the KV$-awareness and load
balance indicators: f= (L−c i)×l i, where L is the
request’s prompt length, soL−c i is the prefill computation
left after reuse. The multiplication eliminates the tuned
weight while preserving both KV$-awareness and load
balance.
• Load-balance-onlyconsiders load only, i.e., f=l i,
routing each request to the least-loaded instance regardless
of its KV$ reuse. It is a variant of the classic join-the-
shortest-queue policy used in traditional cluster-level
request routing and the default policy of vLLM [ 44], a
popular LLM serving framework.
The analysis methodology.We compare the performance
of scheduling methods by replaying our production trace
(Trace 1) on a 32-instance vLLM [44] cluster serving Qwen3-
Coder-30B-A3B (detailed configurations in §5.1). Since the
evaluated model generates responses that differ from those
recorded in the trace, a strawman replay would distort the
request patterns. We therefore carefully adjust the responses
during replay to ensure a consistent trace execution, e.g.,
forcing the model to generate the same number of output
tokens as recorded in the trace (detailed in §5.1). The cluster
uses Mooncake [38] with LMCache [29], the best-performing
open-source stack to our knowledge, as its global KV$ store.

The rationale of using the session turn and its availability.
SMETRICrelies on knowing each request’s turn in its session
for scheduling (line 7). We choose the turn as the indicator
because it can be collected in a router-stateless way—by
stateless, we mean the router keeps no record of users’ past
requests. A naive alternative is to have the router remember
where each session executes—recording, for every active
session, the instance it was routed to. This forces the router
to maintain a session-to-instance table: the table grows with
the number of active sessions, must be kept up to date, and
must be garbage-collected as sessions fall idle, since a session
never signals its end. Choosing the turn avoids all of this
because it can be piggybacked or inferred from the LLM
requests, as we describe below.
We obtain the turn in this stateless way as follows. One
simple option is to modify the agent framework to tag each
request with its turn, but this raises compatibility issues: agent
frameworks are diverse and evolve quickly (e.g., Claude
Code [6] and OpenClaw [ 36]), and a provider can modify
only its own in-house framework, not the external ones its
users run. Instead, we infer the turn information: agents
interact with LLM serving through standard APIs (e.g., the
OpenAI API [35]), and since the API follows a stateless de-
sign, each request carries the past conversations of the session,
so SMETRICdeduces the turn directly from the number of
historical messages in the request. The deduction fails only if
the agent drops the history, but the failure is benign: dropping
the history forfeits its KV$ reuse, which is uneconomical
for the agent and thus rare; even when it happens, SMET-
RICsimply treats the request as the first request of a new
session—which is the right decision, since such a request hits
little KV$ anyway.
5 Performance evaluation
5.1 Evaluation setup
Testbed.Our testbed is a cluster of four GPU servers,
each equipped with eight NVIDIA H20 GPUs (96 GB HBM3
per GPU), 160 CPU cores, and 1280 GB of host DRAM.
The cluster thus supports up to 32 instances for single-GPU
models. Servers are interconnected with 200 Gbps RDMA
NICs. Each instance runs the latest vLLM [22, 44] with de-
fault optimizations enabled and tuned parameters. The global
KV$ store is based on Mooncake [ 38] and LMCache [29],
which implement the state-of-the-art global-tier architecture
described in Figure 2. The scheduler runs on a separate CPU
server with 64 cores and 256 GB DRAM. Unless otherwise
stated, we use all instances to evaluate the performance.
Evaluated model.We evaluate two models, Qwen3-Coder-
30B-A3B and Qwen3-235B-A22B-FP8, both popular models
on the market [48]. Qwen3-30B can be served with only one
GPU, allowing us to evaluate up to 32 instances. In contrast,
Qwen3-235B requires a minimum of 4 GPUs to serve as an
instance, so we can evaluate up to 8 instances.
Evaluated workload.We replay Trace 1 (§3) for all experi-
ments. Because the requests are collected from a much larger
cluster than our testbed, we sample them to control the request
rate to the cluster, following prior work [54, 58, 31, 19, 41].
One issue with replaying is that the evaluated model’s re-
sponses differ from those recorded in the trace. Such a differ-
ence breaks the KV$ reuse pattern in two ways: the generated
response may have a different length, and a follow-up re-
quest’s recorded history no longer matches the tokens the
serving instance actually cached. We fix the issue as follows.
First, we force the evaluated model to generate exactly as
many tokens as the recorded response, by ignoring the end-
of-sequence token and capping the generation at the recorded
length. Second, we rewrite a part of the follow-up requests
with the generated content to ensure consistent KV$ reuse.
