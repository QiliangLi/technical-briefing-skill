SMETRIC: Rethink LLM Scheduling for Serving Agents with
Balanced Session-centric Scheduling
Jiahao Wang1, Kaizhan Lin †1, Kaixi Zhang 1, Jinbo Han 1, Xingda Wei 1, Sijie Shen 2,
Chenguang Fang2, Wenyuan Yu 2, Rong Chen 1, Haibo Chen 1

Abstract
LLM scheduling is critical to serving, yet it remains unclear
how well existing designs fit agentic serving—with LLM re-
quests issued by agents instead of humans. This shifts the
workload in two ways: (1) agents act only on complete re-
sponses, making the cluster’s tokens per second (TPS) the
primary goal and relaxing—not eliminating—per-token la-
tency requirements; and (2) requests share much of their
KV$—reuse exceeds 80 % of request tokens in a production
trace from BAILIAN, versus 54–62 % in chat.
This paper first contributes a systematic study of request
scheduling for agents on two real-world traces. We find that
to increase KV$ reuse, existing schedulers overly prioritize
routing requests to instances caching their KV$, overload-
ing a few while leaving the rest idle, capping TPS. We thus
present two key insights: (1) load balance need not sacrifice
all KV$ reuse, thanks to the global-tier KV$ store and (2)
by utilizing the workload’s intra-session locality, balancing
a small fraction of requests—the first request in each agent
session—suffices to balance the cluster without sacrificing
most KV$ reuse on local instances.
SMETRICrealizes these insights with balanced session-
centric scheduling: it routes each session’s first request purely
for load balance and its follow-up requests in a cache-aware
manner, preserving load balance and local reuse while keep-
ing demand on the global tier low. Using thesession turn
informationas the scheduling metric is deliberate: it is de-
rived efficiently and accurately from the user inputs alone, so
the scheduler stays clean and stateless. SMETRICimproves
cluster TPS by 10–16 % under prefill-decode colocation with
a global store and prefill TPS by 2–34 % under disaggregation
over state-of-the-art schedulers, also with a better per-token
latency.

serves these tokens determines both the speed and the cost of

serving is still LLM serving: the provider serves each request
through the standard LLM API and neither runs the agents
nor sees their internal logic. What changes is the workload,
because the requests now come from agents.
Request scheduling—how the cluster routes each request
to an instance—is a key pillar of LLM serving. Though well-
studied recently [54, 59, 42, 53, 17, 2], we argue that current
scheduling designs must be revisited for agentic serving, for
two reasons:
First, agentic serving requires a different performance ob-
jective: the cluster’stokens per second(TPS) becomes the
primary goal, while the per-token latencies targeted by prior
work [54, 59, 58]—time-to-first-token (TTFT) and time-per-
output-token (TPOT)—still cannot be sacrificed, only relaxed.
This shift is driven by two properties of agentic workloads.
(1) An agent emits far more tokens per request than a human
chat user does [9], so a cluster must sustain high TPS to serve
the load at low cost. Besides cost, a cluster whose TPS falls
short of demand queues requests, so every agent waits longer
for its response. (2) An agent tolerates delays on any individ-
ual token—the first or a later one—as long as the complete
response arrives quickly: unlike a human who reads tokens as
they stream [8], an agent acts only on the complete response,
e.g., to decide which tool to call. Latency requirements still
hold, however: a response that is too slow makes the agent
treat the request as timed out [7]; these requirements are only
more relaxed than for humans.
Second, agentic serving exhibits a different pattern from
chat: KV$ reuse dominates. Specifically, the efficiency of
serving an LLM request depends heavily on KV$ reuse, where
the KV$ is the intermediate state a cluster caches to avoid
recomputation (§2). In chat workloads, this reuse is modest:
only 54–62 % of request tokens are reused from cache [45]. In

agentic serving, KV$ reuse dominates: by analyzing the pro-

when KV$ reuse dominates at this scale.
In this paper, we conduct the first systematic study of re-
quest scheduling for agents, using two recent large-scale real-
world agentic serving traces (§3). By studying both state-of-
the-art schedulers and the production scheduler of BAILIAN,
we find that the key issue is not that they fail to reuse the
KV$, but that they overly prioritize it: they route each request
to the instance holding its cached KV$ (cache-aware), trading
load balance for reuse. In particular, first-turn requests across
sessions of the same agent framework share similar system
prompts (Finding 3), so a cache-aware scheduler routes them
all to the few instances caching these prompts. Moreover,
since each follow-up request is likely routed to the instance
caching its session’s earlier turns, every session is pinned to
the instance where its first request lands; these few instances
thus absorb entire sessions and become overloaded, while the
rest of the cluster sits underutilized.
Sacrificing load balance is harmful: an imbalanced cluster
leaves the compute of underloaded instances idle, directly
capping TPS. Worse, the sacrifice is unnecessary, as we find
the token computation of real-world agentic workloadscan
be balanced across instances at scale (Finding 6). Meanwhile,
simply abandoning cache-awareness for balance is no better,
since reuse saves the computation of most prefill tokens, as
discussed above.
To address this dilemma, we draw two insights. First, from
the system’s perspective, pursuing load balance does not have
to compromise KV$ reuse: modern agentic serving adopts
a two-tier KV$ store—a local tier on each instance’s GPU
memory and a global tier on cluster-wide CPU memory (§2).
Even if the scheduled instance does not hold the KV$ locally,
it can fetch it from the global tier. As long as the global tier
serves these KV$ fetches in time, TPS is unaffected (§4.1); the
only cost is a small increase in TTFT, which agents tolerate
as discussed above. The global tier, however, is not a free
lunch: its capacity and bandwidth are limited, and routing
everyrequest purely for balance—funneling all reuse through
global fetches—risks exceeding what it can hold and serve in
time. The scheduler should therefore still exploit local-tier
reuse.
Second, from the agent workload’s perspective, once the
scheduler considers local-tier KV$ reuse—i.e., prioritizes
routing targets with high reuse, the common practice—the
placement of each session’sfirstrequest largely determines
the cluster’s load balance. This is because of the workload’s
intra-session locality: (1) follow-up requests mostly reuse the
KV$ of earlier turns in the same session (Finding 2), and (2)
such reuse happens quickly (Finding 4), so when a follow-up
request arrives, its KV$ typically still resides in the local tier
of the instance that served the previous turn. Consequently,
all requests of a session are likely routed to the same instance
as its first request (§4.2). Scheduling first requests alone for
load balance thus suffices to balance the cluster; and since
the first requests of sessions are only a small fraction of all
requests, the global tier alone is sufficient to support their
KV$ reuse.
Based on these two insights, we propose SMETRIC: bal-
anced session-centric scheduling for high-TPS agentic serv-
ing. SMETRICincorporates agent session information into
scheduling with a differential policy: for the first request of
each session, it schedules purely for load balance, spread-
ing sessions across all instances of the cluster; for follow-up
requests, it follows traditional cache-aware routing that prior-
itizes local-tier reuse, keeping demand on the global tier low.
Using the session-turn information as a routing hint is our
explicit design choice: this hint can be obtained in a router-
stateless way from an existing LLM call, i.e., without the
router keeping any record of users’ past requests. The router
thus routes each request as a pure function of the request
itself, keeping no per-session state to track or to reclaim as
sessions go idle, which keeps the router simple and scalable.
This simple policy also achieves balanced execution while
preserving KV$ reuse, even for the first requests: their reuse
comes mostly from the shared system prompt of the agent
framework (Finding 3), which the scheduled instance can
fetch from the global tier wherever the request lands. Finally,
to handle the rare tail case where many long sessions accu-
mulate on the same instance, SMETRICmigrates sessions
across instances upon imbalance.
We have implemented SMETRICon vLLM [ 44] and LM-
Cache [ 29], and extensively evaluated it against state-of-
the-art schedulers, including the production scheduler used
in BAILIAN, with serving paradigms spanning both prefill-
decode colocation and prefill-decode disaggregation. SMET-
RICserves 10–16 % more TPS under colocation when the
global store is present, and 2–34 % more prefill TPS un-
der disaggregation than the best-performing baseline across
global-tier provisionings. It also lowers the P50 and P90
TPOT under colocation and the TTFT at all reported per-
centiles under disaggregation (37 % lower at the median).
In summary, this paper makes the following contributions:
• The first study of the workload patterns of LLM requests
served by an agent-dedicated cluster at scale (§3).
• The first analysis of how existing schedulers perform with
the two-tier KV$ store under agentic serving (§4.1).
• A new LLM scheduling design that incorporates the session
characteristics of agent requests to achieve both high KV$
reuse and load-balanced serving (§4.2).
• Evaluation that confirms the effectiveness of SMETRIC
(§5).

2 Background and System Setup
LLM and KV$.An LLM serves a request in two phases.
Given the input tokens (theprompt), aprefillpass pro-
cesses the prompt with a single model forward (possibly
split into chunks [ 1]) and emits the first output token. A
decodepass then emits the remaining tokens one by one in
an auto-regressive manner, until the model produces an end-
of-sequence (EOS) token. Each token comes from a single
model forward whose input is the prompt followed by every
token emitted so far, appended in generation order.
The forward pass of LLMs requires computing a key (K)
and a value (V) tensor for each token in the input sequence.
Since these tensors are the same for inputs with the same
prefix, it is standard to cache the KV tensors generated so
far (the KV$) to accelerate the decode phase, as well as the
prefill phase of later requests with the same prefix. As shown
in Figure 4 (a), if a 3-token input request has two KV$ hits,
then it only needs to compute the KV$ for one token.
KV$ store hierarchy and the local vs. global tiers.Since
cross-request reuse is common in production workloads [45,
38], serving systems typically cache the KV$ of finished
requests for some time. Caching requires storage capacity
because each request’s KV$ is large: for example, a single
128K-token request consumes about 32 GB of KV$ on the
popular Qwen3-32B model. As a result, the KV$ store in
production systems follows a multi-tier architecture as shown
in Figure 1. The first tier is device (GPU) memory; when
it fills, KV$ cascades to the larger, global tiers below—host
(CPU) memory, then cloud storage (e.g., S3). A later KV$
hit on a lower tier must load the entry back up to the GPU.
Note that thanks to recent techniques including GPU-direct
RDMA, the global tier can also fetch data from remote GPU
memory (➂).
In this paper, we consider only two tiers: the GPU memory
tier (local tier) and a CPU memory tier linked by RDMA
(global tier). This does not lose generality: the storage tier
shares the same PCIe and RDMA link as the computation
tier [47], so modeling it separately would not increase the
speed of the global tier.

3.1 KV$ reuse patterns
We first analyze the following key features of KV$ usage in
agentic serving: the KV$ reuse ratio, where the reuse comes
from, and the distribution of reuse intervals. We distilled four
findings through these metrics:
Finding 1:KV$ reuse is dominant: the reuse ratio ex-
ceeds 80 % of the KV$ in both traces (Figure 5).
Figure 5 profiles the workload KV$ reuse ratios in agentic
serving scenarios: we can skip 80 % of the KV$ computation
by reusing those generated so far, assuming all KV$ can be
stored. We measure reuse at KV-cache block granularity
using an idealized infinite KV store, where each block holds
a fixed number of tokens, with the block size matching that
used by the cluster serving the workloads. During prefill,
each KV block is looked up in the store; hit blocks contribute
the tokens whose computation can be skipped. The reusable
ratio is the number of skipped prefill tokens divided by the
total number of prefill tokens.

than 65 % of reuses come fromfollow-uprequests (the
second turn onward) reusing earlier turns of the same
session (Figure 5).
