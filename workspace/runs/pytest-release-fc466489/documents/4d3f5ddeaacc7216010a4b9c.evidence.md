We report each method’smaximum TPS within SLO. For
each offered request rate, TPS within SLO is the cluster-
wide TPS contributed only by requests that satisfy both the
TTFT and TPOT SLOs. As discussed in the introduction, the
request-level SLO remains important for agents: although an
agent tolerates fluctuations in per-token latency, a response
that is too slow makes the agent treat the request as timed
out [7]. We set the SLO following BAILIAN’s production
targets, which also match the common practice in academic
studies [58, 46, 55]: a TTFT SLO linear in the number of
input tokens and a fixed TPOT SLO (30 ms). We sweep the
offered request rate and take the maximum TPS within SLO
over the sweep.
Finally, we also analyze the performance with different
global tier provisioning. We call the global tierfully provi-
sionedwhen it is configured with the maximum capacity of
our testbed. For the model analyzed in this section, the fully
provisioned global tier is never the bottleneck: it holds the
KV$ of all ongoing sessions, and its bandwidth keeps up with
the fetch demand. Nevertheless, in production we do observe
under-provisioned global tiers, due to either insufficient ca-
pacity or bandwidth. We therefore additionally sweep the
global tier’s per-node capacity, relative to the local tier, and
report each method’s performance under each provisioning.

6 Related Work
LLM request scheduling.Recent work on LLM serving
has explored request scheduling from multiple perspectives,
including KV$-aware and SLO-aware scheduling, dynamic
rescheduling with request migration, and flexible request
partitioning across instances [ 42, 38, 43, 59, 11, 40]. Our
work builds upon these insights and mechanisms, and fur-
ther derives agent-session-aware hints for the scheduler to
improve serving performance for agents. Unlike systems that
co-design serving with agent applications and require appli-
cations to expose inter-request structure [26, 30], SMETRIC
operates entirely on the provider side, treating agents as un-
modified clients. This matches how LLM providers, including
BAILIAN, serve agents today.

The compared targets are the same as in PD colocation
(§4.1), because scheduling prefill instances faces the same
trade-off between local KV$ hits and global load balance. The
only exception is load-balance-only: we replace vLLM’s de-
fault policy with Dynamo [34], a state-of-the-art open-source
disaggregated serving system. Dynamo routes a request by
the number of new prefill tokens it would compute on each
instance. This metric improves on other load indicators (e.g.,
the batch size used in vLLM) because it also captures KV$
reuse: a hit reduces the new tokens left to prefill. Note that PD
colocation cannot directly adopt such a unified token count,
because prefill and decode tokens have different computation
patterns.

decode tolerates some imbalance in PD colocation: a decode
step generates one token per request and demands relatively
little computation, so an overloaded instance can still absorb
requests into a larger batch. Although a larger batch slows
each decode step, it also generates more tokens per step, so
load imbalance only mildly degrades the total TPS. Comput-
ing the prefill tokens is different: it is compute-intensive, so
once the batch saturates the GPU’s compute, further enlarging
the batch (or queueing requests behind the current one) only
delays the requests without improving the throughput. As a
result, an imbalanced load directly costs the prefill TPS.
