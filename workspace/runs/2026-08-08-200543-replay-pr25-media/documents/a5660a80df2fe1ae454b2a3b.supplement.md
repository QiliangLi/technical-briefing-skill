Worker.A worker is the fundamental execution unit of
TensorCast, responsible for maintaining tensor states and
executing lifecycle operations. Rather than deploying sepa-
rate services for storage, workflow execution, and metadata
management,TensorCastcomposes worker functionalities
through differentroles. Currently, three roles exist:i) Basic.A
worker with the basic role contributes its memory and disk
resources to the unified tensor pool (§4.2). It also maintains
a local plan executor for processing worker-local plan steps
(e.g.,artifact prefetch()) dispatched from other workers,
but doesnotdirectly receive plans from callers. AllTen-
sorCastworkers operate with the basic role at minimum.
ii) Gateway.Gateway workers provide the entry point for
callers to submit lifecycle workflows. They maintain caller
connections, resolve plan-step dependencies, and dispatch
operations to corresponding workers or instances for exe-
cution. In practice, gateway workers can share a common
routable address behind a load balancer to provide scalable ac-
cess to external callers.iii) Shard Home.For high-cardinality
tensors such as KV caches,TensorCastpartitions tensor
states into multipleshards(§4.2). Workers with the shard
home role maintain the ownership and consistency invari-
ants of specific shards. This composable role architecture
separates different lifecycle responsibilities while preserv-
ing a unified worker abstraction. It simplifies configuration,
deployment, and monitoring of heterogeneous worker re-
sources (e.g.,assigning high-performance nodes as KV cache
shard homes) and allowsTensorCastto introduce new life-
cycle capabilities through additional worker roles.
Instance.Instance nodes implement the mechanism bound-
ary betweenTensorCastand computation engines. A typi-
cal instance node runs an LLM execution engine (e.g.,an in-
ference or training framework) and contains aTensorCast
caller runtime that connects to a gateway worker.Tensor-
Castintegrates with the execution engine through anIn-
stance Adaptor, which implements the minimal interfaces re-
quired to export, import, or transform engine-resident tensor
states. This separation ensures that instance integration fixes
only the underlying tensor management mechanisms, while
workload-specific policies remain programmable through
callers. Consequently, new tensor management strategies
can evolve without repeatedly modifying execution engines
or backend implementations.
Global Store.TensorCastuses a Global Store (GS) as
a lightweight control-plane metadata service rather than
a component in the tensor data path. The GS maintains
cluster metadata, including worker and instance status, the
replica locations of low-cardinality tensors (§4.2), and shard
ownership information. To avoid introducing a centralized
bottleneck, workers cache metadata locally and refresh it
through update exchanges with the GS. Therefore, most
tensor management workflows bypass the GS and execute
directly among workers and instances. The GS additionally
serves as the entry point for cluster observability, including
workload monitoring and runtime metrics.
4.2 Unified Tensor Pool
The unified tensor pool realizes the Artifact abstraction
by separating logical tensor identity from physical tensor
residency. Although callers interact with stable Artifact
handles,TensorCastdynamically manages concrete ten-
sor replicas across workers, devices, and storage tiers.

Setup.We use a single node with 64 CPUs, 500 GB DRAM,
and 8 × H800 GPUs to launch a vLLM instance (TP=8). This
setup emulates a MaaS auto-scaling scenario, where new
instances are launched as quickly as possible. We load model
weights in safetensors format from three storage types:i)
a high-performance distributed file system (JuiceFS [61]);ii)
node-local SSD; andiii)node-local DRAM (tmpfs). Given a
model path on each storage type, the vLLM instance material-
izes weights through four configurations:i) Default, vLLM’s
native weight loader;ii) InstantTensor[ 62], a fast weight
loader with pipelined and zero-copy I/O;iii)TensorCast
cold, where aTensorCastworker reads rank-specific weight
slices from storage and materializes them into VRAM, after
which the vLLM process consumes the tensors through the
tensor_dict API; andiv)TensorCastwarm, where weight
slices are pre-materialized locally through the prefetch API
and vLLM directly consumes the materialized tensors. This
design exploitsTensorCast’s separation between tensor
lifecycle management and execution initialization, allowing
tensor materialization to occur concurrently with instance
launch or during a pre-flight stage.
Results.We report both the model weight loading time dur-
ing instance launch and the end-to-end instance-ready time
to evaluate howTensorCastaccelerates instance initializa-
tion. As shown in Fig. 5 and Fig. 6,TensorCastconsistently
outperforms all baselines across settings. In particular, un-
der JFS, a common case where MaaS providers host model
weights, for the Qwen3-30B-A3B model,TensorCast-cold
reduces model weight loading time by 60.7× and 10.2× com-
pared to Default and InstantTensor, respectively (Fig. 5a).
Consequently, it reduces end-to-end launch-ready time by
28.5× and 5.4×, respectively (Fig. 5b). These gains stem from
two factors:i)TensorCastconcurrently reads slice views
for each rank while also issuing parallel read streams for
each rank’s assigned slice; andii)tensor transfers to VRAM
are pipelined to hide H2D copy overhead. ForTensorCast-
warm, vLLM consumes pre-materialized tensors in less than
1 second, asTensorCastuses CUDA IPC to enable zero-
copy access. As a result, end-to-end launch time is only domi-
nated by runtime initialization overhead, yielding 228.6× and
40.7× speedups over Default and InstantTensor, respectively,
for the Qwen3-235B-A22B model (Fig. 6b). These results
demonstrate thatTensorCastcan efficiently materialize
large immutable tensor states while preserving a general
tensor management abstraction.
