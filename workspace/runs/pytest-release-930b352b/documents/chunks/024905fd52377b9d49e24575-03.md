communicate directly with the global store, pre-
serving the separation between application programs and
the TensorCast control plane.

We evaluateTensorCastto answer two questions:i)whether
a unified tensor lifecycle layer can provide efficient mech-

Setup.We use a single node with 64 CPUs, 500 GB DRAM,
and 8 × H800 GPUs to launch a vLLM instance (TP=8). This
setup emulates a MaaS auto-scaling scenario, where new
instances are launched as quickly as possible. We load model
weights in safetensors format from three storage types:i)
a high-performance distributed file system (JuiceFS [61]);ii)
node-local SSD; andiii)node-local DRAM (tmpfs). Given a
model path on each storage type, the vLLM instance material-
izes weights through four configurations:i) Default, vLLM’s
native weight loader;ii) InstantTensor[ 62], a fast weight
loader with pipelined and zero-copy I/O;iii)TensorCast
cold, where aTensorCastworker reads rank-specific weight
slices from storage and materializes them into VRAM, after
which the vLLM process consumes the tensors through the
tensor_dict API; andiv)TensorCastwarm, where weight
slices are pre-materialized locally through the prefetch API
and vLLM directly consumes the materialized tensors. This
design exploitsTensorCast’s separation between tensor
lifecycle management and execution initialization, allowing
tensor materialization to occur concurrently with instance
launch or during a pre-flight stage.
Results.We report both the model weight loading time dur-
ing instance launch and the end-to-end instance-ready time
to evaluate howTensorCastaccelerates instance initializa-
tion. As shown in Fig. 5 and Fig. 6,TensorCastconsistently
outperforms all baselines across settings. In particular, un-
der JFS, a common case where MaaS providers host model
weights, for the Qwen3-30B-A3B model,TensorCast-cold
reduces model weight loading time by 60.7× and 10.2× com-
pared to Default and InstantTensor, respectively (Fig. 5a).
Consequently, it reduces end-to-end launch-ready time by
28.5× and 5.4×, respectively (Fig. 5b). These gains stem from
two factors:i)TensorCastconcurrently reads slice views
for each rank while also issuing parallel read streams for
each rank’s assigned slice; andii)tensor transfers to VRAM
are pipelined to hide H2D copy overhead. ForTensorCast-
warm, vLLM consumes pre-materialized tensors in less than
1 second, asTensorCastuses CUDA IPC to enable zero-
copy access. As a result, end-to-end launch time is only domi-
nated by runtime initialization overhead, yielding 228.6× and
40.7× speedups over Default and InstantTensor, respectively,
for the Qwen3-235B-A22B model (Fig. 6b). These results
demonstrate thatTensorCastcan efficiently materialize
large immutable tensor states while preserving a general
tensor management abstraction.

6.2 Model Weight Synchronization
We evaluateTensorCast’s ability to synchronize versioned
tensor states across distributed LLM instances by integrating
it into SGLang as a new model weight updating module.
Setup.The experimental setup consists of a two-node clus-
ter, where each node runs aTensorCastworker with 64
CPUs, 500 GB DRAM, and 4 × H800 GPUs. We use the
WeightPublisher helper provided byTensorCast, which
wraps the put() API to publish different versions of model
weights into aTensorCastworker on one node. A serv-
ing SGLang instance on another node synchronizes model
weights by retrieving tensors from theTensorCastcluster.
This setup represents the training-serving synchronization
pattern commonly seen in RL post-training, where a trainer
publishes updated model weights and rollout workers period-
ically synchronize their parameters. During synchronization,
each tensor-parallel (TP) rank retrieves only its correspond-
ing tensor slice through the view() API, demonstratingTen-
sorCast’s ability to materialize different tensor layouts from
a shared tensor state. To ensure a fair comparison against the
Defaultbaseline, which retrieves full model weights from
JFS through a file path, we disable RDMA forTensorCast.
Results.As shown in Fig. 7,TensorCastaccelerates model
weight synchronization by 1.14 × to 2.63× compared with
the default updater. The acceleration trends vary with TP
size and model scale. For the Qwen3-14B model, increas-
ing TP size introduces additional tensor slicing overhead on
theTensorCastworker, which becomes the dominant cost
compared with tensor transfer. In contrast, for the larger
Qwen3-32B model,TensorCastbenefits from concurrently
transferring multiple tensor views, better utilizing available
network bandwidth and achieving higher acceleration as
TP size increases. These results demonstrate thatTensor-
Castcan efficiently manage versioned tensor states across
distributed execution instances while allowing different con-
sumers to materialize the tensor representations required by
their parallelism configurations.

We evaluateTensorCast’s programmability by implement-

multiple tensor lifecycle operations. We integrate an instance
adaptor into SGLang, enabling callers to execute the instance
operations listed in Tab. 2 on SGLang instances.
Setup.Based on the widely used cache-aware routing policy,
we implement a lightweight rebalancing policy that periodi-
cally observes instance states and migrates selected requests,
together with their KV caches, from the most-loaded in-
stance to the least-loaded instance using thePlan abstraction
shown in List. 1 (see detailed rebalancing policy in §A). This
combined policy aims to preserve KV cache locality while
avoiding load imbalance across instances, without losing con-
text during migration. The rebalancing policy is independent
ofTensorCastand can be customized without modifying
the SGLang scheduler, KV cache backend, orTensorCast
runtime. We compare theTensorCastrouter against three

instances; andiii)a pure cache-aware router that routes re-

cluster consists of four nodes, each equipped with 2 × H20
GPUs. Each node runs one Qwen3-32B instance with TP=2.

from real agent rollouts on the SWE-Gym task pool, col-

tain concurrent sessions as workload traffic to the cluster.

is sampled from a LogNormal distribution, since this right-

We use three LogNormal parameter presets–fast, medium,

7 Discussion
Applicability beyond inference workloads.While our
integration and evaluations in §6 focus on inference work-
loads,TensorCastcan also express tensor lifecycles in train-
ing workloads: At the abstraction level, checkpoints can be
mapped to versioned, system-ownedArtifacts, with view()
and transform_into() expressing rank-specific resharding;
gradients, optimizer states, and long-lived activations can be
exposed as caller-leased tensors. We leave the integration of
TensorCastwith training frameworks like Megatron-LM
[70] and DeepSpeed [71] for future work.
Integration cost and abstraction overhead.Decoupling
tensor management does not remove engine-specific integra-
tion:TensorCastconfines the export, import, or transforma-
tion of engine-resident tensor states to an instance adaptor,
so customized programs can evolve in callers without repeat-
edly modifying engines, transports, or storage backends. We
do not claim that a general abstraction is inherently faster
than every specialized implementation. §6.1–§6.3 evaluate
reusable mechanisms and show thatTensorCastachieves
comparable or better performance, while §6.4 shows opti-
mization enabled by composition.
8 Other Related Work
In addition to the studies for efficient tensor management
discussed in §2.1, many other studies have investigated opti-
mizations for LLM workloads.
Efficient LLM inference.An increasing body of literature
focuses on enhancing the efficiency of Transformer-based
LLM inference. These optimizations encompass parallelism
[72–74], request scheduling [75–77], memory management

[44, 78, 79], quantization [80, 81], and specialized GPU ker-
nels [82, 83]. Serving as a complementary approach,Ten-
sorCastoffers flexible, large-scale tensor management and
integrates seamlessly with these existing techniques.
Programmable LLM systems.Numerous studies explore
the programming of LLM behaviors. One line of research
targets frameworks for prompt engineering and agent orches-
tration, including LangChain [84], LangFlow [85], AutoGen
[86], and DSPy [87]. These tools simplify agentic workflows
to accelerate LLM application development. Another direc-
tion provides fine-grained control over the LLM inference
process–encompassing tokenization, attention, KV cache
management, and decoding–through systems like microserv-
ing LLM [88] and PIE [47]. However, existing programmable
LLM systems operate primarily at theexecution layerof
LLM workloads. In contrast,TensorCastintroduces pro-
grammable management of the data lifecycle (i.e.,tensors),
making it an orthogonal and complementary approach to
current frameworks.
9 Conclusion Remarks
As LLM systems continue to evolve toward increasingly
dynamic and stateful workloads, efficient tensor lifecycle
management becomes a fundamental infrastructure chal-
lenge beyond individual optimization techniques.Tensor-
Castintroduces the missing tensor management layer by
decoupling tensor states from the computation that produces
and consumes them, enabling tensors to be managed as pro-
grammable, first-class system resources. Through lifecycle
primitives and a distributed runtime,TensorCastachieves
the efficiency of specialized tensor management mechanisms
while allowing developers to compose new workload-specific
policies. Our results demonstrate that future LLM infrastruc-
ture should not only optimize computation over tensors, but
also provide programmable control over the lifecycle of the
tensor states that drive these computations.
