B. Attention Computation
The attention computation involves three steps, 1⃝P=
QK T , 2⃝S=sof tmax(P), and 3⃝O=S×V, and it
raises two challenges that two strategies address. First, Steps
1⃝and 3⃝are memory-bounded GEMV operations, so slow
KV cache migration from the devices to the GPU limits their
efficiency. Second, offloading part of Steps 1⃝and 3⃝to NDP
cores still sends the intermediate resultSover the link, which
adds significant latency at long sequence lengths.
1. KV Cache Distribution Strategy: For collaborative
GEMV in Steps 1⃝and 3⃝, PLoRA evenly distributes the
KV cache of each request across all memory devices at
the token level, storing the KV cache of thei th token
in the(imodN dev)th device, as shown in Fig. 7. PLoRA
also duplicates a small portion of the KV cache in GPU
memory (HBM) when space permits, which lets GPU and
NDP cores compute in parallel and maximizes aggregated
internal bandwidth. PLoRA overlaps prefill KV cache transfer
with computation, and during decode each new token’s KV
cache goes directly to the devices. Because duplicated entries
compete with LoRA adapters for GPU memory, the GPU
management system in Section VI evicts them using our
algorithm and cost model.

VI. PLORA GPU MEMORYMANAGEMENTSYSTEM
When a request arrives, PLoRA looks up its LoRA adapter
ID and the current batch size, then runs the strategy selection
algorithm (Section VI-A) and the cost model (Section VI-B)
to determine the optimal execution strategy for all requests
that share this adapter. A new request can, for example, push
an adapter’s batch past the point where caching both matrices
beats fetching them, switching that adapter from E4 to E1,
loading its A matrix, and evicting KV cache to fit the budget.
A. Strategy Selection Algorithm
PLoRA selects the optimal execution strategy under the
GPU memory constraint, using the cost model of Section VI-B
to estimate execution time. KV cache, LoRA adapters, and the
base model compete for limited GPU memory. We classify
adapters as serving adapters used by requests in the current
batch, hot adapters likely needed by future requests, and
cold adapters unlikely to be used soon. A temperature metric
separates hot adapters from cold ones: each new request raises
its adapter’s temperature by a fixed increment, all temperatures
relax toward the system average by0.1of the gap per step,
and PLoRA pre-caches the 50 hottest non-serving adapters.

Finding 4: under direct memory access, link latency is
second order.Fig. 13(d) sweeps the one-way link latency
from 50 to 2000 ns, charged per layer since decode is layer-
sequential, two round trips per layer, one LoRA wave and
one attention return. Short-KV throughput never moves, the
charge hides under the base-model step, and the CXL-bound
long-KV workload gives up 0.3% at our assumed 200 ns and
2.6% at 2000 ns. This does not contradict Section III-B: a
memory-semantic link pays these nanoseconds from inside the
running kernel, where in-flight loads overlap them, while the
PCIe+CPU path pays microsecond software latencies, a kernel
stop, a host-run copy, and a relaunch on every exchange, and
it forfeits near-data reduction. CXL-class fabrics win on the
access model, not on wire latency, so PLoRA tolerates any
switch-class latency.
