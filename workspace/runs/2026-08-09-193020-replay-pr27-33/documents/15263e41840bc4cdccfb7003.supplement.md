5.4 Chunked Prefill Scheduler on Decode Nodes
vLLM’s scheduler already supports chunked prefill as a batch-
ing strategy. When a request whose prefill phase is pending
is sent to the decode node,Kairossends the chunk sched-
ule for the request in the KV parameters. The underlying
scheduling policy remains the same, but at each step, the
max tokens in the batch is governed by the corresponding
chunk size in the chunk schedule of the request currently in
its prefill phase.

6.1 Experimental Setup
We run our experiments on Azure Machine Learning Com-
pute Clusters [10], using Standard_ND96amsr_A100_v4 nodes.
Each node is equipped with 8 × Nvidia A100-SXM4-80GB
GPUs connected through NVLINK 3.0, an AMD EPYC 7V12
CPU with 64-Cores along with 900 GiB of host memory and
1.7 TiB disk storage. Internode communication is through
InfiniBand [14] and Azure Accelerated Networking [11].

8 Related Work
A wide variety of works have targeted optimizing LLM infer-
ence, including optimized kernels [4, 7, 19], KV cache man-
agement [8, 20], batching [ 1] and SM partitioning [ 3, 17].
However, these works focus on single node inference opti-
mization. Access to multiple nodes leads to more ways to
route requests, store weights, load balance and parallelize.
SplitWise [15] and DistServe [21] introduced prefill/decode
disaggregation by characterizing the differing compute/mem-
ory boundedness of prefill and decode phases. Mooncake
[16] treats the KV cache as a first-class distributed object
with a global index, enabling prefix reuse and fine-grained
migration. TetriInfer [6] addresses disaggregated scheduling
on heterogeneous GPU fleets.
TaiChi [18] proposes a unified PD aggregation-disaggregation
architecture with different kinds of instances (prefill-heavy
vs.decode-heavy) and configurable sliders that adapt the
ratio between instances and their chunk sizes to optimize
goodput under TTFT/TPOT SLO combination. It uses la-
tency shifting, i.e. selectively reallocating GPU resources
from SLO-satisfied requests to at-risk ones, orchestrated by
flowing-decode scheduling and length-aware prefill schedul-
ing. On the other hand,Kairosidentifies prefill nodes as the
bottleneck during bursts, and performs a per-request TBT-
safe deflection decision instead of modifying global cluster
configuration.

PPD [9] also performs deflection to the decode node, but
does so for Turn 2+ requests in a multi-turn setting, since
these requests with high cached token counts slow down
decode nodes less than Turn 1 prompts. WhileKairosand
PPD share the same idea of deflection to the decode node,
Kairosis more general since any request can be deflected if
there is headroom, and also incorporates run-time monitor-
ing of nodes to make deflection decisions that do not violate
TBT.
9 Conclusion
This paper presentsKairos, a proactive deflection frame-
work that utilizes unused decode node compute to serve
deflected requests. For each incoming request,Kairosesti-
mates its projected TTFT through the regular disaggregated
and deflection paths, and deflects request to a decode node
with available capacity when doing so meets SLO of incom-
ing and existing requests.
