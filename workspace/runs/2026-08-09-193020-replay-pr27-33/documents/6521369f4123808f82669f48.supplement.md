Setup.We use a single node with 64 CPUs, 500 GB DRAM,
and 8 × H800 GPUs to launch a vLLM instance (TP=8). This
setup emulates a MaaS auto-scaling scenario, where new
instances are launched as quickly as possible. We load model
weights in safetensors format from three storage types:i)
a high-performance distributed file system (JuiceFS [61]);ii)
node-local SSD; andiii)node-local DRAM (tmpfs). Given a
model path on each storage type, the vLLM instance material-
izes weights through four configurations:i) Default, vLLM’s
native weight loader;ii) InstantTensor[ 62], a fast weight
loader with pipelined and zero-copy I/O;iii)TensorCast
cold, where aTensorCastworker reads rank-specific weight
slices from storage and materializes them into VRAM, after
which the vLLM process consumes the tensors through the
tensor_dict API; andiv)TensorCastwarm, where weight
slices are pre-materialized locally through the prefetch API
and vLLM directly consumes the materialized tensors. This
design exploitsTensorCast’s separation between tensor
lifecycle management and execution initialization, allowing
tensor materialization to occur concurrently with instance
launch or during a pre-flight stage.
Results.We report both the model weight loading time dur-
ing instance launch and the end-to-end instance-ready time
to evaluate howTensorCastaccelerates instance initializa-
tion. As shown in Fig. 5 and Fig. 6,TensorCastconsistently
outperforms all baselines across settings. In particular, un-
der JFS, a common case where MaaS providers host model
weights, for the Qwen3-30B-A3B model,TensorCast-cold
reduces model weight loading time by 60.7× and 10.2× com-
pared to Default and InstantTensor, respectively (Fig. 5a).
Consequently, it reduces end-to-end launch-ready time by
28.5× and 5.4×, respectively (Fig. 5b). These gains stem from
two factors:i)TensorCastconcurrently reads slice views
for each rank while also issuing parallel read streams for
each rank’s assigned slice; andii)tensor transfers to VRAM
are pipelined to hide H2D copy overhead. ForTensorCast-
warm, vLLM consumes pre-materialized tensors in less than
1 second, asTensorCastuses CUDA IPC to enable zero-
copy access. As a result, end-to-end launch time is only domi-
nated by runtime initialization overhead, yielding 228.6× and
40.7× speedups over Default and InstantTensor, respectively,
for the Qwen3-235B-A22B model (Fig. 6b). These results
demonstrate thatTensorCastcan efficiently materialize
large immutable tensor states while preserving a general
tensor management abstraction.
