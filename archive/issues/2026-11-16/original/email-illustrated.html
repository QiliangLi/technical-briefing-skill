Agent 的主要失效是信错证据，不是算错答案
OpenClaw 的真实部署问题实证里，访问控制失效、敏感暴露与注入三类信任边界失效合计 70.4%。同期受控实验显示：工具输出从全文投递改为按需检索，GPT 系两代模型各损失约十个百分点——模型算出的数值没变，是它改信了自己生成的高精度中间文件；RITE 往工具返回注入符合 Schema 的静默错误，十个模型多数错误未被察觉，平均 Retention 只剩 0.416。而在提示里指明权威报告后，正确数值取自报告的比例升至 99% 以上。运行时校验该瞄准结果可信：信源标注和证据整合比 Schema 检查更值钱。

vllm-rlt实测循环大模型服务：PD吞吐最高达基线3.3倍

论文/来源：What Sets the Serving Speed of Looped Language Models? Measurements and Optimizations Graded by Exactness

循环大模型每个token重复执行同层块，逐层开销被放大，而且朴素优化会改变输出。这项工作在vllm-rlt里按精确度分级优化，并发现PD解耦的KV交接尾延迟由在途预算轮次决定，而不是链路速度。

关键结果

KV经NIXL的CUDA IPC从预填充池直入解码池终页、无中转拷贝；32请求下PD吞吐从143-147升到479 tok/s，提交尾延迟从约1秒缩到17毫秒，而移除TCP只让64MB块从20.0毫秒降到16.9毫秒。

需要注意

PD证据仅限单节点IPC；最快一档关闭了UCX对端容错、与基线传输不匹配；也只测了小型循环模型。对推理网络的启示是先做传输预算与步间调度、再优化链路。

PD分离Agent服务的亚稳态：一次突增后，劣化不再自己恢复

论文/来源：When Cache Pressure Becomes a Trap: Metastability in Agent Serving

PD分离的Agent推理依赖前缀缓存复用，而一次短时请求突增就可能让服务陷入亚稳态——负载回落后劣化仍在持续。论文在真实系统里演示并建模了这种失效，并提出BASIN缓解。

怎么做的

机理是群体-缓存正反馈：变慢的响应拉长会话、扩大工作集，超出缓存后未命中触发重复预填充，会话进一步积压。BASIN用会话优先级准入，并把空闲解码显存出借给缓存扩容。

关键结果

实测10分钟突增一倍后，中位TTFT约60秒，前缀命中率从0.95跌到0.27；H200真实部署突增下，BASIN吞吐是Continuum的1.20到1.70倍。硬件实验仅单模型SGLang，1P1D上只与最强基线相当，多数结果来自仿真。

BridgeKV：大模型预填、小模型解码，中间做一次KV Cache翻译

论文/来源：BridgeKV: Large-Model Prefill and Small-Model Decoding for LLM Inference via KV Cache Translation

预填充计算受限、解码带宽受限，现有解耦方案却仍用同一个模型，解码要承担大模型的带宽成本。BridgeKV把大模型预填的KV Cache翻译成小模型布局，解码阶段只跑小模型。

怎么做的

一个轻量KV缝合模块负责翻译：逐层做源层聚合，键与值各自走残差非线性映射，弥合层数、KV头数与头维度的差异；两个锚点模型冻结训练，推理时只需一次缓存交接。

关键结果

服务仿真中8B→1B的响应时间从39.80秒降到9.13秒，吞吐增至113.5 tok/s；单卡A40实测每请求2.96秒，与1B单独跑的2.80秒相当。主表系统数字来自含排队与传输开销的仿真而非实测，质量侧五个数据集与指标在证据中不可见。

FORGE：把三成MoE专家权重压成种子，片上重生成省显存

论文/来源：FORGE: Procedural Weight Generation for Sparse MoE Inference

稀疏MoE解码同时受专家权重带宽和显存容量制约，多机专家并行每步还要跨机all-to-all。FORGE把三成MoE层的专家权重压成转子种子，由片上即时重生成，既省显存又免去跨机路由。

怎么做的

离线把各专家FFN投影拟合成每层数百KB的转子种子；推理时SM内的转子生成单元实时重生成权重块，绕开HBM加载。

关键结果

每专家8 token时，FFN内核较cuBLASLt FP8基线快2.28到3.23倍；释放28%到29%参数显存，4096上下文的KV容量扩到1.2到2.6倍。但系统级吞吐与时延是模拟器投影而非实测，RGU未流片，替换后下游精度低于不替换的微调模型且降幅未量化。

Firepool：LinkedIn用暖GPU Pod池把Agent循环提速13倍

论文/来源：Firepool: Brokering Warm GPU Capacity for Agentic and RL Workloads at LinkedIn

Agent与RL循环会发起大量秒级GPU任务，而为每个任务新建沙箱Pod即使有镜像缓存也要20到35秒。LinkedIn的Firepool在生产集群里代理暖Pod复用，配对基准下Agent循环快13倍。

怎么做的

每个集群的代理按硬件型号共享基础镜像，启动时才绑定代码与依赖；复用安全靠调用方持有和进程树死亡校验保证，再用零显存待机Pod与队列驱动伸缩。

关键结果

生产高峰期的3206次获取中94.7%由暖池或待机满足；配对基准下Agent与RL循环分别快13倍与10.8倍，p90启动时延从59.1秒降到3.5秒。不过13倍结果来自单节点合成定长任务，生产突发下等待会转为配额排队，论文也未经评审。

REINS：验证过的输出固化成规则记忆，LLM调用率降到12.81%

论文/来源：REINS: A Self-Evolving Agent Harness for Real-Time Trajectory Planning

怎么做的

可以怎么验证

值得在我们自己流水线上试的是这个回路本身：把Agent的Read与Grep结果缓存成带验收门的索引，削减重复探索。同时带上边界看：评估只到战术决策层，感知假设干净，碰撞率也并非可部署水平。

怎么做的
