Nebula：位置无关KV片段升级为集群级对象，跨节点调度预填充

论文/来源：Nebula: Distributed Position-Independent Caching for LLM Serving

RAG与代理的长提示频繁未命中前缀缓存，既有的位置无关缓存又只能在单节点内复用片段。Nebula把这些片段升级为集群级对象，由调度层决定跨节点取用还是并行预填充，以此压低TTFT。

调度怎么判断

调度上有两个设计点：路由器记录预期的缓存位置与各节点负载，靠节点事件纠正偏差；用“幽灵命中”反馈自动调节前缀缓存与位置无关缓存之间的容量配比。预填充完成时间的估计里，排队、计算与KV传输三类成本都计入。

关键结果

四个模型、四类RAG与代理负载上，中位TTFT较最强基线平均降低61.4%，能找回前缀缓存漏失token的76.1%。读数注意：每个请求限定一个输出token，TPOT、吞吐与网络利用率未报告，绝对TTFT只在图中，最强基线对应哪个对比系统文中未点名。

Evolving Infra：节点阶段在线切换不丢KV，端到端时延降到约四分之一

论文/来源：Evolving Infra: Agent-Adaptive LLM Serving at Scale

代理负载会在预填充重与解码重之间动态摆动，主流系统切换阶段需要重启并丢弃KV缓存。Evolving Infra把节点阶段与KV存储解耦，在线切换不重启：每个节点都能跑预填充与解码，规划器在线学习迭代用时模型并重指派阶段；KV驻留主机内存共享池，集群目录以引用计数管理分支，排队期间经RDMA异步取回远端KV。

关键结果

Claude Code负载、GLM-5.2上，平均端到端时延从54.4秒降到13.2秒，P95 TTFT从142秒降到10.2秒，均以Dynamo为基线——平均时延最多降到约四分之一。实验未报告重复次数与方差，聚合KV传输量与网络利用率也没有数字。

可以怎么验证

它的自适应全部做在服务层，网络只承担RDMA传输；因此可以作为衡量网络侧调度增值时的服务层基线，排队期间异步取回KV、与排队重叠的做法也值得借鉴。

ReKV：切层边界与传输精度联合选择，跨节点KV交接快2.36–3.65倍

论文/来源：ReKV: Overlapping Quantized KV Transfer and Suffix Recomputation

Prefill/Decode解耦后，长prompt的KV交接本身成了重要的网络负载。ReKV把“在哪一层切分”与“用什么精度传”作为联合决策并与计算重叠：跨节点H100的合成基准上，过质量门槛的Joint Q8让8K交接的中位时延比全量BF16传输快2.36到3.65倍，也快于更快的单机制动作。

怎么做的

执行上，预填充侧先发BF16的边界隐状态，解码侧重算后缀层；前缀KV量化后在途传输、到端恢复。动作选择先过质量门槛，再取中位时延最小者。

需要注意

读数范围要清楚：计时不包含prefill与后续decode，没有并发下的端到端TTFT/TPOT/P95；最优动作随序列长度与带宽翻转，带宽才是关键编排变量。它优化的是单次交接点，不是并发网络层的调度器。

11条trace的答案：KV多级存储的保留决策需要三个信号

论文/来源：The Storage View Of KV Cache: Characterizing Cache Behavior Across LLM Workloads

KV缓存外溢到DRAM与远端内存后，存储层光凭访问与新近度信号，很难决定保留谁、回收谁。UT Austin与IBM用11条trace提出一个接口：把工作负载、会话、会话结束三个信号交给存储层，信号本身对存储透明。

关键结果

他们先把各trace归一化为带时间戳与执行元数据的KV块访问流，区分单会话与跨会话复用，再用策略对比量化每个信号：按负载定制的空闲TTL比全局p90（253秒）最多多保留22%的会话内命中、少留40%死状态；会话ID计数比请求级少标4到700倍状态，其中41%到99%被复用。

需要注意

全部结论来自trace驱动的模拟，没有TTFT、TPOT这类延迟指标，放置决策也未量化——把它当接口设计的证据看，而不是系统结论。

InfraRSI：五阶段harness把训练优化做成可验证流水线，四负载平均提速1.83倍

论文/来源：InfraRSI: Harnessing Recursive Self-Improvement for Training Infrastructure

分布式训练的吞吐卡在启动参数、算子与通信调度的耦合上，单点优化难以下手。InfraRSI用五阶段harness把一句指令变成经16项不变量验证的训练优化：四个负载几何平均加速1.83倍、最高2.75倍（Gemma-4-26B-A4B），平均MFU从17.4%升到30.0%，均优于OptiCo等基线。

怎么做的

五个阶段各管一段：init锁定可改范围与任务契约，doctor标定测量噪声，run组合搜索启动参数与经AST校验的补丁，apply审计后提交；沉淀下的经验按硬件兼容性过滤，再跨集群复用。

可以怎么验证

最值得搬走的是验收结构：固定契约、分层不变量验证、失败成本记账加经验迁移门控，可以直接用作“让Agent改代码换性能”的验收门。两点保留：搜索消耗的GPU小时与token总成本未见报告；跨GPU代际重放旧配置会因收益压缩甚至反号而失效。

把流程状态搬出上下文：运行时用状态机拦住长程任务的流程漂移

论文/来源：Keeping LLM Agents on Procedure: Executable Finite-State Control for Long-Horizon Instruction Fidelity

长程任务里，Agent会慢慢偏离开头一次性给出的流程，重述提示或续跑只是让漂移改道。这篇论文把流程状态整个移出模型上下文，交给运行时在工具调用、状态迁移与回合结束三处强制执行：状态机由守护进程持有并落盘，上下文压缩抹不掉；工具调用先查当前状态是否允许，守卫命令成功退出才提交迁移，Stop门专门拦住提前收工。

关键结果

效果差距明显：200账号SOP任务上，Haiku配FSM做出139.2项忠实且正确的决策，并稳定保持到最后一个账号，最强基线只有48.4；SWE-bench较难任务上是69对62，分歧全部偏向FSM。

需要注意

限制同样清楚：主实验只评估了单一SOP任务与单一运行时；守卫过严会误拦合法操作，简单任务的中位耗时增加23%。若在自有流水线试点，工具调用门与停止门需要同时启用，守卫质量决定收益。

SkillCache：一次技能执行编译成程序胶囊，复用时模型只做判断

论文/来源：How Much Skill Orchestration Can LLM Agents Compile Away? Execution-Grounded Specialization for Token-Efficient Skill Use

可复用的技能每次调用都要模型重新解读、重排一遍工具调用，token随调用次数持续累积。SkillCache把一次执行编译成“程序加步骤”的参数化胶囊，复用时执行器串接程序传值，只有失败或需要判断的地方才交还模型，原技能保留作回退。

怎么做的

编译器不借助评测就把冷执行与原技能编译为参数化胶囊；复用前先重放校验，确认胶囊仍然成立才走缓存路径。

关键结果

87项SkillsBench任务上，token均值下降80.9%（Sonnet）与74.3%（Opus），奖励持平；Sonnet的模型调用均值从23.6降到5.6。不过验证只在SkillsBench与Claude Code上完成，胶囊源自单次执行、可能硬编码取值，检索与失效未测；消融显示仅重组工具执行链就能降token，机械环节值得试点，请求多变的场景还待验证。

怎么做的

改进分两级：任务级递归用Propose-Probe-Compose的行为对比修改harness；harnessing级把被采纳的编辑沉淀为经验库，供后续任务复用。

关键结果

GLM-5+OpenCode的WorkBuddy-Bench从64.2升到75.7，Gemini下k=5使JobBench增益+7.5。但增益主要来自可靠性而非提速：JobBench与LAB上每任务工具调用反增约两成，递归还要额外的测试时算力。借鉴行为对比验收门可以，别把这类收益记进调用缩减的账。
