SMem把上下文切成block独立编码，复用与删除按构造精确

论文/来源：Memory as a cache: Exact context reuse and deletion by construction
缓存怎么处理

KV缓存和完整前缀纠缠在一起，精确复用就只限于共享前缀。SMem把上下文切成block，block局部编码器各自编码成memory行，reader经交叉注意力用行并集生成。精确复用、O(b)精确删除、与编辑顺序无关这三个性质对所有参数成立，是连接模式的推论而非训练结果。

关键结果

TTFT较冷prefill降67到69%，训练长度4到8倍时降到88到94%，decode持有的KV行少34到38%，删除比重算后缀快8.5到452倍。

需要注意

全部是单GPU微基准，删除加速探测的是成本模型而非服务态，没有跨节点部署实验。细粒度、可精确失效的block缓存对象可以作跨节点调度的候选抽象，但不能据此评估网络侧调度的增量价值。

WUSH-KV按数据二阶统计构造变换，KV缓存2比特还能用

论文/来源：WUSH-KV: KV Cache Quantization with Data-Adaptive Transforms
怎么做的

KV缓存低比特量化的瓶颈之一是固定正交变换。WUSH-KV按校准数据的二阶统计，为key与value分别用Gram矩阵闭式构造可逆变换，value侧变换折叠进模型权重零在线成本，key侧在RoPE后在线施加，与标量量化器无关。

关键结果

Qwen3-8B的2比特下WikiText-2困惑度10.51，OSCAR变换13.74，全精度9.72，LiveCodeBench 35.2对20.4。

需要注意

缺吞吐与时延评测，长上下文RULER上与BF16的差距随长度扩大，最优性证明只对QuEST量化器成立。2比特压缩能等比削减跨节点KV传输字节，是每token字节数的杠杆候选，增量价值要实测。

activation与KV稀疏化的加速交叉点可以提前算出来

论文/来源：Where Activation Sparsity and KV-Cache Sparsity Cross in LLM Decoding
怎么做的

LLM decode同时有两类稀疏化在省带宽，activation稀疏化削权重流量，缓存稀疏化削KV流量，两者收益都依赖上下文长度且难以直接比较。论文给出只用模型维度与keep ratio就能推出两分支字节节省相等的交叉长度，配一个latency gate为每请求选最快且过质量检验的配置。

关键结果

A100上Llama-3.1-8B投影分支在2K处1.36倍，KV选择在128K处1.54倍，组合分支8K起最快、128K达1.91倍，交叉点预测偏差至多4.1K token。

需要注意

主计时是batch 1，大batch下投影分支优势基本消失，没有服务级指标与多节点实验。KV流量何时主导decode带宽的可预测账目，可以当作我们何时为KV传输做网络侧调度的量化依据，结论先限于单GPU。

LYREO用KV占用刻画边缘服务器负载的调度方案，目前只有仿真

论文/来源：End-to-End Latency-Minimizing and Load-Balanced Request Scheduling for Edge LLM Inference in Agentic AI Services
调度怎么判断

agentic服务反复调用LLM，把推理放到地理分布的异构边缘服务器时，调度随时间耦合且延迟反馈滞后。LYREO用KV缓存的内存与时间消耗度量刻画服务器负载，跨时隙模型跟踪传输、prefill、逐迭代解码与各服务器KV占用演化，Lyapunov虚拟队列满足均衡约束，LSTM奖励重分配缓解反馈滞后。仿真里各服务器规模下平均延迟与负载偏差均低于PPO与启发式基线。

需要注意

主结果只有图序与坐标范围，逐方法数值不可见，全部为仿真且无真实testbed。KV占用感知的请求层调度可视为TPN状态感知在边缘的一个实例，但仿真结果不能证明网络侧机制的增量价值。

让Agent一次写完程序，协程桥接把模型调用从工具往返里解放出来

论文/来源：Policy as Code: A Coroutine-Bridge Harness for Fast-Reasoning Reliability on CAR-bench

CAR-bench把每个工具调用放进评测器执行，依赖调用链每出一轮结果就要再调一次模型，多轮任务的时延被模型调用次数拖住。这支队伍改了harness的形状，模型唯一的动作是发出一个Python程序，程序在持久worker里运行，遇到工具调用就阻塞，结果注入后原地恢复，不新增模型调用。

关键结果

官方隐藏评测上该harness以60.0%的Pass^3排名第一，是主办方基线的4.5倍，同批次里成本最低，中位任务时延也最快。换到GPT-5.5的Open赛道，同一份harness不改代码复现出同样的60.0%。

需要注意

隐藏集上仍有四成任务至少失败一次trial，worker状态只存内存，重启即丢，验证域是车载助手任务。我们下一步可以在代码Agent的搜索定位链路上试协程桥接，看重复模型调用能省下多少，代码任务上的迁移收益还没有来源证据。

XRepoSkill从成败轨迹的分歧点学跨仓库可迁移的技能规则

论文/来源：XRepoSkill: Learning Transferable Skills for Software Engineering Agents

从历史轨迹蒸馏技能的agent常见一个毛病，仓库一换技能就失灵，因为成功轨迹里的动作未必真的导致成功。XRepoSkill换了提取方式，先把工具调用抽象成类型加目标，再对比同一issue的成败轨迹，在第一次分歧处导出候选规则，每条规则要过可执行断言，还要在新仓库复现才算数。

关键结果

SWE-bench Pro平均解决率53.8%，高出最强基线2.1个百分点，DeepSWE平均44.2%，比无技能agent高10.3个百分点，六个benchmark与LLM组合全部第一，且评测仓库都不在学习轨迹池里。

需要注意

稳定性与消融只在单一backbone上报告，DeepSWE上的成本是各方法里最高的，论文也没有度量Read和Grep次数的变化。头部规则加按issue限量注入的做法，对我们控制自改进harness的更新成本有直接参考，加速收益本身仍是推断。

Unity Insight给游戏仓库建持久化代码资产索引，Agent的token账单砍半

论文/来源：Unity Insight: A Production Code--Asset Index for LLM Coding Agents in Unity Projects
关系怎么查询

Unity项目的C#脚本和prefab靠GUID互相关联，现成检索工具回答不了跨文件引用的问题，agent只能在源码和序列化资产之间反复摸索。Tuanjie团队的解法是离线建一个只读索引，crawler解析C#源码与资产文件，解开GUID、路径映射和嵌套prefab链，再暴露五个类型化查询工具给agent当导航面。

这组数字只讲成本，没有报告答案正确率，每题只跑一次，索引构建成本也在测量窗口之外，模型与游戏规模未披露。持久只读图加类型化查询的形态值得搬到代码仓库的符号定位链路上试，纯代码仓库的收益要自己验证。

递归自改进何时失效，要审计scaffold而不是只查权重冻结

论文/来源：Audit the Scaffold, Not the Checkpoint: A Stationarity Dichotomy for Recursive Self-Improvement in Agentic Coding
为什么会这样

递归自我改进的安全审计习惯检查模型权重有没有动，但这回答不了自改进什么时候把空间耗尽。这篇论文证明，只要可达编辑集不变，收益就严格递减，想继续涨只能重写scaffold本身，证明用Lean 4做了机器校验，侧向结果还给出best-of-k编排恰好是单个worker的性能上限。

关键结果

30个同族worker上多数投票在42%的任务上失败。401个生产session里，70.0%的多commit会话churn逐步递减，中位晚期比早期只有0.49。

可以怎么验证

对编排的直接影响是，worker数不必超过最优上限，精炼后期轮次大多不再改工件，预算优先投首轮和模型能力，验收门要防住scaffold改写测试。注意生产数据是观测性的，条件化后部分轮次的置信区间含零，结论是有界体制而非成因。
