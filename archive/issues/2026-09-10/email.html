统一AI网关:切模型之前,先问KV缓存放哪了

论文/来源：Unified AI Gateway: A Framework for Joint Model Routing and KV Cache Management

多模型服务里有个常被忽略的耦合:路由切换到另一个模型,已经算好的KV cache往往不可用或不兼容,目标模型只能全量重算前缀,这次重算的成本可能吃掉换模型省下的钱。这篇把选模型和管缓存定义成同一个网关里的联合决策:请求进来时同时决定目标模型、执行站点和缓存动作(复用、跨模型映射、传输或就地重算),后台再持续优化缓存的放置与生命周期。

关键结果

由于没有系统实现,证据来自八个负载profile、不同切换率下的解析仿真:TTFT加速最多13.28倍,输入成本收益最多6.16倍。它同时综合了文献数字——跨模型KV映射比重算快数十倍,质量损失可控制在低个位数百分比——并给出映射值得做的判据:传输加映射的时间要小于目标侧重算时间,误差不超过允许损失。

需要注意

要记住这些收益是仿真与文献数字,不是实测;不同引用来自不同基线,不能横向比较。对我们而言,值得带走的是那句话:路由决策应该把缓存状态当作一阶变量,映射对重算的成本判据可以直接搬进我们多模型网关的设计。

vLLM v0.29.0:三个默认行为变化,升级前先回归

论文/来源：vllm-project/vllm v0.29.0

vLLM v0.29.0是594次提交的大版本,Model Runner V2成为所有模型的默认运行器。对部署方影响最大的不是新模型支持,而是几个默认行为的变化:FlashInfer all-reduce成为TP组默认(可以用环境变量退出),分布式KV cache的NONE_HASH默认确定性(跨引擎共享缓存的用户不用再固定PYTHONHASHSEED),Mamba类模型的前缀缓存引入内部prefill检查点。

可持续推理控制平面:把能耗和缓存复用变成路由决策的一等变量

论文/来源：Toward Sustainable Distributed LLM Inference: A Systems Synthesis and Research Agenda for an Energy-, Carbon-, and Cache-Aware llm-d Control Plane

LLM的可持续性讨论多在训练端,这篇综述把焦点拉回服务系统:推理能耗强烈依赖负载几何、软件栈和硬件组合,而现有路由与扩容只看时延和成本。作者综合近年文献,为llm-d式的分布式推理控制平面画了一张SICP草图:路由与扩容在满足TTFT/TPOT SLO硬约束下,同时考虑能耗、碳强度、缓存复用与重计算代价。

关键结果

文献连接出的几条结论值得记:推理能耗不是模型常数,优化服务能大幅降耗但最优解随负载形状变化;decode主导生成型负载的能耗,投机解码小批量省能、大批量反而增能;KV状态的重计算不只是时延损失,还是可避免的能耗——所以缓存保留还是驱逐,应该成为可测量的能耗优化,而不是路由的副作用。

需要注意

边界很明确:作者没有重测任何引用结果,SICP只是草图,增益不能假定能迁移到llm-d实现。对我们有用的是那个定价框架——传输versus重算的模型(网络能耗、占用、复用概率)可以并入我们KVCache跨节点传输的权衡评估,把能耗列为一等成本。

Jacap:把softmax的非线性算进KV驱逐打分

论文/来源：Jacap: Robust KV Cache Eviction via Jacobian-Based Nonlinear Information Capacity Preservation

KV驱逐的主流方法(SnapKV、KeyDiff一类)都靠启发式打分:注意力权重、新旧度或者值范数。这些分数缺一个理论依据——softmax是非线性的,一个token的贡献不只取决于它自己,还取决于它在整个分布里的相对敏感度。Jacap把保留的注意力建模成非线性信道,对注意力映射做一阶泰勒展开,导出Jacobian信息容量目标,同时覆盖查询相关性、softmax敏感度和值空间的多样性。

怎么做的

实验里最有价值的现象是:压缩率越高,Jacap相对启发式的优势越大——LongBench 0.9压缩时平均领先次优方法约5分,NIAH的深needle与长上下文也持续更稳。代价是复杂度:对头维度有平方依赖,不过实测在常规头维度下与现有方法运行时相当。

可以怎么验证

这提示KV驱逐的下一档收益来自把非线性效应显式建模,而不是再发明一个启发式分数;但采纳前要先量一下驱逐步骤的实际时延占比,矩阵求逆在长上下文需要分块或近似处理。

Airbnb把harness优化变成一道选择题:先看可靠性,再看平均提升

论文/来源：Beyond Prompts: Measuring and Optimizing LLM Tool-Agent Harnesses

围绕固定模型做多轮工具agent,大多数团队的做法是改提示词、改中间件,然后用一轮验证集看提升。Airbnb这篇指出这样做有个坑:搜索过程是随机的,这次搜出来的harness下次可能就不行了。他们把harness改进重新表述成预算受限的选择问题——数据切成repair、gate、scorecard三段,scorecard只在最后碰一次,并引入RelLift95来估计按预算选出harness后,倒霉情形下还能剩多少提升。

RepoNav:代码agent找到了对的文件,为什么还是改错函数?

论文/来源：RepoNav: From Snippet Retrieval to File-Centered Repository Navigation for Code Agents
为什么会这样

这篇先回答了一个我们常遇到的现象:检索工具明明把agent带到了正确的文件,函数级定位还是失败。对失败分类后发现,相当大一部分miss发生在文件对、函数错——扁平的片段列表没有给出足够结构,agent分不清目标函数和同文件里语义相近的替代者。

怎么做的

RepoNav的解法很克制:不动检索分数,只是把检索到的chunk聚合成候选文件,再为每个文件生成三块信息——查询相关的锚点入口、文件内其他符号的略图、一份候选检查目标短名单,配合list_symbols按需浏览。这让agent在承诺修改前先比较兄弟符号。

关键结果

在LocBench七个模型上,函数级Acc@5平均从0.484提到0.557,文件到函数的定位差距大幅收窄到21.7个百分点。两个细节值得注意:只给浏览工具而不做文件中心组织,涨幅有限,组织方式本身贡献更大;代价是交互token几乎翻倍,从31.7k涨到62.4k。

CapScope:给每个agent发单独的权限,间接注入就没那么可怕

论文/来源：Authority Is Not a String: A Capability-Scoped Harness for Prompt-Injection-Resistant Coding Agents

编码agent的沙箱里,工具默认是ambient authority——只要说得出资源名就能动手。间接注入正是利用这一点:在仓库文件或工具输出里塞指令,让模型替攻击者干活。CapScope的思路是不去猜哪段文本恶意,而是收权:任务开始前用可信输入(用户请求加文件树,不看文件内容)预先算出这次任务的权限天花板,冻结后存放在模型上下文之外。

怎么做的

关键是每个agent一份独立能力库:委派子任务时只下发子任务需要的权限,且不超过委派方的天花板;每次工具调用都按发起者自己的能力检查。这样,读到被投毒测试输出的runner可以跑测试,但没有写源码的权限,注入的写操作直接被拦。

关键结果

在Pi编码agent的300次运行里,注入效果执行从基线的33-47/75降到3/75,修复完成率68/75与最强基线持平。代价是时延:均值316秒对基线194秒,但增量主要来自被拒后的重试轮次——有人工审批在环时这部分会明显回收。局限也要说清楚:只有5个小型Python修复任务,而且它不是机密性机制,被允许的读加被允许的写仍然能把数据搬走。

Rufus:一份工作流定义,编译到实时、异步、批三种运行时

论文/来源：Substrate-Portable Execution for Production LLM Workflows

Amazon Rufus的agent逻辑要在三种模式下跑:面向顾客的实时流式、后台异步任务、以及评估和内容预生成这类大批量离线。三种模式各有SLO,过去各用一套运行时,复用流式编排会让异步和批负载阻塞,还用不上打五折的批推理API。他们的解法是把工作流定义成类型化数据流图,推理作为一等可挂起节点,由编译器按目标基底生成原生实现:进程内流式、SWF持久异步、Flink跨调用批提交。

关键结果

关键的验证问题是:同一份工作流在三个基底上输出质量是否一致。答案是有——五种编排模式的Bradley-Terry置信区间全部包含零,没有可检测的质量差异。代价也标清楚了:SWF比流式慢1.1到3.4倍,Flink批路径慢33到152倍,但那是提供商批调度主导的,换来了批价。

需要注意

两个无法消除的分歧源是时间敏感的工具输出和基底基础设施失败;结论也只覆盖Bedrock与对话购物域。对我们最实用的一点:工作流定义与执行基底解耦后,成本变成了编译期决策——评估、预生成这类负载可以迁到批价通道,并用同样的BT配对方法做迁移验收。

同一个请求,不同的回答:前缀缓存会改变agent的轨迹
