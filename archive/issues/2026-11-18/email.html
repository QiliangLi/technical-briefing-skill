HyCoInfer：云端GPU做prefill、边缘FPGA分担decode，链路上只跑RVQ压缩的KV

论文/来源：HyCoInfer: Cloud-Edge Collaborative Inference for Large Language Models on Heterogeneous GPU-FPGA Architectures

GPU解码阶段算力闲置，边缘FPGA又难独撑高并发。HyCoInfer的分工是：云端GPU做prefill、边缘FPGA分担decode，链路上只送RVQ压缩后的KV，500Mbps下时延最多降61.1%。

调度怎么判断

调度上按队列负载、提示长度与网络状态分派请求；KV逐层流水传输，隐藏在prefill之内；RVQ压缩深度不固定，按带宽、质量下限与时延预算来选。

关键结果

500Mbps下相对云上vLLM，三个负载平均时延降32.0–61.1%，Qasper吞吐升到4.11×；100Mbps下较未优化协同吞吐达3.45×。验证限于整形带宽试验台、单模型与单块FPGA，下游精度保持与P95指标未见报告；另外它的场景是广域云边，不是集群内互联。

卫星上做分解式LLM推理可行吗？解析模型先划出容量与距离的可行域

论文/来源：Disaggregated LLM Inference in Space: A Communication Feasibility Study

分解式LLM服务在地面已经成熟，能否承受星间链路约束一直缺少定量判断。这项解析研究算出PDD与AFD的在轨容量-距离可行域，并提出紧凑编队加分布星座的分层轨道推理架构。

怎么做的

建模方式是完全解析的：通信时间按串行化加传播时延计算；PDD沿用Mooncake地面TTFT实测、替换星间传输时间；AFD把逐层激活交换限制在TPOT的10%以内。

关键结果

代入Qwen3-235B的地面基线，星间链路从100提到800 Gbps时，KVCache传输占TTFT的份额从约24-31%降到3.8-5.8%，与地面参考相当。这是纯解析研究，未做真实负载仿真与端到端实测，吞吐与P95也未见报告。

TAILROLL：不做跨引擎KV传输，纯调度也能把RL rollout提速

论文/来源：TAILROLL: Tail-Aware Rollout Acceleration for RL-Based LLM Post-Training

rollout占RL后训练步时的50%–76%，长尾响应让引擎空转。TAILROLL证明了纯调度就能同时改善TTFT、TPOT与吞吐：解码请求在chunk边界迁往其他vLLM引擎、用一次re-prefill恢复，不做跨引擎KVCache传输；GRPO组内样本足够即提前终止。

关键结果

AMC12负载下每步rollout在8K省23.6%、16K省33.9%，p95 TTFT最多下降88.4%，吞吐最高增33.3%且奖励持平或更高。未见交互式推理服务评估，短步多模态负载下时长也几乎不降。

可以怎么验证

在投入KV传输类的网络侧优化之前，先拿这个纯调度上限做对照：证明避免重新prefill、感知KV位置还能在其之上多拿多少收益，才是网络侧投入的价值所在。

Callo：编辑让KV缓存失效后，拿它当投机解码草稿遮住重预填充等待

论文/来源：Callo: Serving Cache-Miss Requests with Speculative Decoding on Invalidated KV under Prefill-Decode Disaggregation
缓存怎么处理

Agent会话反复编辑上下文，前缀KV缓存随之失效，请求必须在解码前完整重预填充。Callo的招是：P实例重预填充期间，D实例拿失效KV当草稿做投机解码，对照流入的精确KV验证后才提交，保持原解码规则，并按累计接受概率让出算力。

关键结果

两GPU测试床上，SWE-agent会话中等负载下较vLLM全请求加速1.05-1.19倍、未命中请求1.06-1.24倍，折叠了47%的未命中惩罚。收益依赖会话亲和路由、缓存未被淘汰与空闲解码算力，接近饱和时退化；集群规模结果是校准仿真。

Cairn：冷启动的大头不是加载权重，编译工件也该放进共享内存池

论文/来源：Fast Serverless LLM Cold Starts by Sharing and Prewarming Startup Work

Serverless LLM冷启动里只有5-11%在加载权重，其余是各服务器重复的编译与初始化。Cairn把权重与引擎工件发布到共享CXL内存池就地读取：首启服务器把权重、编译代码与编译键写一次后转只读，其余服务器经DMA原地读取，槽表索引用CAS加租约更新。

Google用门控进化自改进Agent Harness：约十分之一token逼近全量重写

论文/来源：Harnesses That Improve Themselves: A Unifying Framework for Self-Improving Agent Harnesses

手调的静态harness换一个模型就常停滞甚至回归，token浪费也明显。Google的做法是把harness拆成四个可编辑的运行时组件，外循环诊断轨迹、逐模块提补丁，经过运行时检查和留出任务验证后才部署。

关键结果

在SWE-bench Lite留出集上，门控进化做到40.0%准确率，是种子的8倍，每任务46.7k token；无约束的整体重写能到42.5%，但要消耗451.6k token——门控进化用约十分之一的token成本就逼近了这个准确率。

需要注意

验证范围很窄：仅SWE-bench Lite的60个Python任务和Gemini家族，其他模型与任务类型都未验证。

REPOPREMIUM复测：稠密代码检索对BM25的优势大半是评测设定做出来的

论文/来源：Embeddings vs. Grep: Rethinking the Dense Advantage in Code Search

稠密编码器在代码检索基准上稳定压过BM25，可实践中Agent用grep也干得不错，两边一直对不上。REPOPREMIUM对此做控制变量评测：用真实仓库的策划查询与原始PR查询做文件排序，对比整文件BM25、标签规则、生成式查询扩写、固定RRF融合等干预，并在预注册的锁箱上一次性评分。

为什么会这样

复测把优势翻了个面：换成整文件BM25索引后，策划池里稠密检索的优势从+0.121压到+0.034 nDCG@10；再用LLM把标识符扩写进查询，grep在全部Python池反超稠密检索。也就是说，稠密的优势大半来自评测设定和标识符稀少的查询，而不是检索能力本身。

需要注意

适用范围有限：核心实验只覆盖十个Python仓库，函数级与行级目标未测；96个任务的Agent评测的条件与结果未见于证据。

跨任务记忆要先定价：CoReMem只留能在下一任务赚回成本的记忆

论文/来源：CoReMem: Cost-Internalizing Memory for Successive Coding Tasks with Prospective Valuation

编码代理在共享仓库的连续任务上反复重建上下文，常见的跨任务记忆层反而推高token开销。CoReMem的切入点是定价：只保留经下一任务实测价值能覆盖成本的记忆，在提升解决率的同时压降步数与token。

怎么做的

定价的办法很直接：把下一任务带着与不带候选记忆各重跑一遍再对比；划算的轨迹段被压成WHERE位置与VERIFY检查锚点，并配合演员模型的LoRA后训练。

关键结果

在ChainSWE测试半区，27B模型解决率从21.0%升到25.7%、步数降17%、token降11%；对照的记忆层最多多耗113%的token。评测限于mini-swe-agent、Python仓库与三个模型，缺墙钟时延与工具计数，收益也依赖记忆加后训练的组合。

STITCH：测试时用可复用原语组合出任务专属Harness

论文/来源：Composing Task-specific Agent Harnesses at Test Time with Reusable Primitives

固定harness难以适配异构任务，逐任务生成代码则随机制数量增加而指数级丧失可执行性。STITCH走中间路线：在测试时用可复用原语组合出任务专属的harness，兼顾适配与可靠。

怎么做的

原语从失败轨迹中挖掘，每个都带组合契约；测试时组合器只输出设计级的组合意图，由编译器确定性连接并校验，失败就回退种子harness。

关键结果

GPT-5.6-Luna下，SWE-bench Verified与Terminal-Bench 2的Pass@1分别为80.5%与72.2%，种子是73.0与60.0；困难任务仍弱，Terminal-Bench hard只有46.2%，也未报端到端时延。
