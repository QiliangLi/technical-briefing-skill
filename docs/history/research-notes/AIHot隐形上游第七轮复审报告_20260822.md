## 三、唯一需要修复的问题：报告日期使用 UTC

位置：`briefing_skill/pipeline.py:524,548-552`

生产创建 issue 时使用：

```python
datetime.now(timezone.utc).date().isoformat()
```

该日期还会用于 expanded 选择的 `reference_date` 以及 `issues.date_from/date_to`。例如：

```text
Asia/Shanghai: 2026-08-22 00:57
UTC:           2026-08-21 16:57
```

此时在上海运行，生成的日报日期会是 `2026-08-21`，比本地日期晚一天。这是正常运行中可能发生的真实问题，尤其是自动任务在凌晨执行时。

### 修复要求

- 根据系统配置的时区生成报告日期，当前部署应使用 `Asia/Shanghai`；
- 最好在 active run 创建时固定并持久化该日期；
- selection、issue、Radar 和 resume 都复用同一个日期，不要在后续阶段重新读取 UTC 当前日期；
- 增加一条上海时间跨日测试，覆盖 UTC 日期仍为前一天的窗口。

完成这一项后，本轮即可判定为通过，不需要继续扩大 Ledger、sidecar 或 manifest 的防御性校验。
