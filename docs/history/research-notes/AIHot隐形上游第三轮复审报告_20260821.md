## 一、结论

结论：**仍需修改（Request changes / FIX）**。

`161e5fc` 对上一轮问题做了大量有效修复，468 项全量测试确实全部通过。以下问题已经闭环：

- ledger 的多 query 唯一约束及存量数据库迁移；
- 正常发送路径写入 story/item 身份；
- 已冻结 run 遇到 lane plan 变化时明确失败，不再原地覆盖 freeze；
- active report date 按配置时区解释；
- 站点根 URL 不再被视为具体原始页；
- 一般校验异常下，新归档和历史 rewrite 不再留下部分公开写入；
- 重复 Radar DOM 会被 multiplicity 校验发现。

但是“全部问题已修复”仍不成立。第三轮主审和独立交叉审查共同复现出 3 个 P1：

1. 合法的 daily Radar 和跨 lane 中文文案回退会被新 provenance 发布门错误阻断；
2. 删除关键 hash 或同步改写 manifest 与 DOM 的分类仍能通过发布门；
3. 发送历史会把最终邮件中没有出现的 stale Radar 也标记为已发布，导致后续内容被错误去重。

此外，direct provenance 记录的重复项仍会被 URL dict 折叠，ledger 异常可在审计缺失时继续发布，归档的进程崩溃恢复和 shadow run 验收也尚未闭环。

所以当前状态应评价为：**上一轮大部分具体问题已修，但 provenance 新实现引入了正常输入误杀和新的 fail-open；暂不应视为最终可发布版本。**

## 三、必须修复的问题

### P1-1 新 freeze 回查会拒绝合法 daily 和多 lane 文案回退

相关代码：

- `briefing_skill/radar_direct.py:722-750`
- `briefing_skill/publication_manifest.py:450-475`
- `briefing_skill/adapters/aihot.py:260-291`

`locate_frozen_source()` 只遍历每个 lane payload 顶层的 `items` 或 `data`：

```python
for raw in payload.get("items") or payload.get("data") or []:
```

但是 daily 接口的真实结构是：

```text
payload.report.sections[].items[]
```

因此，daily-only 条目可以正常采集、通过技术范围和中文完整句筛选、进入最终 Radar，随后却必然无法在 freeze 中定位。主审复现得到 `final_count=1`，最终校验报：

```text
radar-direct record ... cannot be located in the frozen AI Hot responses
```

这不是脏数据，而是系统自己支持并默认启用的正式 lane。只要一期确实采用 daily 补充内容，发布就会被错误阻断。

同一个函数还有第二个问题：同一 item 在多个 lane 中具有不同摘要时，它遇到第一个 ID/URL 匹配就立即返回，没有确认该观察是否就是最终采用的 copy variant。

复现输入：

- selected：英文摘要，不符合公开中文要求；
- 后续 lane：完整中文摘要；
- 最终 deterministic direct-copy：正确选择中文版本。

发布校验仍会先命中 selected 的英文版本，然后报告中文 provenance 与 freeze 不一致。也就是说，上一轮刚修好的“多 lane 文案回退”会被这一轮新增的发布门重新阻断。

建议：

1. 在每个 copy variant/provenance 中保存精确 `lane_key`、upstream item ID 和 source field；
2. freeze 读取器统一展开 selected/all/paper 的顶层 items 和 daily 的 `report.sections[].items`；
3. 回查必须按准确 lane/identity/field 定位，或遍历所有身份匹配观察，直到找到与 provenance source text 精确一致的记录；
4. 增加 daily-only 和“前一 lane 不可用、后一 lane 中文可用”的真实 finalize + validate 回归。

### P1-2 provenance 仍未 fail closed，公开分类可绕过 selection binding

相关代码：

- `briefing_skill/publication_manifest.py:441-527`
- `briefing_skill/radar_direct.py:658-709`

新增代码已经会验证存在的 freeze hash 和 selection hash，但使用的是条件式检查：

```python
if stored_freeze_hash is not None and ...
if document.get("selection_hash") and ...
```

在 direct-copy 模式下，把 `radar-direct.json` 中的 `frozen_input_sha256` 和 `selection_hash` 两个字段直接删除，最终发布校验返回空错误。也就是说，“缺 hash”被当作“无需校验”，不符合 fail-closed 契约。

分类链也没有闭合：selection hash 绑定的是 direct record 中的 category，但 validator 只比较 manifest category 与 DOM category，没有把它们与 direct record category 比较。主审同步修改 manifest 与 DOM 的分类、保留 radar-direct 和 selection hash 中的旧分类，校验仍返回 `[]`。

这证明当前链条不是文档宣称的：

```text
freeze -> radar-direct -> manifest -> DOM
```

而是两段没有完整连接的链：

```text
freeze -> radar-direct
manifest -> DOM
```

此外，active report date 和配置时区仍未写入 selection binding；最终 DOM 中显示的 `published_at` 也没有进入 manifest/DOM 交叉校验。

建议：

1. direct-copy 模式下，freeze hash、selection hash、规则版本、selection contract 全部设为必填；任一缺失立即失败；
2. 以 Radar ID 或唯一 URL 对齐 direct、manifest 与 DOM，逐字段比较 category、title、summary、URL、published date；
3. manifest 显式保存 selection hash 或 direct document hash，形成单向链接；
4. 把 active run ID、report date、配置时区和所有公开字段纳入 selection binding；
5. 增加“缺字段”“分类联合改写”“日期联合改写”的 fail-closed 回归。

### P1-3 canonical 发送历史会记录实际未发送的 stale Radar

相关代码：

- `briefing_skill/publication_history.py:213-253`

上一轮指出 production `record_delivery` 没有写 story/item 身份。本次新增 SQL 确实解决了正常路径，但它无条件把该 issue 的全部 `issue_radar_items` 投影到 `radar_history`：

```sql
SELECT ... FROM issue_radar_items WHERE issue_id=?
```

它没有与从最终邮件 HTML 重建的 `published_sources` 取交集。

这与本模块原有的重要原则冲突：最终收件人实际看到的 HTML 才是 publication truth，数据库中的旧计划可能已经过期。

复现：

1. 最终 HTML 只包含 URL A；
2. `issue_radar_items` 中残留未发送的 URL B，带 `item-b/story-b`；
3. 调用 canonical `record_delivery()`；
4. `published_sources` 正确地只有 A；
5. `radar_history` 却出现了 B、`item-b` 和 `story-b`。

后果是：以后真正准备发布 B，或发布同一 story 的另一篇报道时，会被跨期去重静默删除。它不会报错，也不会给编辑者看到，因此属于 briefing integrity 的高优先级问题。

建议让身份投影只处理当前 issue 中同时存在于 canonical `published_sources` 的 Radar URL，例如在同一个事务内 JOIN `published_sources(issue_id, canonical_url)`；并增加“issue_radar 有 A/B、最终 HTML 只有 A”的回归。

## 四、应修复的问题

### P2-1 direct record 的重复项仍会被 URL dict 折叠

相关代码：`briefing_skill/publication_manifest.py:441-443`

DOM 和 manifest 已改用 `Counter`，能够发现重复 DOM；但 direct document 仍构造成：

```python
recorded = {canonical_url: item for item in document["items"]}
```

这会丢掉 direct records 的 multiplicity。

复现方式是复制一条合法的 `radar-direct.json` item，并按两个 item 重新计算合法 selection hash，manifest 和 DOM 保持一条。校验仍返回 `[]`。这违反 AGENTS 对 duplicate re-application 的要求，也没有达到文档中“direct、manifest、DOM 数量完全一致”的声明。

建议 direct records 同样使用有序列表/Counter，并分别要求：

- direct item 数量等于 selection contract final count；
- manifest item 数量等于 final count；
- DOM item 数量等于 final count；
- Radar ID 与 canonical URL 在每一层都唯一。

### P2-2 ledger 写入异常可在审计缺失时继续发布

相关代码：`briefing_skill/adapters/aihot.py:548-560`

表约束与迁移已经修好。但是 `_write_ledger()` 现在捕获所有异常，只把字符串写入 `freeze.ledger_error`，随后 collector 正常返回；collection telemetry 仍显示成功，最终 validation 也不检查 `ledger_error`。

因此数据库锁、磁盘故障、schema 损坏等问题发生时，本期仍可发布，但内部 upstream ledger 可能完全缺失。运维文档已经把这种行为写成允许降级，但它与设计的验收条件“内部 upstream ledger 完整”冲突。

建议至少把 run 标记为明确的 `DEGRADED` 并在最终 validation 中暴露；如果 ledger 是合规与来源审计的硬要求，应直接阻断发布。不能只在无人读取的 freeze 字段中记录错误，同时把采集阶段报告为成功。

### P2-3 归档普通失败已原子化，但进程崩溃恢复仍可能丢失正式目录

相关代码：`briefing_skill/archive_reader.py:616-631`

对正常 Python 异常，新实现能够恢复 backup；主审和交叉审查都确认校验失败时正式目录字节不变。这部分修复有效。

剩余风险是 `_atomic_swap_directory()` 采用固定 `.DATE.backup`：

1. 先把 target rename 为 backup；
2. 再把 temp rename 为 target；
3. 下一次调用一开始会删除已存在的 backup。

如果进程或主机在第 1、2 步之间崩溃，正式 target 不存在、backup 是唯一旧版本。历史 rewrite CLI 会因为 target 不存在而无法继续；新归档重试则可能先删除唯一 backup。

建议入口先检测并恢复 stale backup，或者使用带状态 journal 的可恢复交换协议。真正的“进程崩溃原子性”需要保证重启后不会删除唯一可恢复副本。

### P2-4 shadow run 验收仍未完成

设计文档要求默认启用前完成一期 shadow run。仓库搜索结果仍只有“建议先跑一期 shadow run”的说明，没有实际对比产物；`radar.direct_copy` 继续默认开启。

这不是单元测试错误，但它仍是上一份报告中明确未完成的发布验收项。应保存同一冻结输入下旧/新 Radar 的数量、重复率、分类覆盖、具体原始页比例、正文 provenance 结果和公开痕迹扫描结果。

### P3 文档中的 connector version 已过期

`briefing_skill/adapters/aihot.py` 的 `AIHOT_CONNECTOR_VERSION` 已是 3，`docs/operations/aihot-invisible-upstream.md:15` 仍写“当前 2”。这不会影响运行，但会误导 freeze 兼容性排障，应随下一次修复一并更新。

## 六、实现中确认有效的部分

本报告结论为 FIX，不代表提交没有价值。以下内容已经由代码、测试和最小复现确认有效：

- SQLite 会迁移旧 ledger 唯一约束，同类型多个 query lane 可留下独立审计行；
- ledger 异常不再把已采集的整批 AI Hot 内容静默清零；
- canonical `record_delivery` 已能为实际正常 Radar 保存 story/item 身份；
- lane plan 变化不会在同一 frozen run 重新联网；
- Radar 新鲜度边界正确采用配置时区；
- 公开 URL 会拒绝相对地址、上游域名和站点首页；
- 一般归档校验失败不会修改正式公开目录；
- DOM 中复制一张 Radar 卡会被数量校验发现；
- immutable HTTPS 图片和非相邻插图布局未发现回归；
- 知识层校验仍为 valid。

当前需要修补的是这些实现之间的连接方式，而不是推翻整体方案。

## 七、建议修复顺序

1. 先修 freeze 定位：记录精确 lane key，支持 daily 嵌套结构和真实 copy variant；
2. 把 direct-copy 所有 hash/contract 字段改为必填，连接 direct、manifest、DOM 的分类和日期；
3. 让 publication history 只投影最终 HTML 实际发布的 Radar；
4. 对 direct、manifest、DOM 三层分别做数量与唯一性检查；
5. 决定 ledger error 是 hard fail 还是显式 degraded，并让最终 validation 看得到；
6. 增加归档崩溃恢复协议，清理 connector version 文档不一致；
7. 把上述复现加入测试，再完成一期 shadow run。

## 八、最终判断

`161e5fc` 使上一轮多数问题从“没有实现”进入了“已有明确代码和测试”的状态，这一点是成立的；但 provenance 是发布链的硬门，它现在既会拒绝合法 daily/multi-lane 内容，又会放过缺 hash 和分类联合改写。与此同时，跨期去重会把未实际发送的 stale Radar 误记为已发布。

因此，即使 `468 passed` 全绿，当前版本仍不能判定 PASS。建议完成本报告的 3 个 P1 和 direct multiplicity 后再做第四轮复审。
