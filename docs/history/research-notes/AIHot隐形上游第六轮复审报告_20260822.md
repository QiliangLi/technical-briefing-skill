## 三、阻断问题

### P1-1：ledger 门仍未证明数据库的精确集合与内容

位置：

- `briefing_skill/publication_stage.py:143-177`
- `briefing_skill/adapters/aihot.py:45-80,301-302,603-639`

本提交已经修复：

- sidecar `{}` 会阻断；
- 其他 run 的 sidecar 会阻断；
- 截断 JSON 会转成明确 validation failure；
- DB 完全没有预期记录时会阻断；
- resume 成功/失败状态翻转和 sidecar 原子写生效。

但当前 DB 校验只执行：

```python
expected = expected_ledger_record_ids(freeze, run_id)
actual = {row["record_id"] for row in db_rows}
missing = expected - actual
```

它没有验证 `actual - expected`，也没有读取或比较每行的 provider、lane、item/story、canonical URL、title/summary hash 与 raw payload。

已复现以下状态均返回 `errors=[]`：

1. freeze 和预期 DB 行完整，但 `ledger-status.json` 完全缺失；
2. sidecar 为 `schema=999, records_attempted=-10, last_error=null`；
3. DB 中存在正确 `record_id`，但 `provider/lane_key/item_id/title/summary/hash/raw_payload` 全部错误或为空；
4. DB 除预期记录外，还存在同一 run 的额外 phantom 记录。

这不只是假想的恶意篡改。采集当前先写 DB/status，再写 freeze；若进程在两步之间退出，随后配置/lane 计划变化后恢复，同一 run 可能保留旧计划与新计划的 DB 并集。当前门只检查缺失，不检查多余，会放行 split-brain 状态。

此外，运维文档已经声明 sidecar 缺失即失败、schema 严格验证、数据库实际集合精确比对，但实现尚未达到该描述。

影响：ledger 可以“ID 看起来齐全”，但实际审计内容属于错误 provider/lane、与 freeze 文案不一致，或混入本 run 不应存在的旧记录；这仍违反 run 隔离、审计完整性和重复重放规则。

建议：

- freeze 存在时要求 sidecar 必须存在，schema 必须精确为当前支持版本；
- `records_attempted` 必须是非负整数，并与 freeze 推导出的观察记录数一致；
- 从 freeze 推导每条预期记录的完整审计投影，而不只是 ID；
- 与 DB 做双向精确集合比较，拒绝 missing 和 extras；
- 至少逐条核对 `run_id/provider/lane_key/upstream_item_id/story_id/canonical_original_url/title_hash/summary_hash/raw_payload`；
- 设计 DB/status/freeze 的 crash recovery 状态，避免三者写入顺序留下自然 split-brain。

### P1-2：DB active issue 与 issue.json 的 run/path 身份仍未闭合

位置：

- `briefing_skill/publication_stage.py:102-118`
- `briefing_skill/publication_manifest.py:478-510`

本提交已把 DB `issues.date_to` 加入外部锚点，并能阻断：

- DB 日期与 `issue.json.date_to` 不一致；
- `issue.json` 缺日期；
- manifest 缺 run ID；
- 配置时区不可读或不一致。

但生产入口只从 DB 查询 `run_id,date_to`，没有查询 `id,issue_json_path`；provenance 校验从硬编码路径读取 `issue.json` 后也只使用 `date_to`，不检查 JSON 内的 `run_id/id`。

最小复现：

1. DB、direct、manifest、freeze 均属于 `run-chain`；
2. 把 `workspace/runs/run-chain/issue/issue.json` 的 `run_id` 改为 `run-other`；
3. 保持相同 `date_to`；
4. 传入 DB-backed active issue 后，完整 provenance 校验仍返回 `[]`。

影响：同日期的外来或错误 issue JSON 可以通过 active-run 校验；DB 中记录的 `issue_json_path` 也没有证明实际读取的是同一个文件。

建议：

- DB 查询同时读取 `id,run_id,date_to,issue_json_path`；
- 使用 DB 的 `issue_json_path` 解析并校验实际路径，拒绝越出 active run 目录或与当前读取路径不一致；
- 强制比较 DB、issue JSON、manifest 三者的 issue ID；
- 强制比较 DB、issue JSON、direct、manifest、freeze 的 run ID；
- 日期、路径、ID 任一缺失都 fail closed。
