## 三、阻断问题

### P1-1：空 Radar 状态的 provenance 校验仍然 fail-open

位置：`briefing_skill/publication_manifest.py:524-542`

当前层间一致性只在 `len(direct_items)` 为真时比较，最终数量也只在 `final_count` 为真时比较：

```python
if len(direct_items) and (...):
    ...
if final_count and len(dom_items) != final_count:
    ...
```

最小复现：

1. 生成合法的空 direct 文档：`items=[]`、`final_count=0`；
2. 向 publication manifest 和最终 DOM 同步注入一条 Radar；
3. 该条目不在 direct，也没有 freeze 来源；
4. `publication_provenance_errors(...)` 返回 `[]`。

同一缺口还允许清空原本非空的 direct items、重算 direct selection hash，并让 manifest/DOM 保留原卡片。删除 `manifest.radar_contract.selection_hash` 也不会失败，因为 `publication_manifest.py:518-521` 明确把 `None` 视为可接受值。

影响：最终网页可以出现没有经过冻结输入、选择和 direct provenance 的 Radar，发布门仍放行。

建议：

- 无条件比较 direct、manifest、DOM 三层 `Counter`，包括三层之一为空的情况；
- 无条件比较三层数量与显式存在的 `final_count`，零值不能跳过；
- `manifest.radar_contract.selection_hash` 必填且必须精确等于 direct；
- `selection_contract` 应只接受 direct 的合同，不能在 direct 缺失时回退到 manifest 的自述。

### P1-2：active run 没有外部锚点，旧 run 整套产物可跨 run 重放

位置：

- `briefing_skill/publication_manifest.py:444-478`
- `briefing_skill/radar_direct.py:680-705`
- `briefing_skill/radar_direct.py:825-839`

最小复现：

1. 为 run A 生成一套可通过校验的 freeze、`radar-direct.json`、publication manifest 和 HTML；
2. 把 run A 目录完整复制到 run B 路径；
3. 以 `run_id="run-B"` 调用最终 provenance 校验；
4. direct 与 manifest 文件内部仍声明 run A，但校验返回 `[]`。

selection hash 目前只保证一组文件内部自洽；validator 没有核对：

- direct 的 `run_id` 是否等于调用方的 active run；
- manifest 和 freeze 的 `run_id` 是否等于 active run；
- `reference_date` 是否等于 active issue 的 `date_to`；
- `timezone` 是否等于当前 run 的配置时区。

影响：旧 run 产物或复制到错误目录的 sidecar 可以被当前 run 接受，既是跨 run 数据泄漏，也是报告日期完整性问题。

建议：将 active run ID、active issue 日期和当前配置时区作为校验器的外部可信输入，逐层与 freeze、direct、manifest 比较；不能只校验文档彼此自洽。

### P1-3：恢复路径上的 ledger 状态既可能漏报，也可能永久残留

位置：`briefing_skill/adapters/aihot.py:479-493,556-566`

首次收集时，ledger 写失败会把 `_ledger_error` 写入新 freeze，最终发布门能阻断，这是本提交已经修复的主路径。但恢复路径存在两个相反的问题：

1. 已有健康 freeze 的 resume 中，若本次 ledger 重放失败，`_write_freeze()` 因 `_frozen_lanes is not None` 直接返回，新错误只留在内存，磁盘 freeze 仍是 `ledger_error=null`，发布门看不到失败；
2. 首次失败已把 `ledger_error` 写入 freeze 后，resume 若 ledger 写成功，`_write_freeze()` 同样直接返回，旧错误无法清除，后续发布会一直被阻断。

影响：resume 可能在审计 ledger 实际缺失时继续发布，也可能在 ledger 已修复后永远无法恢复；这违反 advance/resume 的幂等要求。

建议：冻结响应内容与 ledger 写入状态分离。保留不可变的响应 freeze，同时用可原子更新的状态块或 sidecar 记录每次 ledger 尝试；成功时应先核对预期记录已经存在，再把错误标记为 resolved。最终门应同时检查最新状态和 DB 完整性。

### P1-4：正文 Deep 来源可替 stale Radar 身份进入发送历史

位置：`briefing_skill/publication_history.py:242-251`

普通的“最终 HTML 只有 URL A、stale Radar 为 URL B”已经修复。但新 JOIN 只按 `issue_id + canonical_url` 匹配 `published_sources`，没有限定来源所在 section。

最小复现：stale `issue_radar_items` 的 URL 只在最终正文 `deep-card` 中出现，并未成为 Radar 卡；发送后，该 stale Radar 的 `upstream_item_id/story_id` 仍被写入 `radar_history`。

影响：后续真正的对应 Radar story/item 可能被跨期去重静默删除。通用 URL 去重可以保留，但不应把没有实际发送的 Radar 身份附着到正文来源上。

建议：身份投影至少限定 `published_sources.section='radar-item'`；更稳妥的是从最终 DOM/manifest 的 Radar 集合生成明确的已发布 Radar URL，再据此写 item/story 身份。

## 四、非阻断但应修复的问题

### P2-1：`radar_id`、公开来源名称和规则版本没有完整进入跨层契约

- `publication_manifest.py:506-514` 构造 `manifest_records` 时丢弃 `radar_id`，因此 direct 与 manifest 的 ID 不一致仍可通过；
- DOM 的公开来源名称没有与 direct/manifest 绑定，单独篡改页面上的站点名称不会报错；
- `radar_direct.py:680-688` 重算 selection hash 时使用当前代码常量，而不是 direct 文档持久化的版本字段；connector version 也未写入 direct 文档。把已记录规则版本改为 `999`，原 selection hash 仍可通过。未来常量升级时，未改动的旧 run 又可能被新常量反向误杀。

建议：让 connector/direct/taxonomy/policy 版本全部成为持久化且受支持范围校验的字段；selection hash 应绑定持久化值。三层同时绑定 `radar_id` 和公开 `source_name`。

### P2-2：多个历史归档备份时可能恢复较旧副本并删除较新副本

位置：`briefing_skill/archive_reader.py:616-634`

恢复代码对 `.backup-PID-TIMESTAMP` 路径做字符串排序后取最后一个。该顺序优先受 PID 影响，并不等于时间顺序。构造较旧的 `.backup-9999-100` 和较新的 `.backup-1000-200` 后，会恢复旧副本并删除新副本。

建议：解析文件名末尾时间戳或使用可靠的文件元数据选择最新候选；恢复并校验成功前不要删除其他备份。

### P2-3：shadow run 仍没有验收产物

仓库中仍只有 shadow run 的设计与建议，没有“同一冻结输入下，旧 Radar 与 direct-copy Radar 的差异报告、阈值和签收结果”。`config/scoring.yaml` 中 `direct_copy` 仍默认开启。

这不等同于代码错误，但设计文档要求的上线前验收尚未闭环。建议保存一次可重复的 shadow 对比产物，并明确允许差异及上线签收结论。

## 五、低优先级观察

### P3-1：“具体原始页”仍是路径启发式，而非页面身份判断

位置：`briefing_skill/radar_direct.py:291-301`

当前规则把 path 为空的所有 URL 都判为站点首页，把 path 非空的 URL 都视为具体页。因此 `https://example.com/?p=123` 这类合法的 query 路由文章会被拒绝，而 `https://example.com/news` 这类频道页会被接受。

该问题不直接构成 provenance 绕过，但会造成合法来源误删或聚合页误收。建议至少把 query 中稳定的内容 ID 纳入判断，并对常见频道/列表路径做显式识别；更可靠的方案是在采集阶段保存 upstream 提供的 original-page 类型或解析后的 canonical 元数据。

### P3-2：测试文件末尾有多余空行

`git diff --check 161e5fc..982bf83` 仅报告 `tests/test_radar_direct.py` 文件末尾多余空行，不影响运行。
