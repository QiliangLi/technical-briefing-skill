# briefing-run 运行可视性优化（未命名泳道与进度可读性）

- Status: implemented
- Created: 2026-10-31
- Last updated: 2026-10-31

## Problem and evidence

用户在最近几期 workflow 运行（最近一次 2026-10-29，`dwfrun-fc199848`：26 波、约 116 个子代理、570 步、4h16m）中反馈两点：

1. **仍有「未命名 Agent」**。排查结论：运行期所有子代理实际都有名字——10-29 运行日志中 117 个 dwf actor 会话全部由 `uniqueName()` 命名，工具调用统计（submit_result/Read/Bash/Write/Edit 等）证实没有嵌套 Agent 再开子代理的情况；`GetWorkflowRun` 的子代理列表也全部带名。未命名条目来自**运行图的泳道标签**：桌面端泳道标签由「脚本静态投影出的 name/namePattern」决定（UI 常量 `chat.toolCall.workflow.graph.lane.anonymous` =「未命名子代理」；namePattern 无法解析时回退匿名，图上限 32 泳道/64 参与者，超出显示「图过大，部分参与者已省略」）。`briefing-run.dwf.ts` 三处 `agent()` 的名字都是**运行期变量**（`waveNames[i]`、`repairNames[i]`），静态分析拿不到任何字面片段，泳道头只能显示匿名——尽管泳道内每次派发都有名字。
2. **已命名的子代理一下弹出一百多个，看不出当前进度**。现有三个展示面都以「波/任务」这种机制粒度呈现：阶段图整体一个循环只占一个节点（26 轮都在里面，不区分流水线阶段）；波次看板 26–52 张卡，标题是「第 N 波·K 个任务」这类机械编号（dynamic-workflows 技能 §9 明确把机制编号列为反模式）；子代理流是 ~116 张平铺卡片，无分组，重新打开面板或断线恢复时整批渲染像「一下涌出」。没有任何一面直接回答「现在跑到流水线哪一步、完成了多少、还剩多少」。

## Goals and non-goals

目标：

- 运行图中不再出现「未命名子代理」泳道（子代理名以模板字面量形式内联到 `agent()` 调用点，符合技能文档认可的 fan-out 命名惯用法 `agent(\`judge-${i.id}\`)`）。
- 打开运行页第一眼能看到：当前流水线阶段（筛选候选→提取事实→…→生成插画）、累计进度（已完成/总数）、并行批次上下文。
- 波次卡片与日志行从「机制编号」改为「阶段直述」，与子代理的功能直述命名体系一致。
- 命名保持跨修订缓存兼容（AmendWorkflow 按名导入，首个占用者保留原名）。

非目标：

- 不改流水线任务粒度（每任务全新子代理上下文是 workflow 的核心价值；evidence 隔离不变）。
- 不改发送/归档边界、任务图、Schema、advance 语义。
- 不改桌面端 UI 本身（平铺子代理流的渲染行为、32 泳道/64 参与者上限属宿主，脚本只能改变自己产出的内容）。

## Constraints and invariants

- 单次运行 report 上限 256 条：新看板 + 进度总览的总 report 量必须计入预算（见下方测算）。
- 子代理名运行内唯一（重名直接终止运行）；所有命名必须继续经 `uniqueName()` 语义去重。
- 名字跨修订稳定：`AmendWorkflow` 缓存按「子代理名 + 逐字相同指令」命中，改名会让已完成的波次重跑；本期改动发生在下一期新运行前，无存量缓存可损失。
- 阶段（phase）是编译期字面量，不能按运行期 stage 动态生成节点；阶段进度只能由 board/log 承载。
- 脚本解析函数与现网格式耦合的三处契约不变（canonical 执行卡、`tasks list` 行、advance/render JSON）。

## Proposed design

四处脚本改动，全部在 `.zcode/workflows/briefing-run.dwf.ts`：

1. **子代理名内联为模板字面量**（修未命名泳道）。三处调用点改为在 `agent(...)` 参数位置直接写模板字面量，去重后缀预计算进插值变量：

   ```ts
   // 去重结果预先算进 label（如 subject 追加「·之N」），调用点只留模板
   agent(`${labels[i].role}·${labels[i].subject}·第${waves}波`)
   agent(`修复输出·${ROLE[row.task_type] ?? "执行编辑"}·${row.task_id.slice(0, 6)}`)
   agent(`终审修复·第${attempt}次`)
   ```

   模板中的字面片段（`·`、`第`、`波` 等）给静态分析留下可建 pattern 的素材；若分析器看不穿插值表达式，泳道头仍是匿名——这一点在下次 `CreateWorkflow` 确认对话框（确认时即绘制阶段图）零成本目检，若未生效则接受现状并在运维文档记录，进度可读性不依赖泳道头。修复代理名从「第N波·修复输出·id前8位」改为「修复输出·功能·id前6位」，去掉打头的机械编号且带上功能标签（`row.task_type` 现成可用）。

2. **阶段看板替换波次看板**。`artifact.board("tasks", ...)` 改为按**流水线阶段**出卡：固定阶段序（开放搜索/筛选候选/提取事实/补齐证据/撰写条目/核查事实/读者润稿/汇总判断/生成插画），每阶段一张卡，列 = 未开始（初始不出现）→ 执行中 → 完成。状态判定用每波已取的 `tasks list` PENDING 行：某 task_type 出现在当前波或 PENDING 中即「执行中」，曾经出现且已从 PENDING 消失即「完成」（INVALID reopen 会让它回到执行中，规则自洽）。卡面 note 记「第 N 波起·累计 X 批」，波内任务明细留在日志行。26 波的一期约 9–11 张卡 + 约 30 次状态更新，远小于现在 52 条的占用。

3. **进度总览卡**。新增小看板 `progress`，单张固定 key 的卡，每波 advance 后原位更新标题：`当前：提取事实·第 8 波｜完成 62/151｜待办 23｜INVALID 累计 9`。累计值由脚本对每次 advance 的 applied/invalid 求和、总数取首波 applied+pending+invalid 基线；这是回答「当前进度是什么」的第一入口，每波 1 次 report。

4. **日志行阶段直述**。波日志从「第 8 波（并行 6/23 待办）：…」改为「提取事实·第 8 批（并行 6/23）：…；进度 62/151」——阶段名取该波任务的主类型（混合波取队列最靠前任务的类型），与子代理命名同一套功能直述词汇。

report 预算测算（按 10-27/10-29 两期上限形态：30 波、12 轮 INVALID 修复）：阶段看板 ≈ 45 条 + 进度总览 ≈ 30 条 + 现有 INVALID/校验流程内嵌 log 不变，合计 < 100 条，加上保留的收尾产物发布，距 256 上限余量充足。若未来波数显著增长，进度总览可降频为「阶段切换 + 每 5 波」。

## Compatibility and migration

- 存量运行不受影响；改动只影响下一次新起/续跑的运行展示。子代理名形状不变（`功能·对象·第N波[·之N]`），仅修复/终审两类名字换了拼法——对旧运行的 Amend 缓存本就按旧名匹配，不混用。
- `docs/operations/zcode-workflow-run.md`「进度观察」节随实现同步改写（波次看板→阶段看板+进度总览；泳道标签的已知行为与目检方法）。
- 阶段判定完全复用每波已有的 `tasks list` 输出，不新增 `world.run` 调用，不读任务输入以外的东西。

## Failure, recovery, and rollback

- 阶段卡状态误判（如 PENDING 顺序变化导致阶段短暂回跳）只影响展示，不影响任务执行；卡随下一次 advance 自愈。
- 进度基线异常（首波 advance JSON 缺字段）时总览卡退化为只显示「当前阶段·第 N 波」，不阻塞主循环；所有新增展示代码包在 try/catch 或默认值里，展示失败不允许终止运行。
- 回滚 = 还原脚本文件后按普通脚本缺陷流程 `AmendWorkflow`；无状态迁移。

## Verification

- `EvalWorkflowSnippet` 以 10-29 期真实卡片样本回归：新命名拼法、阶段判定函数、累计进度计算、模板字面量编译（strict tsc）。
- 下次例行运行三级目检：(a) `CreateWorkflow` 确认对话框里泳道头是否已非「未命名子代理」；(b) 前 3 波的阶段看板/进度总览/日志是否符合预期形状；(c) 结束后 `GetWorkflowRun` 复核 report 用量与看板内容。
- 对照观察：同一期 26–30 波下，打开运行页 10 秒内能否说出「当前阶段 + 完成比例」。
