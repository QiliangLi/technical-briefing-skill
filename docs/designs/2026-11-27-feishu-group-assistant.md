## Problem and evidence

两个缺口，可以在同一个群里一起补：

1. **Idea 价值不可衡量。** `evidence_for` / `evidence_against` 是 AI 对已发布证据的机器分类，不是人类反馈。51 个正式 Idea（28 seed / 22 observing / 1 ready_for_validation）没有一条经过同事评价；「表述抽象、看不懂」是用户已两次提出的问题。
2. **讨论与沉淀脱节。** 日报库有 35 期 777 条条目和 478 条雷达题录，知识库有 51 个 Idea、11 条 Roadmap，全部已公开、可链接。但群里讨论一个方向时没人会想起去查，讨论本身也不留记录。

用户 2026-11-27 的方向：把部门同事拉进一个飞书群，大家讨论 idea 时助手主动理解讨论、检索历史日报与 idea 库、推荐相关条目，参照 DeepSeek 的 Super-agent。

用户 2026-11-28 补充：语义判断不接模型 API，也不用 `codex` 或 `claude`。要像现在跑简报一样，开一个 ZCode 会话，让会话里的 agent 来盯着群消息。这与仓库的既有架构一致：`docs/architecture.md` 写明实现不绑定模型 API，由宿主执行任务文件。

**与 DeepSeek Super-agent 的关系。** 这一部分在 2026-11-27 至 28 对照原始材料重新核对过。更早的版本依据的是媒体转述，出处混杂，另有一处引用有误导。原始材料有三份：

- DeepSeek Harness 团队的文章《Super-agent 设计探索：迈向更自主的 Agent 系统》，2026-10-31 发表在 DeepSeek 的官方知乎账号。它是一篇架构文章，开头就注明不是对 DeepSeek Harness 产品功能的介绍。
- 开源研究原型 `deepseek-ai/dsh-superagent-prototype`，MIT 许可。文章作者注明「部分设计已在原型中实现」。原型 README 注明公开代码与文章描述不完全一致，文章里有些设计只是方向。
- `deepseek-ai/deepseek-harness`。Super-agent 是跑在它上面的一个插件，与本设计的关系见下文「运行时」。

从文章借的：

- 事件过滤分两级。程序层按来源、群组范围、用户或机器人名单做确定性准入，模型只处理通过准入的候选。文章没有量化程序层滤掉了多少消息；它实验用的合成负载是约 300 条消息里约 20 条工作请求，那是负载的构成，不是过滤的效果。
- 常驻的 Router 层只做交互和分派，不执行具体任务，可以用较轻的模型，部分逻辑不必调用模型。
- 同一 IM 话题下的连续事件是一条 Thread。后续事件直接送达已经订阅这条 Thread 的一方，不必重新判断。
- 给模型的上下文从最少开始，按需内联紧邻的信息：消息前后相邻的消息、它所回复的消息。长内容留在窗口外，保留续读入口。文章的原话是「浪费上下文窗口，就是浪费模型的智能」。
- 提前在后台尝试，结果有价值就交付，没有价值就丢弃。
- IM 信道的规范：只在需要决策或验收时发通知，只问直接问题、给简短结论。文章说实测有效的一条硬规定是单次回复不超过 100 词。
- 安全与隐私是文章自己列出的开放问题。事件驱动增加了接触不可信输入的风险，解决不好就「只有在一个很小且可信的范围才能工作」。

从原型文档借的：

- 行动准则：只在被请求、或有书面规则允许时行动；只在人必须行动或能用上结果时才说话。
- 准入表：按「是否在名单上」和「是否点名了助手」，把每条消息判为明确请求、推断候选或不处理，由程序裁决。
- 接受模式三档：off、observe、auto，默认 observe。观察模式下主动类候选照样研判，但只记下「本会接受」，不执行；人工看过记录再切到 auto。它是全局开关，不按规则；明确请求在每种模式下都照常处理。
- 每次研判对每条启用的规则各给一次结论，主动接受至少要有一条规则命中。每条授权记录它所依据的策略版本。
- 消息、评论和被引用的文档只是研判的输入，不能改变权限。
- IM 回复规范：默认一句话，只说结果、链接和必要的下一步。发送前对每个分句自问，删掉它会不会让人看不懂结果或没法行动，不会就删。

从原型代码核对过的。核对方式是通读原型的全部文档和源码，逐条给出文件与行号，再对其中的出处抽查原文：

- 准入分两层，都先于模型。「准入」由程序按发送者、是否点名、所属范围和接受模式判定，从不读消息正文；全部不准入时直接记为忽略，不调用模型。「研判」才交给模型。
- 接受模式定义为 off、observe、auto，默认 observe。观察模式下，肯定的研判被改写成「忽略」，同时记下 `would_accept` 和它的提议。
- `Engine` 是状态的唯一写入者，每个命令包在一个事务里。`Outbox.send` 把回执和待发的回复放在同一个事务里，提交后才发送。
- 飞书接入用的就是 `lark-cli`：启动 `lark-cli event consume im.message.receive_v1 --as bot`，每 60 秒补一次群历史，再轮询已订阅的话题。三种入口对同一条消息算出相同的键。线程号是群 ID 加根消息 ID。出站消息一律回复在触发消息的话题里。
- 回复的种类由程序把关：结果类回复要求对应的工作已就绪，进度类回复永不送达。
- 出站的 IM 消息有 100 词的硬上限，由程序计数，超了直接报错。
- 安装时要求 `lark-cli` 只允许 bot 身份，否则拒绝。

文章里有、公开的原型里没有的：Inline 与 Spill、链式召回、Watchdog、云端存算分离、异步全双工。原型里最接近的只有「截断并保留读指针」和有界的讨论窗口。原型 README 对此有说明。

原型里有、本设计不采用的：

- 主会话可以用工具改写名单、规则和接受模式，只靠提示词约束。本设计只认本机 CLI。
- 执行器带着完整工具并以完全访问权限运行。本设计的会话只经任务文件进出，不直接调用 `lark-cli`。
- 默认提示词和规则以 GitHub 和 PR 为中心，安装时强依赖一个 GitHub 仓库。

本设计自己加的、原型里没有对应机制的：成形闸门里的发言上限和工作时间；离线评测集和影子期的「该说」比例；会话只在有任务时被叫醒。

不借的部分：

- Worker 执行有副作用的任务，例如复现缺陷、提交 PR。本助手的「工作」只有检索与回复，不写代码、不发邮件、不改仓库。
- 多个 Worker 并发、云端存算分离和端侧守护进程。本助手的一次工作是一次检索加一条回复，先在本机跑。

**本机与语料实测（2026-11-27）。**

lark-cli：最初用 1.0.60 冒烟，2026-11-27 已升级到 1.0.100 并重新冒烟。

- bot 身份 ready。你的用户授权 2026-10-18 过期，2026-11-28 重新办好，12-05 失效。助手全程走 bot；用户身份只给实传端到端的脚本用。
- `im.message.receive_v1` 仅 bot 身份。`lark-cli event consume` 对它输出扁平化事件：`.content` 已转成纯文本，`sender_id` 只有 open_id。
- `lark-cli auth check` 不可信，两个方向都错过：它报缺的细分 scope 没有挡住单聊事件和群内点名事件，它报已授予的 `im:chat.members:read` 在真实调用里被拒。应用权限的权威状态是官方的「查询租户授权状态」接口（`GET /open-apis/application/v6/scopes`，bot 身份可调，不需要额外权限）。

冒烟实测（2026-11-27）。单聊指 bot 与应用所有者的单聊，测试群指只含应用所有者与机器人的普通群。

- 长连接可用：收消息、表情增删、卡片回调三类事件都能订阅，有界监听到时自行退出。卡片回调最初启动即失败，原因是后台未订阅；应用所有者订阅后恢复。
- 发送（单聊与测试群）：文本、带四个按钮的交互卡片、`--reply-in-thread` 话题内回复都成功。幂等有效：同一个 idempotency key 发了 3 次，历史里只有一条消息。
- 事件送达：单聊消息事件约 0.3 秒。开通 `im:message.group_msg` 之前，群里只有 @机器人 的消息会送达，约 0.34 秒，一条不带 @ 的群消息在监听运行期间发出，没有送达。开通之后，不带 @ 的群消息约 0.33 秒送达，不带 @ 的话题回复约 0.26 秒送达。
- 断线补送：两条在没有监听时发出的单聊消息，在重新连上后被补送，最晚一条隔了约 5 分钟。补送窗口有多长没有测。
- 表情：新增与删除事件毫秒级送达，人类操作者的事件带 open_id。`reactions list` 返回操作者 ID、操作者类型、表情类型和时间。机器人可以给自己的消息加和撤表情。
- 卡片按钮回调：带操作者 open_id、按钮上定义的结构化值、卡片原文和延时更新 token。
- 线程归并：按消息 ID 补查详情能拿到 `root_id` / `parent_id` / `thread_id` 和结构化的 `mentions`，用户在单聊话题里的回复也验证过。
- 读取边界（开通 `im:message.group_msg` 之前）：单聊的历史和话题列表可读。群里只能按消息 ID 点查，群历史、话题列表、成员列表都被拒。
- 读群消息的权限已对照官方文档确认：应用身份读群聊消息必须开通 `im:message.group_msg`（获取群组中所有消息）。lark-cli 的读群历史命令在源码里声明的也是它。官方把它标为敏感权限。
- 应用的权限现状：原有 195 项，租户全部已授权，`im:message.group_msg` 从来没加过。2026-11-27 应用所有者在官方申请页确认后，清单新增 6 项并即时生效，没有走管理员审批：`im:message.group_msg`，以及页面一并加上的 `im:message.urgent`、`im:message.urgent:phone`、`im:message.urgent:sms`、`im:message:recall`、`search:message`。后五项助手用不到。
- 开通后的复测：bot 能读群历史（含不带 @ 的消息和系统消息），读历史时自带表情明细；能按根消息读整条话题，批量查询时也会展开话题回复；群成员列表可读并带姓名。
- 以你的身份发言（2026-11-28 验证）：你的用户授权重新办好后，`lark-cli --as user` 在测试群里发了普通消息、话题回复和点名机器人的消息，三条都在约 0.22 到 0.33 秒内作为真实事件送达机器人。事件里的发送者类型是 `user`，点名和话题字段齐全。实传端到端据此以你的身份来驱动。
- 你的用户授权 7 天后过期，两次实测都一样：10-11 授权、10-18 失效；11-28 授权、12-05 失效。官方文档的示例里刷新令牌约 30 天。11-28 这次只申请了八项必需权限，飞书返回的授权里有 161 项，是以前授权的累计。
- lark-cli 的默认身份原本是 `auto`，会跟着可用的登录态变：你的授权失效时默认是 bot，恢复后默认变成 user，不带 `--as` 的命令就以你的身份执行。2026-11-28 已把默认身份改成 `bot`。
- 开通权限没有接口可调，只能在开发者后台操作。lark-cli 1.0.100 在权限未开通的报错里会给出官方申请页的链接，格式是 `https://open.feishu.cn/page/scope-apply?clientID=<应用 ID>&scopes=<scope>`，权限已预填，需要应用开发者本人在已登录的浏览器里确认，这一步已由你完成。ZCode 内置浏览器里飞书登录页渲染不出来，不能代劳。
- 权限加上之后如果尚未授权，可以用「向管理员申请授权」接口（`POST /open-apis/application/v6/scopes/apply`，bot 身份，不需要额外权限）发起申请。它不接受权限列表，只申请应用内已开通而未授权的权限；剩余未授权的权限属于高敏权限时会拒绝（212001）。
- 以用户身份读群消息需要 `im:message.group_msg:get_as_user`，这个应用已经开通，在应用所有者的用户授权清单里。应用开发者可以用自己的登录态免审调试需审核权限。该登录态已于 2026-10-18 过期；上次登录态 7 天后失效，事件订阅也只支持 bot 身份，所以用户身份只适合人工读取，不适合常驻。

- 升级 lark-cli 不改变读群消息的结果：1.0.60 与 1.0.100 读群历史时发出的请求完全相同，声明所需的 scope 也相同，拦截发生在服务端；升级后复测，读群历史仍返回 230027。升级带来的相关改动：1.0.69 起收消息事件带线程字段；1.0.64 起权限未开通的报错链接改为官方申请入口；1.0.85 起加固了令牌刷新。应用配置和登录态存放在 `~/.lark-cli/`，升级没有影响到，读路径回归通过。
- 官方要求消息事件按 `message_id` 去重，不要依赖 `event_id`。
- bot 身份用 `contact +get-user` 解析用户只返回 open_id 与 union_id，没有姓名；群成员列表接口带姓名。
- 仍未实测：话题群模式；部门同事（非应用所有者）的消息；已有话题里后续回复的事件是否带 `thread_id`。

仓库与语料：

- 仓库与站点是 PUBLIC，`archive/`、`knowledge/` 直接发布到 GitHub Pages。任何群聊内容进入会被提交的路径都会公开。
- `docs/architecture.md` 规定实现不绑定模型 API、由宿主执行任务文件。仓库里没有检索索引、没有嵌入或全文检索代码；唯一的密钥是生图用的 `workspace/secrets/image_api.json`，走第三方中转，不适合承载内部群聊。本机装有 `codex` 与 `claude` CLI，本设计不用它们。
- 可索引文本的质量高：每条日报条目已有中文 `core_conclusion`、`mechanism`、`keywords` 和事实核查状态，Idea 有 `title` / `problem` / `hypothesis`。venv 的 SQLite 3.53.4 支持 FTS5。
- 一次只读探针（828 篇 = 777 条目 + 51 Idea，英文按词、中文二元字组的 BM25；6 条自拟口语化问题，按标题判断相关性）：纯词法检索在 5 条问题上把相关条目送进前三，其中一条精确命中原 Idea。漏掉的一条是「多智能体上下文超长怎么压缩」：语料里有 3 篇上下文压缩的条目，被查询里的「多智能体」盖住了。样本只有 6 条，出题人知道语料，不能当评测结论；只说明两点——检索骨架不必依赖模型，而查询改写需要。

## Goals and non-goals

目标：

1. **回答**：群里点名助手提问，必答；答不出就明说。
2. **主动推荐**：大家讨论一个方向时，助手判断日报库或 idea 库帮得上忙才在话题里接一句，帮不上就沉默。
3. **Idea 反馈**：每周推送少量通俗化的 idea 卡片，同事一次点按即可评价，讨论留在卡片的话题里。
4. **可衡量**：提问量、推荐的有用率、每个 idea 的评价与讨论量都进本地台账。
5. **可试、可退**：主动能力先影子运行，随时一键静音，关闭后不留残余。

非目标：

- 不执行有副作用的任务（写代码、发邮件、改仓库、建文档）。
- 不把群聊内容或讨论中产生的新想法写进本仓库。「自动沉淀群聊 idea」不在范围内，原因见约束 2。
- 不改动简报流水线、任务队列和证据边界。助手是流水线之外的独立子系统。
- 不公开发布匿名聚合数据。

## Constraints and invariants

1. **只读公开库。** 助手对 `archive/` 与 `knowledge/` 只读。索引只从已发布文件构建，不读候选池、全文缓存或运行目录。助手推荐的每一条都是已经公开的条目。
2. **公开仓库红线。** 助手的全部状态只写入 gitignore 的 `workspace/assistant/`。实现时加测试，用 `git check-ignore` 断言每个状态路径，并断言助手模块不向该目录之外写文件。
3. **只在被请求或规则允许时发言。** 回答由用户用 CLI 显式开启，开启记录带时间。主动推荐默认关闭，经 observe 模式运行后由用户开启。Idea 卡片推送沿用 `--confirm-send`。平台不再过滤不带 @ 的消息，这层过滤由准入表负责，默认开启。
4. **会话只提议，程序裁决。** 状态只由确定性核心写入。会话只经任务文件进出，它的输出要过 Schema 校验才会被采纳。回复里引用的条目必须同时存在于当前索引快照和交给会话的候选集。标题、日期、结论、链接由程序从索引生成，不采信会话输出里的任何 URL。会话写的「对应你们说的那句话」和研判引用的原文片段必须是原消息的子串，由程序校验。
5. **外部文本永远是数据。** 群消息只作为待分析内容进入提示词，其中的指令不执行。准入只读消息的元数据，不读正文。群消息不能触发任何命令；静音、切换模式、改规则、改准入表只认本机 CLI。
6. **沉默优先。** 主动推荐的任何一道闸门不过就不发言，并在决策日志里写明停在哪一道。
7. **先落库再发送。** 每条外发消息先写 Outbox，再调用 lark-cli，带幂等键。
8. **隐私最小化。** 送给会话的只有白名单群里当前讨论窗口的文本：至多 20 条、每条截断到 400 字符、发送者替换为「同事 A / B」。原始事件本地保留 30 天，之后只留哈希和统计。
9. **助手只能以 bot 身份调用 lark-cli。** 所有调用显式带 `--as bot`，并经过一个只放行 bot 身份的包装脚本。以你的身份发消息的只有一个地方：实传端到端的脚本。它不属于助手进程，写死测试群的 ID，消息带 `[E2E]` 前缀。lark-cli 的默认身份已设为 `bot`，这样忘写身份的命令只会以机器人身份执行，不会以你的名义做事。包装脚本仍然每条都显式带 `--as bot`。

## Proposed design

### 总览

```text
飞书群（部门）
  │ 长连接事件：lark-cli event consume × 4（消息 / 表情增 / 表情删 / 卡片回调）＋ 定期补历史
  ▼
群助手进程（确定性核心；试用期由 ZCode 会话作为后台任务拉起）
  ├─ Source（程序）：丢掉自己的消息和白名单外的群，去重，归并到话题，记下去向
  ├─ 准入（程序）：准入表 ＋ 接受模式 → 明确请求 / 推断候选 / 不处理
  ├─ 词法召回（程序）：BM25 over 日报条目 / 雷达题录 / Idea / Roadmap
  ├─ 有把握就直接回；没把握，或需要研判要不要接话时，排一个语义任务
  ├─ 校验与组装（程序）：引用 ⊆ 索引快照；链接由程序生成；回复种类由程序把关
  ├─ Outbox：先落库，再话题内回复
  └─ 本地台账：事件、去向、决策日志、反馈
        │ 有语义任务时叫醒
        ▼
ZCode 会话（专用会话）：执行语义任务，把结果写回任务文件，不直接调用 lark-cli
        ▲ 只读
  archive/（35 期）＋ knowledge/（Idea / Roadmap）→ 检索索引
```

词汇沿用 Super-agent 原型：Source 是消息入口，Trigger 是一条不可变的消息事件，Thread 是一个话题。本设计用「讨论」指代 Thread。

### 运行时

不采用 DeepSeek Harness 作为运行时，继续用自写的小进程。2026-11-27 对照 `deepseek-ai/deepseek-harness` master 4b399c3 的文档核对过，依据如下：

- Harness 的核心没有入站的 IM 通道。官方的飞书插件只是把 `lark-cli` 的路径交给模型，让它经 Shell 工具调用。入站这部分不管选哪条路都要自己写。
- 它是给编码智能体用的运行时，和本设计的硬约束相反。它自带的最小预设仍然带着常驻 Shell；文档写明「预设不是安全沙箱」，沙箱只管文件写入。
- 走官方模型路由时，默认会上传完整的会话日志（`dsh_session_log` 默认开启）。群聊内容会进去。它可以关掉，但默认值不对。
- 它处于开发者预览阶段。README 写明会有破坏兼容的变更，npm 上只有预发布版本。
- 它的安全声明写明没有经过安全审计，不能当作安全或生产可用的软件。

从 Harness 借三点：「模型看得到的都要先落日志」；凭据在配置里只放引用；对能力的限制只能收紧，不能放开。

Super-agent 原型把研判交给一个常驻的模型会话。本设计也把研判交给一个 agent 会话，用的是 ZCode 的会话，并且只在有任务时才叫醒它。

### 常驻进程与事件接入

- 试用期里，进程由一个专用的 ZCode 会话作为后台任务拉起，会话结束时一起结束。要脱离会话常驻时再改用 launchd。
- 会话的循环只有四步：挂起等待、执行任务、apply、再挂起等待。等待用的是阻塞命令 `assistant tasks wait`，有语义任务时返回。命令返回时会话被自动唤起，空闲时不消耗 token。这个机制在 2026-11-27 的冒烟里验证过，当时的飞书监听就是这样唤起会话的。
- 会话要用不弹确认的权限模式打开，并且不能是跑简报定时任务的那个会话。本机没有 ZCode 的命令行可以在不开会话的情况下调用，所以开着的会话是语义层的唯一入口。
- `briefing.py assistant serve` 是唯一的常驻进程。它按「一个 EventKey 一个子进程」拉起 `lark-cli event consume`，读取 stdout 的 NDJSON。Super-agent 原型也是这样调用 `lark-cli` 的。
- 子进程以 stdin、stdout、stderr 三路管道启动。监督进程为每个子进程保持 stdin 打开，因为无界 consume 遇到 stdin EOF 会自行退出。就绪以 stderr 的 `[event] ready` 为准。
- 子进程退出后 1 秒重启，连续失败时退避到最多 60 秒；45 秒内没有就绪就结束它并报错。`missing_scope` 这类鉴权错误不重试，直接在 `status` 里报出。
- 停止时先关 stdin，再发 SIGTERM，不用 `kill -9`，否则会泄漏服务端订阅。监督进程退出时再执行 `lark-cli event stop`。两次冒烟里监听全部退出约 30–40 秒后总线仍在运行，不能指望它自动退出。
- 实时事件之外，每个群定期读一次群历史来补漏。游标只在整轮成功后才前移，并回退 5 秒；首轮只设游标，不读历史。实时事件、补历史、话题轮询三种入口对同一条消息算出相同的键，补漏不会造成重复处理。
- 断线期间的事件平台也会补送，按 `message_id` 去重。补送的消息按创建时间判断是否已过时。
- 助手只能以 bot 身份调用 `lark-cli`：所有调用显式带 `--as bot`，并经过一个只放行 bot 身份的包装脚本，助手进程拿不到用户身份的调用途径。这一条借自原型。它在安装时就要求 CLI 只允许 bot 身份，理由是执行者会调用这个 CLI，如果它还允许用户身份，执行者就能以用户身份行事。

### 权限

这个应用需要的权限都已开通并生效。

| 能力 | 权限 | 状态 |
| --- | --- | --- |
| 发消息、发卡片、话题内回复 | `im:message` | 已验证 |
| 收点名它的消息、单聊消息 | `im:message.group_at_msg:readonly`、`im:message.p2p_msg:readonly` | 已验证 |
| 表情事件与读取 | `im:message.reactions:read` | 已验证 |
| 按钮回调 | 后台订阅 `card.action.trigger` | 已验证 |
| 群里全部消息、话题、群历史 | `im:message.group_msg`（敏感权限） | 已验证 |
| 群成员列表 | `im:chat.members:read` | 已验证，带姓名 |

平台不再替助手挡掉不带 @ 的消息：机器人进了哪个群，就能收到那个群的全部消息并读到历史。回答模式下「只处理点名的消息」要靠助手的准入表保证。把机器人拉进部门群之前，先在群里说明它会读取群消息。助手实现之前，本机没有任何常驻监听在跑。

### Source 与准入（快路径，纯程序）

Source 在任何模型调用之前做四件事：

- 丢掉机器人自己发的消息。
- 丢掉不在 `config/group-assistant.yaml` 白名单里的群。
- 按 `message_id` 去重。官方明确要求不要依赖 `event_id`。表情和卡片回调事件用 `message_id`、操作者、动作时间组成键。
- 把消息归到讨论。话题号是「群 ID 加根消息 ID」，没有根消息的消息自成一个话题。主频道里没有话题的消息另按时间簇归并：10 分钟内、相邻间隔不超过 5 分钟。

每条消息都留一条去向记录，写明它被挡下、被研判还是被采纳，以及原因。

准入表是入口的全部规则，由程序裁决：

| 单元格 | 原型里的可选值 | 本设计的取值 |
| --- | --- | --- |
| 名单上的人，没有点名助手 | 推断候选 / 不处理 | 推断候选 |
| 不在名单上的人，点名了助手 | 明确请求 / 推断候选 / 不处理 | 明确请求 |
| 不在名单上的人，没有点名助手 | 推断候选 / 不处理 | 推断候选 |
| 名单上的机器人 | 只能是推断候选 | 不配置 |
| 其他机器人 | 不准入 | 不准入 |

- 本设计不设人员名单。部门群本身就是向同事开放的对话，群里任何人点名助手都是明确请求。
- 点名与否只看事件里的 `mentions` 是否包含机器人，不看文本。准入只读消息的元数据：发送者、是否点名、所属群。它不读正文。
- 接受模式决定推断候选的去向：

| 模式 | 推断候选 |
| --- | --- |
| `off`（默认） | 不研判 |
| `observe` | 照样研判，记下「本会接受」和会发的内容，不发送 |
| `auto` | 研判通过就发送 |

- 明确请求在每种模式下都照常回答。接受模式、规则和准入表只能在本机 CLI 上改。
- 私聊只应答本群成员，用群成员列表判断。
- 事件自带 `root_id` / `thread_id` / `reply_to` / `mentions`，这依赖 lark-cli 1.0.100，已在真实事件里验证。回复发回同一个话题。

### 研判与规则

- 规则是具名、可单独开关的单元，每条用自然语言写明它针对哪种讨论。首批两条：`prior_art`，有人在找先例或问有没有人做过；`related_evidence`，大家在讨论一个方案，而日报库里有直接相关的、已核实的结果。
- 每次研判对每条启用的规则各给一次结论，不论是否命中。至少一条规则命中才算通过。
- 通过主动研判必须引用原消息片段作为依据，程序校验这段引用确实是原消息的子串。原型只要求这个字段非空，不校验真伪；这里比它严一步。
- 每条决策记录所依据的策略版本。规则、接受模式和准入表的内容一起算出版本号，任何一项改了，版本就变。影子期的记录因此可以按版本比较，哪条规则太吵也能单独关掉。
- 研判由会话执行。进程把讨论窗口、启用的规则和候选条目打包成一个任务，会话按 Schema 写回每条规则的结论和原文引用。输出不过校验，或引用不是原消息的子串时，这次研判按未通过处理。
- 研判任务 5 分钟内没有被执行就过期，直接丢弃，不发言。讨论冷了再接话没有意义。

### 什么情况下发言

**回答。** 有人点名助手，包括在话题里点名。只过 Source 和准入，再加每人每分钟 10 次的限速。分两种情况：

- 词法检索有把握：进程直接回，约 2 秒，不需要会话。
- 词法检索没有把握：进程排一个「细查」任务，会话改写查询、从候选里选，结果通过校验后由进程回，通常一两分钟。会话没有按时回来时，进程用已有的低把握结果收尾：相关性偏低的近似条目标注「相关度低」，并注明没能细查；一条都没有时回一句「日报库里没有直接相关的」。

每个点名最多引出一条回复，所以慢的那条路上不发「稍等」。

**主动推荐。** 只在 `observe` 和 `auto` 下评估，依次过三道闸门：

| 闸门 | 执行者 | 默认规则 | 不过则 |
| --- | --- | --- | --- |
| 成形 | 程序 | 同一讨论至少 3 条、至少 2 人参与，且已安静 90 秒；该讨论 24 小时内助手没有主动发过言；当天主动发言少于 3 条；在工作时间内 | 不评估 |
| 研判 | 会话 | 按上面的规则逐条给结论，并引用原文 | 沉默 |
| 命中 | 程序 + 会话 | 至少 1 条的相关性达到「高」 | 沉默 |

- 成形闸门里的几个上限是本设计自己加的，原型没有对应机制。它们先做成代码常量，试用证明需要调再变成配置。
- 任何人对接话点 👎，助手在该讨论里不再主动发言。全局静音只认本机 CLI：`assistant mute [时长]`。

**锚定讨论。** 讨论挂在本助手发出的 idea 卡片下面时，助手带着该 idea 的上下文检索，并降低成形门槛，因为卡片本身就是在邀请讨论。

### 检索与答复管线

| 步骤 | 进程直接回答 | 会话细查 |
| --- | --- | --- |
| 1 构造查询 | 去掉 @ 的那条消息，加上它回复的消息和所在话题的根消息 | 会话输出 3–6 条中英检索式、话题提示、触发原文片段 |
| 2 词法召回 | 英文按词、中文二元字组，BM25 加权，取前 20。话题提示命中 `topic_id` / `direction_id` 时加权 | 同左 |
| 3 选择 | 按分数取前 3，低于下限视为无命中 | 会话从 20 条里选条目并给出相关性等级。主动推荐选 1 条，回答至多 3 条 |
| 4 点题 | 无 | 会话指出这条对应讨论里的哪句原文 |
| 5 校验与组装 | 引用必须在索引快照里；标题、日期、结论、链接取索引原文 | 同左，另校验点题片段是原消息子串 |
| 6 发送 | 在该话题内回复，先落库后发送 | 同左 |

进程直接回答不需要会话，现在就能开始试用。会话细查和主动推荐需要开着会话。

送给会话的讨论窗口：至多 20 条，发送者替换为「同事 A / B」。每条带上它回复的消息；触发消息另带前后各 5 条相邻消息和话题的根消息。每条截断到 400 字符，更长的只留开头并标记「已截断」。这是文章里「从最少信息开始、按需内联紧邻信息」的做法；原型给研判的窗口也是这样组织的。

索引内容：

| 类型 | 数量 | 索引文本 | 回复里的标记 |
| --- | --- | --- | --- |
| 日报条目 | 777 | 标题、`keywords`、`core_conclusion`、`mechanism` | 📄 日报，带期次，链到归档页锚点 |
| 雷达题录 | 478 | 标题 | 📡 雷达题录（日报未展开） |
| Idea | 51 | 标题、`problem`、`hypothesis`、`mechanism` | 💡 想法，带状态与首次出现期次 |
| Roadmap | 11 | 专题名、`summary`、分支摘要 | 🗺 专题脉络，每个回复至多 1 条 |

候选（316 条）不进索引：它们是审计记录，不是确认的知识。

索引由 `assistant index build` 确定性重建，记录输入摘要（`archive/index.json` 与 `knowledge/index.json`）。每次归档发布和知识阶段结束后重建；助手启动时发现摘要变化也会自动重建。同一输入两次构建除时间戳外必须字节等价。

### 回复形态

回复只有两种，能不能发由程序把关，不只靠提示词：

| 种类 | 程序检查的条件 |
| --- | --- |
| 回答 | 对应的消息来自人，并且点名了助手 |
| 推荐 | 接受模式是 `auto`，并且对应的决策有命中的规则和通过校验的原文引用 |

- 每条消息最多引出一条回复。幂等键由消息 ID 和回复种类算出。
- 助手不主动请人评价，不发进度，不发「我正在处理」。

主动推荐默认一句话、一个链接：

```text
这个方向日报里有一篇相关的：<条目标题>（2026-11-25）：<结论首句>  查看详情
```

回答至多 3 条。每条的正文是条目自己的结论原文，不是模型对论文的转述：

```text
日报库里相关的：
• 📄 <条目标题>（2026-11-25）：<core_conclusion 首句>  查看详情
• 💡 <Idea 标题>（observing，2026-11-11 起）：<hypothesis 首句>  查看详情
• 🗺 专题脉络：<专题名>  查看详情
觉得有用点 👍，不相关点 👎
```

- 单次回复不超过 100 词，用分词器数中英文混排的词数，网址不计入。原型把链接文字和网址都算在内，对要带链接的回复偏紧，这里放宽了算法。
- 用同事口吻，不加身份开场，用讨论本身的语言。发送前对每个分句自问：删掉它，会不会让人看不懂结果或没法行动？不会就删。
- 有人问「你为什么发这个」，助手用决策记录里命中的规则和引用的原文回答，不临时编理由。
- 对推荐点 👍 / 👎 是检索质量的标注数据。

### Idea 卡片反馈

- 节奏与选择规则沿用 11-13 草案：每周至多 3 条；本期有状态变化或新证据的优先，其次本期新建，至多 1 条零反馈的旧 idea 翻新。
- 形态从「markdown + 表情」改为交互卡片，带四个按钮：值得投入验证、不看好、证据不足、已有人做过。表情回应的语义不变，照常计入。
- 按钮回调与表情事件到达即入账，两者都带操作者 open_id。`collect` 用表情点查做对账。
- 卡片话题里的文字讨论能读到，计入讨论量。
- 通俗化文案由「卡片文案」语义任务生成，推送前先出预览。
- 卡片下的话题属于锚定讨论：助手知道讨论的是哪条 idea。同事在话题里点名助手提问，回复发回同一个话题。

### 状态与台账

`workspace/assistant/assistant.sqlite`（gitignore）：

| 表 | 内容 |
| --- | --- |
| `events` | 原始事件，只追加。正文保留 30 天，到期只留哈希 |
| `dispositions` | 每条消息的去向：挡下、研判、采纳，以及原因 |
| `threads` | 讨论状态：成员消息、最后活动时间、锚定的 idea、本讨论内的发言记录 |
| `decisions` | 每次研判：各闸门结果、每条规则的结论、命中的规则、原文引用、检索分数、会话的原始输出、动作（已发 / 沉默 / 影子）、策略版本 |
| `tasks` | 语义任务：待执行、已采纳、过期。每个任务带输入、输出和校验结果 |
| `outbox` | 外发消息：待发、已发、失败，幂等键与 message_id |
| `feedback` | 对 idea 和对推荐的反馈事件，含操作者 open_id（仅本地） |
| `meta` | 心跳、接受模式及开启时间、索引摘要、Source 的读取位置 |

检索索引快照存 `workspace/assistant/index/<digest>.json`。

会话看到的内容一定先落日志：送给会话的讨论窗口和会话写回的原始输出都存在本地，影子期靠它复盘。

每个 idea 的关注度有三个来源，按 idea 聚合后只进本地台账：卡片按钮与表情；助手推荐后被点 👍 的次数；卡片话题里的讨论条数与人数。

### 自检

文章里的 Watchdog 在公开的原型里没有实现。本设计用一个轻量版本：

- 每天用几个固定问题验证检索还正常。索引过期或检索异常时在 `status` 里报出。
- 主动发言达到当天上限，或推荐被点 👎 的比例超过阈值时，自动把接受模式退回 `off`，并在本机留一条记录。
- 自检不向群里发任何消息。

### CLI

```bash
python briefing.py assistant index build              # 重建索引
python briefing.py assistant ask "<问题>"             # 离线走完整管线，只打印不发送
python briefing.py assistant serve                    # 常驻进程；会话把它作为后台任务拉起
python briefing.py assistant stop                     # 停止进程
python briefing.py assistant tasks wait               # 阻塞到有语义任务；会话靠它被叫醒
python briefing.py assistant tasks card --task <id>   # 取只读执行卡
python briefing.py assistant tasks apply --task <id>  # 校验并采纳任务输出
python briefing.py assistant status                   # 心跳、索引新鲜度、今日去向与决策计数、待执行和过期的任务数、自检结果
python briefing.py assistant mode explicit on|off   # 回答点名它的消息
python briefing.py assistant mode proactive off|observe|auto
python briefing.py assistant rules                  # 列出规则、开关和当前策略版本
python briefing.py assistant mute [时长]            # 全局静音
python briefing.py assistant review                 # 列出待评的影子决策，按规则汇总
python briefing.py assistant stats
python briefing.py assistant e2e                    # 回放端到端，不联网
python briefing.py assistant e2e --live              # 实传端到端，对着测试群真实发送
python briefing.py feedback prepare|push --confirm-send|collect|status
```

代码放在独立的 `briefing_skill/assistant/` 包里，不 import 流水线模块，避免两边意外耦合。

### 语义层由 ZCode 会话执行

语义判断不接模型 API，也不用 `codex` 或 `claude`。它是几个有界任务，由一个 ZCode 会话作为宿主执行，和简报流水线是同一个模式：进程产出任务文件，会话按 Schema 写回输出，进程校验后采纳。仓库「实现不绑定模型 API」的约定因此保持完整，早先版本里写的那处例外取消。

语义任务只有三种：

| 任务 | 什么时候排 | 会话做什么 | 多久过期 |
| --- | --- | --- | --- |
| 细查 | 点名提问，词法检索没有把握 | 改写查询，从候选里选条目并点题 | 10 分钟 |
| 研判 | 成形闸门通过，接受模式是 `observe` 或 `auto` | 对每条启用的规则各给一次结论，引用原文 | 5 分钟 |
| 卡片文案 | 每周推送前 | 把 idea 的字段写成通俗的卡片文案 | 当天 |

叫醒会话的规则：

- 攒批。任务到齐后至少等 60 秒再叫，一次把所有待执行的任务交给会话。
- 每日上限。一天叫醒的次数有上限。达到后细查任务按过期处理，研判任务丢弃，第二天恢复。数值在内测时量过一次叫醒的耗时和 token 之后再定。
- 空闲不叫。`tasks wait` 在没有任务时一直阻塞，会话空闲时不消耗 token。
- `tasks wait` 返回的内容末尾带下一步提示。会话被唤起后照着做：取执行卡、执行、apply、再挂起等待。会话上下文被压缩之后，也靠这行提示接上。

会话的约束：

- 专用会话。不能是跑简报定时任务的那个会话。
- 会话只经任务文件进出，不直接调用 `lark-cli`，不接触凭据。`lark-cli` 只由进程经 bot 身份的包装脚本调用。这台机器上有你的用户授权，会话循环不使用它。这两条靠操作说明和抽检来保证，不是代码强制。
- 每次被叫醒只做几件小事，输出都很短。上下文变长后重开会话。
- 讨论内容会发给 ZCode 背后的模型提供方，和简报现在用的是同一个，不再需要另找模型服务。
- 原型的执行器带着完整工具并以完全访问权限运行，本设计不采用。ZCode 会话本身什么工具都有，但在这个循环里只被要求做任务文件里的事。

模型提供方偶尔会长时间停滞，简报运行里出现过。停滞期间进程的回答照常，受影响的只有细查和主动推荐。

## Compatibility and migration

纯增量：新配置文件（默认全部关闭）、新包、新子命令、gitignore 新增条目。试用期不需要 launchd 任务。不改 Schema、不改任何 knowledge 文件、不改任务顺序、不改流水线模块。简报运行与环境不受影响，无迁移。11-13 草案标记为被本文取代。

lark-cli 已于 2026-11-27 从 1.0.60 升级到 1.0.100。应用配置和登录态未受影响，读路径回归通过。

## Failure, recovery, and rollback

- **进程或子进程退出**：launchd 拉起主进程；子进程 1 秒后重启，连续失败时退避到最多 60 秒，45 秒内没有就绪就结束它并报错。鉴权类错误不重试，`status` 报出缺的 scope。
- **会话关闭、电脑休眠或模型提供方停滞**：进程直接回答的那条路不受影响。语义任务按各自的期限过期：细查任务过期后，进程用低把握的结果收尾并注明没能细查；研判任务过期后丢弃，不发言。待执行和过期的任务数在 `status` 里报出。
- **发送失败**：Outbox 里保持待发，用同一幂等键重试，不产生重复消息。目的地已经不存在时记为「无法送达」，不再排队。
- **本机休眠或断网**：助手离线。恢复后平台会补送断线期间的事件，窗口多长未知；平台没有补送到的，由定期补历史按游标找回。助手只补答 2 小时内点名的提问并注明是补答；错过的主动窗口直接丢弃。
- **规则或接受模式变了**：策略版本随之改变。在途的研判任务作废，已发出的回复不撤回。
- **索引过期或检索异常**：`status` 报出；发布流程末尾的重建命令把索引拉平。
- **自检触发暂停**：主动发言达到当天上限，或推荐被点 👎 的比例超过阈值时，接受模式自动退回 `off`，并在本机留一条记录。要重新开启只能在本机 CLI 上操作。
- **回滚**：`assistant stop`、删除 `workspace/assistant/`。仓库内没有任何状态被触碰。

## Verification

验证有六块不需要你动手。其中实传端到端和长时间运行需要你的授权有效。另有一块是只能由人来做的事。 每一项功能对应的逐个场景见下一节「端到端功能验证」。

**单元测试。** 分词与检索的确定性（同输入两次结果一致）、索引摘要、引用校验、准入表、策略版本、限速、回复种类的把关、Outbox 幂等、Source 的游标与回退、三种入口同键、去名、bot 身份包装。夹具用合成事件，合成数据不进长期统计。另有两条防泄漏断言，对应约束 2。

**任务协议。** 会话的输出要过 Schema 校验才会被采纳。用脚本替身模拟会话，覆盖合法输出、非法输出和过期三种情况；攒批和每日上限也有测试。一次叫醒的耗时和 token 在内测时实测，用来定每日上限的数值。

**回放端到端。** 不联网，每次改代码都跑。夹具是 2026-11-27 冒烟时录到的真实事件（收消息、表情增删、卡片回调、断线补送），加上合成的讨论序列。事件从入口一路跑到 Outbox，传输层换成捕获器。覆盖：Source 的四件事、归并到话题、准入表的每个格子、成形闸门、observe 只记不发、100 词上限、引用校验、策略版本变更时在途任务作废。

**实传端到端。** 对着测试群跑，真实发送。`assistant e2e --live` 在独立的状态目录上起一个进程，绑定测试群。脚本以你的身份发消息（`lark-cli --as user`），机器人收到的是真实的用户消息事件，走完整链路后回复；脚本再读话题来断言。逐个场景：

- 以你的身份点名机器人提问，2 秒内话题里出现回复；链接能打开；每个点名只有一条回复。
- 杀掉进程再重启，没有重复发送。
- 以你的身份在话题里回复，助手的回复落在同一个话题里。
- 以你的身份给一条推荐点 👎，这个讨论不再有主动发言。
- 接受模式是 `observe` 时，研判照常记录，群里没有任何消息。
- 每个场景结束后，去向计数与预期一致。

实传端到端不需要任何测试专用的开关，进程跑的就是生产代码。需要多人参与的成形闸门只在回放端到端里测，因为只有你一个身份可以用来发消息。

脚本以你的身份发消息时写死测试群的 ID，换一个群就拒绝执行，消息都带 `[E2E]` 前缀。它不会在部门群里以你的身份发任何东西。测试消息不撤回，撤回是高风险写操作，需要你明确确认。

以你的身份调用需要你的授权，7 天后过期，两次实测都一样，见 Problem and evidence。过期之后需要你重新授权一次，这是实传端到端唯一要麻烦你的地方。必需的权限有八项：`im:message`、`im:message.send_as_user`、`im:message.group_msg:get_as_user`、`im:message.p2p_msg:get_as_user`、`im:message.reactions:read`、`im:message.reactions:write_only`、`im:chat:read`、`offline_access`。官方文档写明，以用户身份发消息必须同时有前两项。你的令牌实际带着 161 项权限，是以前授权的累计；脚本只用这八项。

一个实测到的限制：机器人收不到自己发的消息的事件。2026-11-28 验证过，自发一条消息后监听 75 秒，收到 0 个事件。所以测试不能靠机器人自问自答，要以你的身份来问。

**长时间运行。** 进程在测试群里连跑一夜或一个周末，定时以你的身份发探针。看心跳、去重、有没有重复发送、状态库的增长。

**离线评测。** 30–50 题，不需要你来出题：

- 起步的题由脚本从日报条目反向改写，2026-11-27 探针里的 6 道口语化问题也放进去。这类题的答案是已知的，命中的标准是源条目出现在结果里。
- 你和同事在群里的真实提问自动积累进题库。助手回复上的 👍 和 👎 就是标注。

初始阈值如下，阶段 1 结束时按实测校准：

| 层 | 指标 | 初始阈值 |
| --- | --- | --- |
| 词法层 | Recall@20 | ≥ 0.85 |
| 回答 | 前 3 条至少 1 条相关的比例 | ≥ 0.85 |
| 主动推荐（observe 模式） | 影子决策里「该说」的比例，按规则分别统计 | ≥ 0.70 |

**只能由人来的四件事：**

- 你的授权过期之后重新授权一次。上次的实际情况是 7 天。
- 卡片按钮的真实点击。回放用的是录到的真实回调事件；卡片格式改了才需要你点一次。
- 影子期里「这条该不该说」的判断。这是设计上留给人的决定，不是测试。
- 部门同事入群后的真实表现。

会话循环本身（等待、执行、apply、再等待）需要一个真实的 ZCode 会话，进不了自动测试。它由我在一个会话里跑，不需要你动手，每次改了任务协议之后跑一次。实测结论写进 `docs/operations/group-assistant.md`。
