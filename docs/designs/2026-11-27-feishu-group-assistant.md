## Problem and evidence

两个缺口，可以在同一个群里一起补：

1. **Idea 价值不可衡量。** `evidence_for` / `evidence_against` 是 AI 对已发布证据的机器分类，不是人类反馈。51 个正式 Idea（28 seed / 22 observing / 1 ready_for_validation）没有一条经过同事评价；「表述抽象、看不懂」是用户已两次提出的问题。
2. **讨论与沉淀脱节。** 日报库有 35 期 777 条条目和 478 条雷达题录，知识库有 51 个 Idea、11 条 Roadmap，全部已公开、可链接。但群里讨论一个方向时没人会想起去查，讨论本身也不留记录。

用户 2026-11-27 的方向：把部门同事拉进一个飞书群，大家讨论 idea 时助手主动理解讨论、检索历史日报与 idea 库、推荐相关条目，参照 DeepSeek 的 Super-agent。

**从 Super-agent 借什么。** 公开报道与开源原型说明（链接见文末）给出的可借鉴原则：

- 常驻的 Router 只判断「这事该不该接」，不亲自干活。规则快路径先过滤，模型慢路径只处理剩下的少数事件（其合成负载里约 300 条消息产生约 20 个工作请求）。
- 只在被请求、或书面规则允许时行动；拿不出结果就沉默，不汇报过程。
- 新的主动规则默认 dry-run：只判断、只记日志，人工看过日志再放开。
- 模型只提议、程序裁决；对外动作先落库再执行；外部文本永远是数据。

不借的部分：Super-agent 的 Worker 会执行有副作用的任务（复现 bug、提交 PR）。本助手的「工作」只有检索与回复，不写代码、不发邮件、不改仓库。

**本机与语料实测（2026-11-27）。**

lark-cli 1.0.60：

- bot 身份 ready；user 身份的 refresh token 已于 2026-10-18 过期。全程走 bot。
- 已授予：`im:message`、`im:message:readonly`、`im:message.reactions:read`、`im:chat:read`、`im:chat.members:read`、`contact:user.base:readonly`。
- 未授予：`im:message.p2p_msg:readonly`、`im:message.group_at_msg:readonly`、`im:message.group_msg:readonly`。
- `im.message.receive_v1` 仅 bot 身份。`lark-cli event consume` 输出扁平化事件：`.content` 已转成纯文本，`sender_id` 只有 open_id。`event schema` 列出的输出字段里没有线程字段（`root_id` / `thread_id`）。
- 冒烟实测（2026-11-27，bot → 应用所有者单聊）：
  - 收消息事件与表情事件的 `event consume` 正常启动，`feishu-websocket: connected`，超时后自行退出。长连接可用，这两个事件在后台已订阅。
  - `card.action.trigger` 启动即失败，退出码 2：后台未订阅该回调。CLI 有预检，并给出一条一键订阅链接。
  - 真实发送成功：文本、带四个按钮的交互卡片、`--reply-in-thread` 话题内回复。
  - 幂等有效：同一个 idempotency key 发了 3 次，历史里只有一条消息。
  - 单聊消息事件在现有 scope 下送达，从消息创建到事件送达约 0.3 秒。`auth check` 报缺的 `im:message.p2p_msg:readonly` 没有挡住事件。
  - 扁平化事件只有 11 个字段，没有 `root_id`、`parent_id`、`thread_id`、`mentions`。用户在话题里的回复要靠消息详情接口补查，已验证能拿到这三个字段。
  - bot 能读单聊历史、按根消息 ID 列出整条话题、查询自己消息上的表情（当时为空）。
  - bot 身份解析用户信息只返回 open_id 与 union_id，没有姓名。
- 仍未实测：非空的表情读取与表情事件；卡片回调（要等后台订阅）；bot 在群里的全部行为（要等入群，尤其是群消息在现有 scope 下是否同样送达）。

仓库与语料：

- 仓库与站点是 PUBLIC，`archive/`、`knowledge/` 直接发布到 GitHub Pages。任何群聊内容进入会被提交的路径都会公开。
- `docs/architecture.md` 规定实现不绑定模型 API、由宿主执行任务文件。仓库里没有检索索引、没有嵌入或全文检索代码；唯一的密钥是生图用的 `workspace/secrets/image_api.json`，走第三方中转，不适合承载内部群聊。本机装有 `codex` 与 `claude` CLI。
- 可索引文本的质量高：每条日报条目已有中文 `core_conclusion`、`mechanism`、`keywords` 和事实核查状态，Idea 有 `title` / `problem` / `hypothesis`。venv 的 SQLite 3.53.4 支持 FTS5。
- 一次只读探针（828 篇 = 777 条目 + 51 Idea，英文按词、中文二元字组的 BM25；6 条自拟口语化问题，按标题判断相关性）：纯词法检索在 5 条问题上把相关条目送进前三，其中一条精确命中原 Idea。漏掉的一条是「多智能体上下文超长怎么压缩」：语料里有 3 篇上下文压缩的条目，被查询里的「多智能体」盖住了。样本只有 6 条，出题人知道语料，不能当评测结论；只说明两点——检索骨架不必依赖模型，而查询改写需要。

## Goals and non-goals

目标：

1. **显式问答**：群里 @助手 提问，必答；答不出就明说。
2. **主动推荐**：大家讨论一个方向时，助手判断日报库或 idea 库帮得上忙才在话题里接一句，帮不上就沉默。
3. **Idea 反馈**：每周推送少量通俗化的 idea 卡片，同事一次点按即可评价，讨论留在卡片的话题里。
4. **可衡量**：提问量、推荐的有用率、每个 idea 的评价与讨论量都进本地台账。
5. **可试、可退**：主动能力先影子运行，随时一键静音，关闭后不留残余。

非目标：

- 不执行有副作用的任务（写代码、发邮件、改仓库、建文档）。
- 不把群聊内容或讨论中产生的新想法写进本仓库。「自动沉淀群聊 idea」不在范围内，原因见约束 2。
- 不改动简报流水线、任务队列和证据边界。助手是流水线之外的独立子系统。
- 不公开发布匿名聚合数据。

## Constraints and invariants

1. **只读公开库。** 助手对 `archive/` 与 `knowledge/` 只读。索引只从已发布文件构建，不读候选池、全文缓存或运行目录。助手推荐的每一条都是已经公开的条目。
2. **公开仓库红线。** 助手的全部状态只写入 gitignore 的 `workspace/assistant/`。实现时加测试，用 `git check-ignore` 断言每个状态路径，并断言助手模块不向该目录之外写文件。
3. **只在被请求或规则允许时发言。** 显式问答由用户用 CLI 显式开启，开启记录带时间。主动推荐默认关闭，经影子运行后由用户开启。Idea 卡片推送沿用 `--confirm-send`。
4. **模型只提议，程序裁决。** 回复里引用的条目必须同时存在于当前索引快照和送进模型的候选集。标题、日期、结论、链接由程序从索引生成，不采信模型输出里的任何 URL。模型写的「对应你们说的那句话」必须是原消息的子串，由程序校验。
5. **外部文本永远是数据。** 群消息只作为待分析内容进入提示词，其中的指令不执行。群消息不能触发任何命令；静音、切换模式、改配置只认本机 CLI。
6. **沉默优先。** 主动模式的任何一道闸门不过就不发言，并在决策日志里写明停在哪一道。
7. **先落库再发送。** 每条外发消息先写 Outbox，再调用 lark-cli，带幂等键。
8. **隐私最小化。** 送给模型的只有白名单群里当前讨论窗口的文本：至多 20 条、每条截断、发送者替换为「同事 A / B」。原始事件本地保留 30 天，之后只留哈希和统计。

## Proposed design

### 总览

```text
飞书群（部门）
  │ 长连接事件：lark-cli event consume × 4（消息 / 表情增 / 表情删 / 卡片回调）
  ▼
群助手进程（本机 launchd 保活；确定性核心，不绑定流水线）
  ├─ 入口闸门（程序）：群白名单、发送者资格、去重
  ├─ 讨论归并（程序）：话题串，或主频道时间簇
  ├─ 触发裁决：显式 @ → 必答；主动 → 闸门 G1–G3
  ├─ 词法召回（程序）：BM25 over 日报条目 / 雷达题录 / Idea / Roadmap
  ├─ 语义层（模型，可选）：改写查询 → 选条目、点题
  ├─ 校验与组装（程序）：引用 ⊆ 索引快照；链接由程序生成
  ├─ Outbox：先落库，再话题内回复
  └─ 本地台账：事件、讨论、决策日志、反馈
        ▲ 只读
  archive/（35 期）+ knowledge/（Idea / Roadmap）→ 检索索引
```

### 常驻进程与事件接入

- `briefing.py assistant serve` 是唯一的常驻进程，由 launchd 保活。它按「一个 EventKey 一个子进程」拉起 `lark-cli event consume`，读取 stdout 的 NDJSON。
- 子进程在 stderr 输出 `[event] ready` 表示就绪，监督进程据此开始读取。监督进程为每个子进程保持 stdin 打开：无界 consume 遇到 stdin EOF 会自行退出。停止只用 SIGTERM，不用 `kill -9`，否则会泄漏服务端订阅。
- 心跳写入本地状态。子进程非零退出按退避重启；`missing_scope` 这类鉴权错误不重试，直接在 `status` 里报出。
- 拉取只用于对账：`feedback collect` 定期重拉已推送消息上的表情，补偿离线期间漏掉的事件。

### 权限阶梯

| 级别 | 需要新增 | 得到什么 | 助手能看到的消息 |
| --- | --- | --- | --- |
| L0 | 后台订阅 `card.action.trigger` 回调（表情事件已订阅），不需要新 scope | 表情事件、卡片按钮回调 → Idea 反馈回路 | 只有点在自己消息上的互动 |
| L1 | bot 入群。是否还需要 `im:message.group_at_msg:readonly`，要入群后实测 | 群里 @助手 → 显式问答 | 只有点名发给它的消息 |
| L2 | 是否需要 `im:message.group_msg:readonly`，同样要实测 | 全部群消息 → 主动推荐 | 群里的全部消息 |

单聊实测表明，宽 scope `im:message` 已足以让消息事件送达，所以 `auth check` 报缺的细分 scope 不等于功能不可用。群消息是否同理要等入群验证。若同理，bot 一入群就能收到全部群消息，「只看点名消息」要由助手的入口闸门保证，而不是由平台权限保证。需要新 scope 时，在开发者后台改权限并发布新版本，可能需要管理员审批。

先在一个只有应用所有者和机器人的测试群里验证，再决定是否申请权限、何时把机器人拉进部门群。

### 入口闸门与讨论归并（快路径，纯程序）

- 群白名单：只处理 `config/group-assistant.yaml` 里配置的群。私聊只应答该群的成员。
- 发送者资格：排除机器人发的消息和助手自己发的消息。成员允许 / 排除名单在代码里判断，先于任何模型调用。
- 去重：按 `event_id`。
- 一个讨论 = 一个话题串（`root_id` 相同）。主频道里没有话题时退化为时间簇：10 分钟窗口内、相邻消息间隔不超过 5 分钟。
- 扁平化事件里没有线程字段（已实测），所以每条通过白名单的消息都要补一次消息详情查询来归并讨论。消息详情返回 `root_id` / `parent_id` / `thread_id`。

### 触发策略

**显式（必答）。** 群里 @助手，或助手收到的私聊。只过入口闸门，再加每人每分钟 10 次的限速。命中就回。没有命中时回「日报库里没有直接相关的」，相关性偏低的近似条目标注「相关度低」一起给出，由人判断。

**主动（克制）。** 三道闸门依次过：

| 闸门 | 执行者 | 默认规则 | 不过则 |
| --- | --- | --- | --- |
| G1 成形 | 程序 | 同一讨论至少 3 条、至少 2 人参与，且已安静 90 秒；该讨论 24 小时内助手没有主动发过言；当天主动发言少于 3 条；在工作时间内 | 不评估 |
| G2 判断 | 模型 | 这是不是技术讨论，且日报库或 idea 库可能帮上忙（找先例、方案讨论、现象解释、选型比较）。必须引用原消息片段为证 | 沉默 |
| G3 命中 | 程序 + 模型 | 至少 1 条的相关性达到「高」 | 沉默 |

- G2 要排除的：闲聊、行政事务、与日报主题无关的技术问题。判断规则用自然语言写在配置里，改策略只改这一段。
- 影子模式下三道闸门照常运行，只把「会怎么回」写进决策日志，不发送。
- 任何人对接话点 👎 或在话题里回「不相关」，助手在该讨论里不再主动发言。全局静音只认本机 CLI：`assistant mute [时长]`。

**锚定讨论。** 讨论挂在本助手发出的 idea 卡片下面时，助手带着该 idea 的上下文检索，并在该讨论里降低 G1 门槛（卡片本身就是在邀请讨论）。

### 检索与答复管线

| 步骤 | v0 纯检索 | v1 语义层 |
| --- | --- | --- |
| 1 构造查询 | 去掉 @ 文本的原消息 | 模型输出 3–6 条中英检索式、话题提示、一句话问题复述、触发原文片段 |
| 2 词法召回 | 英文按词、中文二元字组，BM25 加权，取前 20。话题提示命中 `topic_id` / `direction_id` 时加权 | 同左 |
| 3 选择 | 按分数取前 3，低于下限视为无命中 | 模型从 20 条里选至多 3 条，并给出相关性等级 |
| 4 点题 | 无 | 模型指出每条对应讨论里的哪句原文 |
| 5 校验与组装 | 引用必须在索引快照里；标题、日期、结论、链接取索引原文 | 同左，另校验点题片段是原消息子串 |
| 6 发送 | 在该话题内回复，先落库后发送 | 同左 |

v0 不需要模型，权限批下来就能开始试用。v1 在其上增加语义层，同时解锁主动模式。

索引内容：

| 类型 | 数量 | 索引文本 | 回复里的标记 |
| --- | --- | --- | --- |
| 日报条目 | 777 | 标题、`keywords`、`core_conclusion`、`mechanism` | 📄 日报，带期次，链到归档页锚点 |
| 雷达题录 | 478 | 标题 | 📡 雷达题录（日报未展开） |
| Idea | 51 | 标题、`problem`、`hypothesis`、`mechanism` | 💡 想法，带状态与首次出现期次 |
| Roadmap | 11 | 专题名、`summary`、分支摘要 | 🗺 专题脉络，每个回复至多 1 条 |

候选（316 条）不进索引：它们是审计记录，不是确认的知识。

索引由 `assistant index build` 确定性重建，记录输入摘要（`archive/index.json` 与 `knowledge/index.json`）。每次归档发布和知识阶段结束后重建；助手启动时发现摘要变化也会自动重建。同一输入两次构建除时间戳外必须字节等价。

### 回复形态

```text
我理解你们在讨论：<一句话问题复述>
日报库里相关的：
• 💡 想法｜<Idea 标题>（observing，2026-11-11 起）
   <结论原文首句> —— 对应你们说的「<讨论原文片段>」  查看详情
• 📄 日报｜<条目标题>（2026-11-25）
   <core_conclusion 首句>  查看详情
• 🗺 专题脉络｜<专题名>  查看详情
觉得有用点 👍，不相关点 👎
```

- 首行是模型对讨论的理解，写出来是为了让人能当场纠正。
- 每条的正文是条目自己的结论原文，不是模型对论文的转述。
- 至多 3 个链接。对推荐点 👍 / 👎 是检索质量的标注数据。

### Idea 卡片反馈

- 节奏与选择规则沿用 11-13 草案：每周至多 3 条；本期有状态变化或新证据的优先，其次本期新建，至多 1 条零反馈的旧 idea 翻新。
- 形态从「markdown + 表情」改为交互卡片，带四个按钮：值得投入验证、不看好、证据不足、已有人做过。表情回应的语义不变，照常计入。
- 按钮回调与表情事件到达即入账，不再等到下一期运行开头才收集；`collect` 降级为对账。
- 通俗化文案仍由宿主执行的有界任务生成，不进助手的模型适配器。推送前先出预览。
- 卡片下的话题属于锚定讨论：助手知道讨论的是哪条 idea。

### 状态与台账

`workspace/assistant/assistant.sqlite`（gitignore）：

| 表 | 内容 |
| --- | --- |
| `events` | 原始事件。正文保留 30 天，到期只留哈希 |
| `threads` | 讨论状态：成员消息、最后活动时间、锚定的 idea |
| `decisions` | 每次触发评估：各闸门结果、检索分数、模型输出、动作（已发 / 沉默 / 影子）与停留的闸门 |
| `outbox` | 外发消息：待发、已发、失败，幂等键与 message_id |
| `feedback` | 对 idea 和对推荐的反馈事件，含操作者 open_id（仅本地；bot 身份目前解析不出姓名） |
| `meta` | 心跳、模式开关及开启时间、索引摘要 |

检索索引快照存 `workspace/assistant/index/<digest>.json`。

每个 idea 的关注度有三个来源，按 idea 聚合后只进本地台账：卡片按钮与表情；卡片话题里的讨论条数与人数；助手推荐后被点 👍 的次数。

### CLI

```bash
python briefing.py assistant index build            # 重建索引
python briefing.py assistant ask "<问题>"           # 离线走完整管线，只打印不发送
python briefing.py assistant serve                  # 常驻
python briefing.py assistant status                 # 心跳、索引新鲜度、今日决策与外发计数
python briefing.py assistant mode explicit on|off   # 显式问答
python briefing.py assistant mode proactive shadow|on|off
python briefing.py assistant mute [时长]            # 全局静音
python briefing.py assistant review                 # 列出待评的影子决策
python briefing.py assistant stats
python briefing.py feedback prepare|push --confirm-send|collect|status
```

代码放在独立的 `briefing_skill/assistant/` 包里，不 import 流水线模块，避免两边意外耦合。

### 模型接入

这是全仓库唯一需要绑定模型的地方，也是对「实现不绑定模型 API」的一处显式例外，限定在 `briefing_skill/assistant/` 内。语义层只有两个小调用：理解讨论并改写查询；从 20 条候选里选条目并点题。每次评估约 3–5k token。

适配器两种：`api`（OpenAI 兼容的聊天接口，密钥放 `workspace/secrets/assistant_model.json`）与 `cli`（`codex exec` 或 `claude -p`，用于起步和影子期）。v0 用 `none`。

## Compatibility and migration

纯增量：新配置文件（默认全部关闭）、新包、新子命令、gitignore 新增条目、一个 launchd 任务。不改 Schema、不改任何 knowledge 文件、不改任务顺序、不改流水线模块。简报运行与环境不受影响，无迁移。11-13 草案标记为被本文取代。

## Failure, recovery, and rollback

- **进程或子进程退出**：launchd 拉起主进程；子进程按退避重启；鉴权类错误不重试，`status` 报出缺的 scope。
- **模型不可用**：显式问答退回 v0 的纯检索回复；主动模式不发言。两种降级都记入决策日志。
- **发送失败**：Outbox 里保持待发，用同一幂等键重试，不产生重复消息。
- **本机休眠或断网**：助手离线。恢复后只补答 2 小时内点名的提问并注明是补答；错过的主动窗口直接丢弃。能否补答取决于读取历史消息的权限，冒烟时确认。
- **索引过期**：`status` 报出输入摘要不一致；发布流程末尾的重建命令把它拉平。
- **回滚**：`assistant mode off`、卸载 launchd 任务、删除 `workspace/assistant/`。仓库内没有任何状态被触碰。

## Verification

- 单元测试：分词与检索的确定性（同输入两次结果一致）、索引摘要、引用校验、闸门与限速、Outbox 幂等、去名。夹具用合成事件，合成数据不进长期统计。
- 防泄漏测试：约束 2 的两条断言。
- 离线评测：30–50 题，由三部分组成——你出的真实问题、从条目反向改写的口语化提问、试用中积累的真实提问。初始阈值如下，阶段 1 结束时按实测校准：

| 主动影子 | 影子决策里「该说」的比例 | ≥ 0.70 |
